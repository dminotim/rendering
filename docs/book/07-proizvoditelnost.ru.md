# Часть VII. Производительность

**Выпуски 18–19.** До сих пор нас не волновала цена вызова отрисовки — их было три. Разберём,
где на самом деле уходит процессорное время, и уберём главные накладные расходы: выделение
дескрипторов на каждую отрисовку и передачу параметров через буферы. Заодно добавим чтение
данных с GPU и непрямую отрисовку.

---

## Выпуск 18. Push-константы и кэш привязок

### 18.1. Где на самом деле тратится время

Наивный рендерер тратит на кадр:

```
на каждый вызов отрисовки:
    выделить дескрипторный набор       ← дорого
    записать в него привязки           ← дорого
    привязать набор                    ← дёшево
    записать команду отрисовки         ← дёшево
```

Именно так у нас и было:

```cpp
// Свежий набор на каждый вызов отрисовки.
VkDescriptorSet descriptorSet = allocate(layout);
vkUpdateDescriptorSets(logicalDevice, writes.size(), writes.data(), 0, nullptr);
vkCmdBindDescriptorSets(cmd, …);
```

Комментарий рядом честно объяснял почему: сторонний код — бэкенд ImGui — привязывает **свои**
наборы между нашими отрисовками, поэтому кэшировать саму привязку нельзя.

Но это не значит, что нельзя кэшировать **набор**.

### 18.2. Ключевое наблюдение

Большинство отрисовок в кадре привязывают одни и те же ресурсы. Отличаются они параметрами:
матрицей, индексом материала, цветом. Если параметры вынести из буферов, то **набор привязок у
множества отрисовок становится идентичным**, и его можно переиспользовать.

Отсюда две меры, работающие в паре:

1. **push-константы** — параметры уезжают из буферов прямо в поток команд;
2. **кэш дескрипторных наборов** — одинаковые привязки перестают перевыделяться.

По отдельности каждая даёт меньше, чем вместе.

### 18.3. Push-константы

Самый дешёвый способ передать данные, свои для каждой отрисовки. Ничего не выделяется, ничего
не привязывается — байты едут внутри самого командного буфера.

Гарантированный объём — **128 байт**. Больше работает на большинстве десктопного железа, но
непереносимо, поэтому абстракция обещает только гарантированное:

```cpp
inline constexpr size_t kMaxPushConstantBytes = 128;
```

Диапазон объявляется **всегда**, на любом пайплайне:

```cpp
VkPushConstantRange pushConstantRange{};
pushConstantRange.stageFlags = VK_SHADER_STAGE_VERTEX_BIT | VK_SHADER_STAGE_FRAGMENT_BIT;
pushConstantRange.offset = 0;
pushConstantRange.size = static_cast<uint32_t>(kMaxPushConstantBytes);
```

Шейдер, который их не использует, ничего не теряет, зато `setPushConstants()` работает с любым
пайплайном без проверок на стороне вызывающего.

### 18.4. Единственное место, где шейдеры расходятся

В Metal push-констант **нет**. Эквивалент — `setVertexBytes:`/`setFragmentBytes:`: малые данные
копируются прямо в командный буфер, но адресуются как буфер. Значит, нужен зарезервированный
слот:

```cpp
inline constexpr uint32_t kPushConstantBufferSlot = 8;   // сразу за диапазоном uniform-слотов
```

Из-за этого объявление в шейдерах отличается:

```glsl
// GLSL
layout(push_constant) uniform OverlayConstants { … } uniforms;
```

```metal
// MSL
constant OverlayUniforms& uniforms [[buffer(8)]]
```

Вызов из C++ при этом **одинаков**. Это второе (и последнее) расхождение в исходниках шейдеров
за весь курс — первое разобрано в части VIII. Оба задокументированы в обоих файлах, чтобы
следующий читатель не «исправил» их обратно.

Ещё отличие: у Metal нет адресуемого блока, поэтому частичная запись со смещением
невыразима. Смещение, отличное от нуля, честно отвергается — вместо тихого расхождения
поведения.

### 18.5. Кэш дескрипторных наборов

Ключ — хеш от того, что привязано, плюс раскладка набора:

```cpp
uint64_t hashBufferBindings(const std::array<BoundBuffer, kMaxBindingSlots>& bindings,
                            VkDescriptorSetLayout layout) {
    uint64_t hash = kHashSeed;
    hashCombine(hash, reinterpret_cast<uint64_t>(layout));
    for (uint32_t slot = 0; slot < kMaxBindingSlots; ++slot) {
        const BoundBuffer& bound = bindings[slot];
        if (!bound.buffer) continue;
        hashCombine(hash, slot);
        hashCombine(hash, reinterpret_cast<uint64_t>(bound.buffer->buffer()));
        hashCombine(hash, static_cast<uint64_t>(bound.offset));
        hashCombine(hash, static_cast<uint64_t>(bound.buffer->size()));
        hashCombine(hash, static_cast<uint64_t>(bound.descriptorType));
    }
    return hash;
}
```

Раскладка входит в ключ обязательно: два пайплайна с разными раскладками не могут разделять
набор, даже если привязаны те же ресурсы.

### 18.6. Где живёт кэш и когда очищается

Наборы выделяются из пула слота кадра. Пул сбрасывается целиком в начале кадра — и это
**аннулирует все выданные из него наборы**. Значит, кэш обязан жить рядом с пулом и очищаться
вместе с ним:

```cpp
VkCheck(vkResetDescriptorPool(logicalDevice, m_data->descriptorPools[slot], 0), "reset");
// Сброс пула аннулирует все наборы, выданные из него, — кэш обязан уйти следом.
m_data->descriptorCache.clear();
m_data->descriptorCacheHits = 0;
m_data->descriptorCacheRequests = 0;
```

Это ровно тот же принцип, что и с фреймбуферами в части VI: **кэш живёт там, где живёт то, что
его инвалидирует.**

### 18.7. Что кэшируем, а что нет

```cpp
// Привязка выполняется каждую отрисовку даже при попадании в кэш: сторонний код,
// в частности бэкенд ImGui, привязывает свои наборы между нашими. Привязка дёшева;
// кэш убирает выделение и запись.
if (bufferSet) {
    vkCmdBindDescriptorSets(cmd, VK_PIPELINE_BIND_POINT_GRAPHICS, pipelineLayout,
                            kBufferDescriptorSet, 1, &bufferSet, 0, nullptr);
}
```

Важно понимать разделение: убираем дорогое (выделение и запись), оставляем дешёвое (привязку).
Попытка сэкономить и на привязке сломалась бы об ImGui.

### 18.8. Измерение

Кэш без измерения — вера, а не инженерия. Добавляем счётчики и меряем на 20 отрисовках,
отличающихся **только** push-константами:

```
38/44 descriptor set requests served from cache
```

86% попаданий. Шесть промахов — три действительно разных набора привязок в кадре (по два
набора каждый). Двадцать отрисовок оверлея не выделяют **ни одного** дополнительного набора;
до изменения их было бы сорок.

**Честная оговорка, которую стоит проговорить в видео:** в немодифицированном демо
статистика — 0 из 6. Три отрисовки, три разных набора привязок, переиспользовать нечего. Кэш
окупается с ростом числа отрисовок — то есть ровно тогда, когда он нужен. Показывать только
выгодный замер было бы нечестно.

## Выпуск 19. Чтение с GPU и непрямая отрисовка

### 19.1. Чтение обратно: зачем

Три применения, каждое из которых иначе недоступно:

* **скриншот** — сохранить кадр в файл;
* **выбор объекта мышью** — отрисовать идентификаторы и прочитать пиксель под курсором;
* **тесты** — сравнить отрисованное с эталоном, то есть проверять рендерер автоматически.

Последнее важнее, чем кажется: без чтения обратно любая проверка сводится к «посмотрел
глазами».

### 19.2. Реализация

Обратная операция к загрузке: перевести в состояние источника, скопировать в промежуточный
буфер, вернуть состояние, скопировать на CPU.

```cpp
void VulkanDevice::readbackFromImage(…) {
    // Всё отправленное должно завершиться, прежде чем результат можно читать.
    VkCheck(vkDeviceWaitIdle(m_data->device), "vkDeviceWaitIdle");

    ensureStagingCapacity(size);
    VkCommandBuffer cmd = beginTransferCommands();

    transitionLevels(cmd, image, mipLevel, 1, currentLayout,
                     VK_IMAGE_LAYOUT_TRANSFER_SRC_OPTIMAL, …);
    vkCmdCopyImageToBuffer(cmd, image, VK_IMAGE_LAYOUT_TRANSFER_SRC_OPTIMAL,
                           m_data->stagingBuffer, 1, &region);
    // Возвращаем изображение туда, где оно было: чтение прозрачно для цикла кадра.
    transitionLevels(cmd, image, mipLevel, 1, VK_IMAGE_LAYOUT_TRANSFER_SRC_OPTIMAL,
                     currentLayout, …);

    endTransferCommands();
    std::memcpy(destination, m_data->stagingAllocation.mapped, size);
}
```

Две детали. Первая: **возврат состояния** — после чтения изображение должно остаться таким,
каким было, иначе следующий кадр упрётся в неожиданное состояние. Вторая: ожидание простоя
делает операцию тяжёлой намеренно.

Для буфера читаем из **актуального** региона, а не вслепую из нулевого:

```cpp
const VkDeviceSize sourceOffset = m_data->regionStride * m_data->latestRegion + offset;
```

### 19.3. Скриншот

Формат BMP выбран не случайно: порядок байтов у него уже BGRA — как у наших целей, — поэтому
перестановка каналов не нужна. Отрицательная высота в заголовке означает «строки сверху вниз»,
что совпадает с порядком, в котором отдаёт GPU.

Проверка арифметикой: файл вышел 3 686 454 байта = 54 (заголовок) + 1280 × 720 × 4. Сходится.

### 19.4. Непрямая отрисовка: в чём смысл

Обычная отрисовка: CPU сообщает, сколько вершин и экземпляров рисовать. Непрямая: параметры
лежат **в буфере**, и GPU читает их сам.

Зачем это нужно:

* список отрисовок готовится один раз и переиспользуется;
* в перспективе его заполняет вычислительный шейдер — отсечение по видимости целиком на GPU,
  без возврата данных процессору.

### 19.5. Приятная находка

Структуры аргументов у двух API **побайтово совпадают**:

```
Vulkan VkDrawIndexedIndirectCommand      Metal MTLDrawIndexedPrimitivesIndirectArguments
    uint32_t indexCount;                     uint32_t indexCount;
    uint32_t instanceCount;                  uint32_t instanceCount;
    uint32_t firstIndex;                     uint32_t indexStart;
    int32_t  vertexOffset;                   int32_t  baseVertex;
    uint32_t firstInstance;                  uint32_t baseInstance;
```

Поэтому одна структура пишется в буфер напрямую, без перевода:

```cpp
struct DrawIndexedIndirectCommand {
    uint32_t indexCount = 0;
    uint32_t instanceCount = 0;
    uint32_t firstIndex = 0;
    int32_t vertexOffset = 0;
    uint32_t firstInstance = 0;
};
```

Редкий случай полного согласия. Стоит отметить в видео: обычно приходится переводить, здесь —
нет.

### 19.6. Где они расходятся

Vulkan может выдать много отрисовок **за один вызов**, если включена соответствующая
возможность. Metal всегда выполняет ровно одну команду за вызов.

```cpp
if (m_data->device->supportsMultiDrawIndirect()) {
    vkCmdDrawIndexedIndirect(cmd, arguments->buffer(), base, drawCount, effectiveStride);
} else {
    // Без возможности drawCount обязан быть 1. Отрисовки те же, отличается только
    // количество записанных команд.
    for (uint32_t i = 0; i < drawCount; ++i) {
        vkCmdDrawIndexedIndirect(cmd, arguments->buffer(),
                                 base + static_cast<VkDeviceSize>(i) * effectiveStride,
                                 1, effectiveStride);
    }
}
```

Metal делает то же самое циклом всегда. Результат одинаков, отличается нагрузка на CPU — и
это честно написано в документации метода.

### 19.7. Новый тип буфера

```cpp
case BufferType::Indirect:
    // Ещё и storage: вычислительный шейдер сможет позже заполнять список прямо на месте,
    // без пересоздания буфера.
    return VK_BUFFER_USAGE_INDIRECT_BUFFER_BIT | VK_BUFFER_USAGE_STORAGE_BUFFER_BIT;
```

Дополнительный флаг стоит ноль и оставляет дверь открытой.

### 19.8. Данные экземпляров

Непрямая отрисовка выдаёт много экземпляров из одной команды. Значит, всё, что различается
между экземплярами, **обязано лежать в буфере**: CPU не получает шанса подменить push-константы
между ними.

```glsl
layout(std140, set = 0, binding = 1) uniform InstanceData {
    vec4 offsets[9];
} instances;

void main() {
    vec3 offset = instances.offsets[gl_InstanceIndex].xyz;
    gl_Position = constants.modelViewProjection * vec4(position + offset, 1.0);
}
```

Массив `vec4` в `std140` имеет естественный шаг 16 байт — здесь ловушки выравнивания нет.

### 19.9. Проверка сравнением

Как убедиться, что непрямая отрисовка действительно работает, а не «вроде рисует»? Отрисовать
одну и ту же сцену обоими способами и сравнить пиксели:

```
direct vs indirect: 0 of 3686400 bytes differ -> IDENTICAL
```

Побайтовое совпадение на полной цели 1280×720. Это и есть доказательство.

### 19.10. Урок: стенд тоже может быть неисправен

Первая версия этой проверки выдала стену ошибок валидации:

```
vkAcquireNextImageKHR(): Semaphore must not be currently signaled.
vkAcquireNextImageKHR(): Application has already previously acquired 2 images…
vkDestroyDevice(): … has not been destroyed.
```

Выглядит как поломка библиотеки. На деле — ошибка **стенда**: он делал `continue` после
отправки, пропуская показ. Изображения забирались и не показывались, пара «забрать/показать»
рассыпалась, дальше эффект нарастал лавиной.

Исправление — выполнять чтение после показа и отправки, как это уже делал код скриншота.

**Методический вывод, который стоит отдельного эпизода:** прежде чем чинить библиотеку по
следам ошибок валидации, убедитесь, что тест сам по себе корректен. Ошибочный стенд выглядит
точно так же, как настоящий баг, и может увести на полдня.
