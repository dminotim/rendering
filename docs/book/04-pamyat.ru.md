# Часть IV. Память

**Выпуски 10–11.** Всё, что мы создавали до сих пор, лежало в памяти, видимой процессору —
самом медленном для GPU варианте. Разберёмся, какая память бывает, научимся класть данные в
видеопамять, измерять её расход и не упереться в лимит драйвера на число выделений.

---

## Выпуск 10. Промежуточные буферы и видеопамять

### 10.1. Какая память бывает

У дискретной видеокарты своя память — VRAM. Она быстрая для GPU и **не адресуется
процессором**: записать в неё напрямую нельзя.

Есть и память, видимая процессору. GPU читает её через системную шину — заметно медленнее.

Свойства памяти описываются флагами:

| Свойство | Что значит |
|---|---|
| `DEVICE_LOCAL` | Быстрая для GPU. На дискретной карте — VRAM |
| `HOST_VISIBLE` | Процессор может отобразить её в своё адресное пространство |
| `HOST_COHERENT` | Записи процессора видны GPU без явного сброса кэша |

Ключевое: на дискретной карте `DEVICE_LOCAL` обычно **не** `HOST_VISIBLE`. На встроенной
графике — почти всегда обе сразу, потому что память физически одна.

### 10.2. Как выбирать, не заставляя приложение думать

Приложение уже сообщает намерение через `BufferUsage`. Свяжем намерение с размещением:

```cpp
bool wantsDeviceLocal(BufferUsage usage) {
    // Только Static окупает копирование: пишется один раз, читается тысячи.
    // Dynamic и Stream переписываются слишком часто, чтобы это себя оправдало.
    return usage == BufferUsage::Static;
}
```

Логика экономическая: разовая стоимость копирования делится на все последующие чтения. Для
данных, переписываемых каждый кадр, делить не на что.

### 10.3. Выбор с запасным вариантом

Просить `DEVICE_LOCAL`, соглашаться на `HOST_VISIBLE`:

```cpp
uint32_t VulkanDevice::selectMemoryType(uint32_t typeBits,
                                        VkMemoryPropertyFlags preferred,
                                        VkMemoryPropertyFlags required,
                                        VkMemoryPropertyFlags& outFlags) const {
    for (VkMemoryPropertyFlags wanted : { preferred, required }) {
        for (uint32_t i = 0; i < memory.memoryTypeCount; ++i) {
            const bool allowed = (typeBits & (1u << i)) != 0;
            const VkMemoryPropertyFlags flags = memory.memoryTypes[i].propertyFlags;
            if (allowed && (flags & wanted) == wanted) {
                outFlags = flags;
                return i;
            }
        }
    }
    throw std::runtime_error("нет подходящего типа памяти");
}
```

Возврат фактических флагов через `outFlags` — не мелочь. Именно по ним выясняется, попали мы в
видеопамять или нет, и **можно ли отобразить** полученную память.

### 10.4. Бесплатная оптимизация

Если выбранный тип оказался и `DEVICE_LOCAL`, и `HOST_VISIBLE` — встроенная графика или
включённый Resizable BAR, — то данные можно писать **прямо в видеопамять**, минуя копирование:

```cpp
m_data->location = (chosenFlags & VK_MEMORY_PROPERTY_DEVICE_LOCAL_BIT)
    ? MemoryLocation::DeviceLocal
    : MemoryLocation::HostVisible;

// Отображаем всегда, когда память это позволяет — даже если она видеопамять.
if (chosenFlags & VK_MEMORY_PROPERTY_HOST_VISIBLE_BIT) {
    m_data->mapped = /* отображение */;
}
```

Проверка идёт **по фактическим флагам**, а не по типу устройства. Это и есть «где возможно» в
формулировке задачи: решение принимается для каждого выделения по тому, что сообщил драйвер.

### 10.5. Промежуточный буфер

Данные в видеопамять едут так: пишем в буфер, видимый процессору → GPU копирует его в
видеопамять.

Устройство держит **один** такой буфер и растит по мере надобности:

```cpp
void VulkanDevice::ensureStagingCapacity(VkDeviceSize size) {
    if (size <= m_data->stagingCapacity) return;
    // пересоздать больше
}
```

Загрузки редки, а их размеры кучкуются — один буфер, доросший до максимума, лучше выделения на
каждый вызов.

Флаги использования — **оба**: он источник для загрузки и приёмник для чтения обратно
(понадобится в части VII).

```cpp
bufferInfo.usage = VK_BUFFER_USAGE_TRANSFER_SRC_BIT | VK_BUFFER_USAGE_TRANSFER_DST_BIT;
```

### 10.6. Контекст передачи

Копирование — это работа GPU, значит нужен командный буфер и очередь. Устройство заводит
собственные:

```cpp
vkGetDeviceQueue(m_data->device, m_data->graphicsFamilyIndex, 0, &m_data->transferQueue);
```

Это **та же самая** очередь, которую получит `VulkanCommandQueues`: одинаковые семейство и
индекс дают один объект. Значит, загрузки упорядочены относительно отрисовки, а не гоняются с
ней. Ограничение — однопоточность, и её нужно задокументировать.

Отправка и ожидание:

```cpp
VkCheck(vkResetFences(m_data->device, 1, &m_data->transferFence), "vkResetFences");
VkCheck(vkQueueSubmit(m_data->transferQueue, 1, &submitInfo, m_data->transferFence), "vkQueueSubmit");
// Ждём: промежуточный буфер должен освободиться, а вызывающий — считать,
// что после возврата данные на месте.
VkCheck(vkWaitForFences(m_data->device, 1, &m_data->transferFence, VK_TRUE, UINT64_MAX), "wait");
```

Ожидание делает загрузку синхронной. Это осознанно: операция должна выглядеть тяжёлой, чтобы её
не звали каждый кадр.

### 10.7. Гонка динамических буферов

Проблема, о которой не пишут в туториалах.

Кадр N+1 пишет константы, пока GPU ещё читает их для кадра N. Одна и та же память. Результат —
мерцание, воспроизводящееся не всегда.

Решение: динамический буфер выделяется как **несколько выровненных областей** в одном буфере,
по одной на слот кадра. Пишем в область текущего слота, привязываем её же.

```cpp
m_data->regionCount = (usage == BufferUsage::Dynamic) ? kFramesInFlight : 1;
m_data->regionStride = alignUp(size, alignment);
```

Выравнивание берётся из ограничений устройства — минимальное для смещения uniform- или
storage-буфера.

Текущий слот кадра хранится на устройстве и обновляется очередью в начале кадра. Небольшая
связанность, зато буферу не нужно знать про очередь.

### 10.8. Ловушка: частичное обновление

Регионы порождают неочевидный баг. Частичная запись трогает **только** переданные байты; в
остальной части этого региона лежит то, что было **два кадра назад**.

Последовательность из четырёх частичных записей в буфер `{1,2,3,4}`:

```
без исправления   region1 = {1, 20, 3, 40}   ← записи в другой регион потеряны
с исправлением    region1 = {10, 20, 30, 40}
```

Исправление: перед частичной записью скопировать в текущий регион **весь** самый свежий, и уже
поверх положить новые байты.

```cpp
const bool coversWholeBuffer = (offset == 0 && dataSize == m_data->size);
if (m_data->regionCount > 1 && !coversWholeBuffer && region != m_data->latestRegion) {
    std::memcpy(base + m_data->regionStride * region,
                base + m_data->regionStride * m_data->latestRegion,
                m_data->size);
}
std::memcpy(base + destinationOffset, data, dataSize);
m_data->latestRegion = region;
```

Две проверки убирают лишнюю работу: запись целиком копировать неоткуда, а повторная запись в
тот же регион уже актуальна. Обычный случай — перезапись всей структуры констант — не платит
ничего.

### 10.9. Бюджет видеопамяти

Расширение `VK_EXT_memory_budget` даёт настоящие цифры с учётом других процессов. Оно
необязательное, поэтому включается «если есть»:

```cpp
const std::vector<const char*> optionalDeviceExtensions = {
    VK_EXT_MEMORY_BUDGET_EXTENSION_NAME
};
```

Без него честно сообщаем размер кучи и ставим `preciseBudget = false` — вместо выдумывания
цифры.

### 10.10. Проверка вместимости

Встраивается в создание ресурсов:

* **буфер**, который не помещается, размещается в системной памяти. Рисовать медленнее лучше,
  чем не рисовать;
* **изображение** — наоборот: текстура вне видеопамяти бессмысленна, поэтому создание падает с
  сообщением, сколько именно не хватило.

Разная политика для разных ресурсов — осознанное решение, и его стоит проговорить.

### 10.11. Проверка

Диагностика при запуске:

```
total=8256 MiB budget=7486 MiB used=45 MiB precise=1 unified=0
vertex=VRAM index=VRAM uniform=host sceneTarget=VRAM
```

Статические буферы в видеопамяти, динамические — в системной. Ровно как задумано.

**Важно проверить и запасной путь.** Он иначе остаётся мёртвым кодом. Временно форсируем
условие «не помещается» — буферы должны честно оказаться в системной памяти, а картинка не
измениться.

## Выпуск 11. Суб-аллокатор

### 11.1. Почему одного выделения на ресурс недостаточно

До сих пор каждый ресурс запрашивал память отдельно. Это работает — и упирается в жёсткую
стену.

Драйверы ограничивают `maxMemoryAllocationCount`. Типичное значение — **4096**. Это не
рекомендация: 4097-е выделение не удастся. Плюс каждое обращение медленное.

Сцена с тысячами объектов упрётся в потолок. Решение — выделять **крупные блоки** и раздавать
куски внутри них. Именно это делает известная библиотека AMD VMA; мы напишем компактный
аналог, чтобы понять принцип.

### 11.2. Структура

```cpp
struct VulkanAllocation {
    VkDeviceMemory memory;
    VkDeviceSize offset;     // теперь не ноль!
    VkDeviceSize size;
    void* mapped;            // отображение блока, сдвинутое на offset
    VkMemoryPropertyFlags properties;
    uint32_t blockIndex;
};
```

Главное изменение: привязка ресурса теперь использует **и память, и смещение**.

### 11.3. Стратегия

```
Блоки по 64 МиБ, пул на каждый тип памяти
Внутри блока — список свободных диапазонов, отсортированный по смещению
Выделение — первый подходящий
Освобождение — вставка обратно со склейкой соседей
Запрос больше половины блока — собственное выделение
```

Склейка обязательна. Без неё создание и уничтожение ресурсов разного размера постепенно
дробит блок так, что крупный запрос не помещается при формально свободной памяти.

```cpp
FreeRange returned{ allocation.offset, allocation.size };
auto position = std::lower_bound(block.freeRanges.begin(), block.freeRanges.end(), returned,
    [](const FreeRange& a, const FreeRange& b) { return a.offset < b.offset; });
position = block.freeRanges.insert(position, returned);

// склеить со следующим, затем с предыдущим
if (position + 1 != block.freeRanges.end()) {
    auto next = position + 1;
    if (position->offset + position->size == next->offset) {
        position->size += next->size;
        block.freeRanges.erase(next);
    }
}
if (position != block.freeRanges.begin()) {
    auto previous = position - 1;
    if (previous->offset + previous->size == position->offset) {
        previous->size += position->size;
        block.freeRanges.erase(position);
    }
}
```

### 11.4. Ловушка: bufferImageGranularity

Тонкость, о которой легко не узнать до странного повреждения данных.

Буферы имеют **линейную** раскладку, изображения — **оптимальную** (внутренний формат
драйвера). Если они соседствуют в одной памяти, между ними нужен отступ, задаваемый
`bufferImageGranularity`.

Отслеживать это на каждом диапазоне — сложно и легко ошибиться. Радикально проще: **разделить
блоки по типу ресурса**.

```cpp
enum class ResourceKind { Linear, Optimal };
```

Буферы берут память из линейных блоков, изображения — из оптимальных. Они физически не могут
оказаться рядом, и проблема исчезает целиком. Цена — немного лишней памяти.

Это хороший пример инженерного решения: вместо аккуратной реализации сложного правила —
устранение ситуации, в которой оно применяется.

### 11.5. Отображение — один раз на блок

Блок видимой процессору памяти отображается **при создании** и остаётся отображённым. Выделение
получает готовый указатель со смещением:

```cpp
allocation.mapped = block.mapped
    ? static_cast<char*>(block.mapped) + alignedOffset
    : nullptr;
```

Ресурсы больше не отображают память сами — и, что важно, не отменяют отображение в
деструкторах. Оно принадлежит блоку.

### 11.6. Освобождение пустых блоков

Блок, из которого ушло последнее выделение, возвращается системе — иначе долго живущее
приложение держит пулы, которыми перестало пользоваться. Слот в векторе при этом сохраняется,
чтобы уже выданные индексы блоков оставались валидными.

### 11.7. Проверка — самая наглядная в курсе

Создаём 400 ресурсов и смотрим на число системных выделений:

```
baseline:                  3 native allocations, 192.0 MiB reserved
with 400 live resources:   3 native allocations, 192.0 MiB reserved
after releasing them:      3 native allocations, 192.0 MiB reserved
```

Ноль дополнительных выделений на 400 ресурсов. Без аллокатора их было бы 400 — при лимите 4096.

Эта цифра — лучший кадр для превью выпуска.
