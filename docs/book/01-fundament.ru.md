# Часть I. Фундамент

**Выпуски 1–3.** К концу части у нас будет окно, которое открывается, корректно меняет размер,
закрывается без единой жалобы слоёв валидации — и не рисует ничего. Это правильный первый
результат: вся сложность современных графических API находится не в отрисовке, а в подготовке
и синхронизации.

---

## Выпуск 1. Зачем обёртка и как её проектировать

### 1.1. Постановка задачи

Мы пишем слой, который позволяет написать цикл кадра **один раз** и получить одинаковую
картинку на Windows (через Vulkan) и на macOS (через Metal).

Соблазн начать с «напишем классы Device, Buffer, Texture» велик, и это ошибка. Начинать нужно
с вопроса: **что именно у этих двух API различается настолько, что требует абстракции?**

Разберём честно.

| Область | Vulkan | Metal | Насколько расходятся |
|---|---|---|---|
| Создание устройства | Явный выбор физического устройства, семейств очередей, расширений | Одна строка | Сильно |
| Показ на экран | Свопчейн, семафоры, забор изображений | `CAMetalLayer`, `nextDrawable` | Сильно |
| Синхронизация | Всё вручную: заборы, семафоры, барьеры | В основном автоматически | **Максимально** |
| Командные буферы | Выделяются из пула, переиспользуются | Создаются каждый кадр, драйвер утилизирует | Сильно |
| Проход рендеринга | `VkRenderPass` + `VkFramebuffer` — объекты | Дескриптор-значение, создаётся каждый кадр | Средне |
| Пайплайн | Всё в одном неизменяемом объекте | Разнесено по трём местам | Средне |
| Привязка ресурсов | Дескрипторные наборы | Прямые вызовы на энкодере | Средне |
| Шейдеры | SPIR-V, компилируется заранее | MSL, компилируется в рантайме | Средне |
| Память | Выделяем и привязываем вручную | Драйвер сам | Сильно |

Вывод, который определит всю архитектуру: **Vulkan требует явного описания почти всего, что
Metal делает неявно.** Значит, форма API должна быть ближе к Metal — более высокоуровневой, —
а бэкенд Vulkan будет доделывать то, что Metal получает бесплатно.

Обратный подход (форма API в стиле Vulkan) заставил бы приложение управлять сущностями,
которых в Metal просто нет, и Metal-бэкенд превратился бы в эмуляцию.

### 1.2. Как выглядит целевой цикл кадра

Прежде чем писать хоть строчку реализации, напишем на бумаге код, который **хотим** получить:

```cpp
auto surface   = helper::createSurface(window, ImageFormat::BGRA8_UNORM);
auto device    = helper::createDefaultDevice(surface);
auto queue     = helper::createCommandQueue(device);
auto swapChain = helper::createSwapChain(device, queue, surface, w, h);

while (!shouldClose) {
    auto target = swapChain->acquireNextImage();
    if (!target) continue;

    auto pass = helper::createRenderPassDescriptor();
    pass->setColorAttachment(0, target, true, clearColor);

    auto cmd = helper::createCommandBuffer(queue);
    cmd->beginRenderPass(pass);
        cmd->setRenderPipeline(pipeline);
        cmd->drawIndexed(...);
    cmd->endRenderPass();
    cmd->present(target);
    cmd->commit();
}
```

Это техника, которую стоит перенести в любой проект: **проектирование от места использования**.
Всё, что появится дальше, должно обслуживать вот этот текст.

### 1.3. Структура проекта

```
render_pipeline/     чистые абстрактные интерфейсы, без единого #include платформы
render_vulkan/       реализация Vulkan
render_metal/        реализация Metal
```

Правило, которое нужно защищать всю разработку: в `render_pipeline/` **не должно быть ни одного
упоминания Vulkan или Metal**. Ни в заголовках, ни в комментариях. Как только оно появляется,
абстракция начинает протекать, и через месяц у вас не обёртка, а Vulkan с чужими именами.

Приём, который это обеспечивает — **PIMPL**. В заголовке объявляется только указатель на
непрозрачную структуру:

```cpp
// render_vulkan/VulkanDevice.hpp
namespace dmrender {
    struct VulkanDeviceNativeData;      // объявлена, но не определена

    class VulkanDevice : public Device {
        // ...
    private:
        std::unique_ptr<VulkanDeviceNativeData> m_data;
    };
}
```

Определение уезжает в `.cpp`, где уже можно всё:

```cpp
struct VulkanDeviceNativeData {
    VkPhysicalDevice physicalDevice;
    VkDevice device;
    // ...
};
```

Плюс: заголовки бэкенда не тянут за собой `vulkan.h` в весь проект, и время сборки не
взрывается.

### 1.4. Окно и инстанс

GLFW создаёт окно без графического контекста — контекстом займётся графический API:

```cpp
glfwInit();
glfwWindowHint(GLFW_CLIENT_API, GLFW_NO_API);   // важно: не создавать OpenGL-контекст
GLFWwindow* window = glfwCreateWindow(1280, 720, "Renderer", nullptr, nullptr);
```

**Инстанс Vulkan** — точка входа в библиотеку драйвера. Он один на процесс, поэтому оформляем
его синглтоном:

```cpp
class VulkanSingleton {
public:
    static VulkanSingleton& getInstance();
    VkInstance nativeHandle() const;
private:
    VulkanSingleton();
    ~VulkanSingleton();
    VkInstance m_instance = nullptr;
    VkDebugUtilsMessengerEXT m_debugMessenger = nullptr;
};
```

При создании инстанса запрашиваются расширения, нужные для вывода в окно. GLFW знает, какие
именно, для текущей платформы:

```cpp
uint32_t count = 0;
const char** required = glfwGetRequiredInstanceExtensions(&count);
std::vector<const char*> extensions(required, required + count);
```

### 1.5. Слои валидации — включить прямо сейчас

Самое важное решение первого выпуска. Vulkan по умолчанию **не проверяет ничего**: неверный
вызов не вернёт ошибку, он приведёт к порче памяти, которая проявится через двадцать минут в
другом месте.

```cpp
extensions.push_back(VK_EXT_DEBUG_UTILS_EXTENSION_NAME);
createInfo.enabledLayerCount = 1;
createInfo.ppEnabledLayerNames = &"VK_LAYER_KHRONOS_validation";

VkDebugUtilsMessengerCreateInfoEXT debugInfo{};
debugInfo.sType = VK_STRUCTURE_TYPE_DEBUG_UTILS_MESSENGER_CREATE_INFO_EXT;
debugInfo.messageSeverity = VK_DEBUG_UTILS_MESSAGE_SEVERITY_WARNING_BIT_EXT
                          | VK_DEBUG_UTILS_MESSAGE_SEVERITY_ERROR_BIT_EXT;
debugInfo.messageType = VK_DEBUG_UTILS_MESSAGE_TYPE_GENERAL_BIT_EXT
                      | VK_DEBUG_UTILS_MESSAGE_TYPE_VALIDATION_BIT_EXT
                      | VK_DEBUG_UTILS_MESSAGE_TYPE_PERFORMANCE_BIT_EXT;
debugInfo.pfnUserCallback = debugCallback;
createInfo.pNext = &debugInfo;      // ловим ошибки уже при создании инстанса
```

Обратите внимание на `pNext`: цепочка нужна, чтобы ловить ошибки **самого создания инстанса**,
до того как мессенджер существует как объект.

Правило на весь курс: **пустой лог валидации — это результат, который нужно проверять после
каждого изменения.** Не «вроде работает», а «слои молчат».

### 1.6. Проверка

Окно открывается и закрывается, в логе — ни строчки. Если в логе что-то есть, дальше идти
бессмысленно: последующие ошибки будут наслаиваться.

## Выпуск 2. Устройство, поверхность и очереди

### 2.1. Порядок, который неочевиден

Интуиция подсказывает: сначала устройство, потом поверхность. **Это неверно.**

Физическое устройство выбирается **с учётом поверхности**, потому что не всякий GPU в системе
умеет выводить изображение в конкретное окно. Классический случай — ноутбук с дискретной и
встроенной картой, где к экрану подключена только одна.

Правильный порядок: **поверхность → устройство**.

```cpp
auto surface = helper::createSurface(window, ImageFormat::BGRA8_UNORM);
auto device  = helper::createDefaultDevice(surface);   // surface нужен для выбора
```

Это тот случай, когда порядок вызовов — часть контракта API, и его стоит задокументировать.

### 2.2. Поверхность

В Vulkan создание отдано GLFW, потому что оно платформозависимо:

```cpp
VkSurfaceKHR surface;
glfwCreateWindowSurface(VulkanSingleton::getInstance().nativeHandle(), window, nullptr, &surface);
```

В Metal — это `NSView` с включённым слоем:

```objc
m_nswin = glfwGetCocoaWindow(window);
m_nsview = m_nswin.contentView;
m_nsview.wantsLayer = YES;
```

Совершенно разные сущности за одним интерфейсом — ровно то, ради чего абстракция и нужна.

### 2.3. Выбор физического устройства

Устройство подходит, если выполнены **три** условия:

```cpp
bool isDeviceSuitable(VkPhysicalDevice dev, const std::shared_ptr<Surface>& surface) {
    QueueFamilyIndices indices = findQueueFamilies(dev, surface);
    bool extensionsOk = checkDeviceExtensionSupport(dev);       // умеет свопчейн
    bool swapChainOk = false;
    if (extensionsOk) {
        auto support = querySwapChainSupport(dev, surface);
        swapChainOk = !support.formats.empty() && !support.presentModes.empty();
    }
    return indices.isComplete() && extensionsOk && swapChainOk;
}
```

### 2.4. Семейства очередей

GPU принимает работу через очереди, и очереди сгруппированы в семейства по умениям. Нам нужны
два умения: рисовать и показывать.

```cpp
struct QueueFamilyIndices {
    std::optional<uint32_t> graphicsFamily;
    std::optional<uint32_t> presentFamily;
    bool isComplete() const { return graphicsFamily && presentFamily; }
};
```

Ключевой момент: **это могут быть разные семейства**. Обычно совпадают, но полагаться на это
нельзя — при их различии свопчейн создаётся в режиме совместного доступа.

`std::optional` здесь не украшение: индекс 0 — валидное семейство, поэтому «не найдено»
нельзя закодировать нулём.

### 2.5. Логическое устройство и возможности

```cpp
VkPhysicalDeviceFeatures supported{};
vkGetPhysicalDeviceFeatures(physicalDevice, &supported);

VkPhysicalDeviceFeatures enabled{};
enabled.textureCompressionBC       = supported.textureCompressionBC;
enabled.multiDrawIndirect          = supported.multiDrawIndirect;
enabled.drawIndirectFirstInstance  = supported.drawIndirectFirstInstance;
```

Правило Vulkan, которое ловит новичков: **возможности выключены по умолчанию**. Не запросили —
использовать нельзя, и это не деградация, а ошибка. Но и запрашивать вслепую нельзя:
неподдерживаемая возможность приводит к отказу в создании устройства.

Отсюда шаблон «спросить, потом запросить поддерживаемое подмножество». Мы вернёмся к нему в
частях про сжатие текстур и непрямую отрисовку.

### 2.6. Очередь и то, чем она владеет

В Metal очередь — одна строка. В Vulkan она становится владельцем всего, что переиспользуется
между кадрами, и это архитектурно важно:

| Ресурс | Почему на кадр |
|---|---|
| Командный буфер | Нельзя перезаписывать, пока GPU его исполняет |
| Забор (fence) | Сообщает CPU, что слот освободился |
| Пул дескрипторов | Сбрасывается целиком, а не по одному набору |

Значит, очередь хранит по **две** копии каждого (два кадра в полёте) и циклически их
переключает. Приложение об этом не знает.

### 2.7. Проверка

В лог выводится имя видеокарты, индексы семейств очередей и включённые возможности. Слои
молчат.

## Выпуск 3. Свопчейн и синхронизация

Самый концептуально тяжёлый выпуск курса. Здесь появляется вся синхронизация — и здесь же
рождается архитектурное решение о разделении владения.

### 3.1. Что такое свопчейн

Набор изображений, циклически показываемых на экране. Пока одно на экране, в другое рисуем.
Без этого был бы виден процесс отрисовки.

```cpp
VkSwapchainCreateInfoKHR createInfo{};
createInfo.surface          = surface;
createInfo.minImageCount    = capabilities.minImageCount + 1;
createInfo.imageFormat      = surfaceFormat.format;
createInfo.imageExtent      = extent;
createInfo.imageArrayLayers = 1;
createInfo.imageUsage       = VK_IMAGE_USAGE_COLOR_ATTACHMENT_BIT;
createInfo.presentMode      = VK_PRESENT_MODE_FIFO_KHR;
createInfo.clipped          = VK_TRUE;
```

**`minImageCount + 1`** — не суеверие. При минимуме драйвер может заставить нас ждать
освобождения изображения; одно лишнее даёт запас.

**Формат** выбираем тот, что запросило приложение. Здесь прячется ловушка, стоившая нам
реального бага: почти все примеры выбирают sRGB-вариант. Metal при этом настроен на линейный
формат, и **один и тот же шейдер даёт разную картинку**. Правило: честно отдавать запрошенное.

**`FIFO`** — вертикальная синхронизация, доступна всегда. Совпадает с поведением Metal по
умолчанию, что важно для одинаковости.

### 3.2. Три вида ожидания

Здесь три разных примитива, и путать их — источник самых неприятных багов.

| Примитив | Кто кого ждёт | Зачем здесь |
|---|---|---|
| **Забор (fence)** | CPU ждёт GPU | Узнать, что слот кадра свободен |
| **Семафор** | GPU ждёт GPU | Упорядочить операции внутри GPU |
| **Барьер** | Внутри командного буфера | Видимость записей |

Работающая схема кадра:

```
1. CPU ждёт забор слота          — предыдущий кадр в этом слоте завершён
2. Забирает изображение          — GPU просигналит семафор «изображение готово»
3. Записывает команды
4. Отправляет:
      ждать   семафор «изображение готово»
      сигналить семафор «отрисовка завершена»
      сигналить забор слота
5. Показ ждёт семафор «отрисовка завершена»
```

### 3.3. Решение об индексации семафоров

Тонкость, которую большинство туториалов делают неправильно.

* Семафор **«изображение готово»** — по **слоту кадра** (их два).
* Семафор **«отрисовка завершена»** — по **индексу изображения** свопчейна (их три и больше).

Почему по-разному? Семафор «отрисовка завершена» ожидается операцией показа. Если
индексировать его по слоту кадра, он может быть переиспользован раньше, чем завершится показ,
который его ждёт. Это даёт плавающие ошибки валидации при изменении размера окна — из тех, что
воспроизводятся раз в двадцать запусков.

### 3.4. Разделение владения

Ключевое архитектурное решение части.

```
CommandQueue владеет:  командные буферы, заборы, пулы дескрипторов   (по слоту кадра)
SwapChain   владеет:   изображения, семафоры, отслеживание занятости (по изображению)
```

Почему забор у очереди, а не у свопчейна? Потому что он охраняет **переиспользование
командного буфера и пула**, а не изображение. Отдать его свопчейну — значит связать две вещи,
которые независимы.

Но тогда `acquireNextImage()` должен попросить очередь открыть кадр:

```cpp
std::shared_ptr<GImage> VulkanSwapChain::acquireNextImage() {
    m_queue->beginFrame();     // ждём забор, сбрасываем буфер и пул

    VkResult result = vkAcquireNextImageKHR(device, swapChain, UINT64_MAX,
                                            imageAvailable, VK_NULL_HANDLE, &imageIndex);
    if (result == VK_ERROR_OUT_OF_DATE_KHR) {
        recreate(width, height);
        return nullptr;        // приложение пропустит кадр
    }
    // ...
}
```

Порядок принципиален: **сначала ждём забор, потом забираем изображение**. Иначе можно
запросить изображение с семафором, который ещё используется.

### 3.5. Ловушка: когда сбрасывать забор

Ошибка, которая приводит к вечному зависанию.

Наивно: ждём забор и тут же сбрасываем. Но если получение изображения **не удалось** (окно
меняет размер) и мы вышли из кадра — забор сброшен, а отправки не было. На следующем кадре ждём
забор, который никто не просигналит. Зависание навсегда.

Решение: **сбрасывать забор непосредственно перед отправкой**, а не после ожидания.

```cpp
void beginFrame() {
    vkWaitForFences(device, 1, &fence[slot], VK_TRUE, UINT64_MAX);
    // НЕ сбрасываем
    vkResetCommandBuffer(cmd[slot], 0);
    vkResetDescriptorPool(device, pool[slot], 0);
}

void commit() {
    vkResetFences(device, 1, &fence[slot]);    // вот здесь
    vkQueueSubmit(queue, 1, &submitInfo, fence[slot]);
}
```

Побочный плюс: `beginFrame()` становится идемпотентным — вызвать его дважды безопасно.

### 3.6. Ловушка: пересоздание после показа

Если показ вернул «устарело», пересоздавать свопчейн **немедленно нельзя**: только что
отправленный кадр всё ещё ссылается на его изображения.

```cpp
if (result == VK_ERROR_OUT_OF_DATE_KHR || result == VK_SUBOPTIMAL_KHR) {
    m_needsRecreate = true;      // только флаг
}
```

Работу делает следующий `acquireNextImage()` — после ожидания забора, когда безопасно.

### 3.7. Изображение свернуто

Свёрнутое окно даёт нулевой размер, а свопчейн нулевого размера создать нельзя. Ждём:

```cpp
int w = 0, h = 0;
glfwGetFramebufferSize(window, &w, &h);
while (w == 0 || h == 0) {
    glfwGetFramebufferSize(window, &w, &h);
    glfwWaitEvents();
}
```

### 3.8. Проверка

Окно открывается, показывает чёрный экран, меняет размер десяток раз, сворачивается и
разворачивается — слои молчат. Это уже нетривиальный результат: большинство самодельных
рендереров валятся именно на ресайзе.
