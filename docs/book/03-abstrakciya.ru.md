# Часть III. Абстракция и второй бэкенд

**Выпуски 7–9.** Самая «архитектурная» часть курса. Код уже работает, но он написан на Vulkan
напрямую. Задача — вытащить интерфейсы так, чтобы второй бэкенд встал на место без единого
изменения в цикле кадра, и доказать это, реализовав его.

---

## Выпуск 7. Проектирование интерфейсов

### 7.1. Как понять, что абстракция правильная

Плохая абстракция определяется по двум признакам:

1. в интерфейсе появляются понятия, существующие только в одном бэкенде;
2. код приложения содержит `#ifdef`.

Проверка, которую стоит применять к каждому методу: **«что этот вызов означает на второй
платформе?»** Если ответа нет — метод спроектирован неверно.

Пример из нашей разработки. Интерфейс командного буфера содержит:

```cpp
virtual void* nativeEncoder() = 0;
```

В Metal энкодер — отдельный объект, живущий между `beginRenderPass` и `endRenderPass`, и он
нужен ImGui. В Vulkan отдельного энкодера **нет вовсе**. Абстракция протекла?

Не совсем: контракт можно сформулировать нейтрально — «низкоуровневая ручка, действительная
только внутри прохода». Vulkan возвращает тот же командный буфер внутри прохода и `nullptr`
снаружи. Смысл сохранён, обе платформы честно его реализуют.

### 7.2. Единственное место с ветвлением

Правило, которое защищаем всю разработку: **весь выбор бэкенда живёт в одном файле**.

```cpp
// render_pipeline/RenderHelper.cpp
std::shared_ptr<Device> createDefaultDevice(const std::shared_ptr<Surface>& surface) {
    #if defined(__APPLE__)
        return MetalDevice::createDefaultDevice(surface);
    #else
        return VulkanDevice::createDefaultDevice(surface);
    #endif
}
```

Это же место — контрольная точка на код-ревью: если `#ifdef` появился где-то ещё, абстракция
дала течь.

Ловушка, на которой мы реально споткнулись: заголовки бэкенда были подключены **вне** блока
условной компиляции:

```cpp
#if defined(__APPLE__)
    #include "MetalDevice.hpp"
#endif
#include <render_vulkan/VulkanDevice.hpp>   // ← сборка на macOS сломана
```

Компилятор на Windows этого не заметит. Такие вещи ловятся только сборкой на второй платформе —
и это аргумент собирать её регулярно, а не «когда-нибудь».

### 7.3. Фабрики против конструкторов

Часть объектов создаётся через `Device`, часть — через `helper::`. Разделение не случайно:

| Через `Device` | Через `helper::` |
|---|---|
| Буферы, изображения, сэмплеры | Поверхность, свопчейн, очередь |
| Всё, чему нужно **только** устройство | Всё, чему нужно что-то ещё |

Свопчейну нужны устройство, очередь и поверхность одновременно — метод устройства выглядел бы
странно. Фабрика в `helper::` честнее.

### 7.4. Собственность и время жизни

Схема, к которой приходим:

```
Приложение держит shared_ptr на: Surface, Device, CommandQueue, SwapChain, ресурсы
Командный буфер держит shared_ptr на очередь   (чтобы та не умерла в середине кадра)
Пайплайн держит shared_ptr на шейдеры          (модули нужны всю его жизнь)
Изображение свопчейна ссылается на свопчейн    (не владея им)
```

Порядок разрушения при выходе из области видимости — обратный порядку объявления: ресурсы,
затем свопчейн, очередь, устройство, поверхность. Это правильный порядок, и он получается сам,
если объявлять в правильном.

**Но есть подвох.** Metal держит ресурс живым, пока его использует хоть один незавершённый
командный буфер. Vulkan — **нет**. Уничтожение буфера, который читает выполняющийся кадр, —
ошибка.

Решение — ожидание простоя устройства в деструкторах ресурсов Vulkan:

```cpp
VulkanBuffer::~VulkanBuffer() {
    VkDevice logicalDevice = m_data->device->logicalDevice();
    // Metal держит ресурс живым до завершения команд. Vulkan — нет.
    vkDeviceWaitIdle(logicalDevice);
    // ...
}
```

Грубо, но при разрушении это допустимо и снимает целый класс ошибок.

### 7.5. Ошибка, которую нашла сборка на macOS

В базовый интерфейс очереди был добавлен чисто виртуальный метод:

```cpp
virtual std::shared_ptr<CommandBuffer> getCommandBuffer() = 0;
```

Реализация появилась только в Vulkan. `MetalCommandQueues` остался абстрактным — **сборка на
Apple была невозможна**, и никто этого не замечал, пока её не запустили.

Урок для курса: **добавление метода в базовый интерфейс — изменение обоих бэкендов**, даже
если сейчас собирается только один.

Попутно всплыла деталь: чтобы очередь могла вернуть командный буфер, ссылающийся на неё саму,
понадобилось `enable_shared_from_this`:

```cpp
class CommandQueue : public std::enable_shared_from_this<CommandQueue> { … };

std::shared_ptr<CommandBuffer> VulkanCommandQueues::getCommandBuffer() {
    return std::make_shared<VulkanCommandBuffer>(shared_from_this());
}
```

Работает только если объект создан через `make_shared` — что все наши фабрики и делают.

## Выпуск 8. Второй бэкенд

### 8.1. Насколько он проще

Порядок величин: Metal-бэкенд примерно **втрое короче** Vulkan-овского при том же наборе
возможностей. Почти вся разница — синхронизация и управление памятью, которые Metal делает сам.

```objc
// Весь Metal-эквивалент цепочки «выделить память, создать буфер, привязать, замапить»
id<MTLBuffer> buffer = [device newBufferWithBytes:data
                                           length:size
                                          options:MTLResourceStorageModeShared];
```

Это полезно показать в видео: не «Metal лучше», а «два API сделали разный выбор в компромиссе
контроль/простота», и обёртка выбирает, какую сторону показывать наружу.

### 8.2. Свопчейн на Metal

```objc
m_layer = [CAMetalLayer layer];
m_layer.device = (id<MTLDevice>)m_device->nativeHandle();
m_layer.pixelFormat = ToMTLPixelFormat(m_surface->getFormat());
content.layer = m_layer;
m_layer.drawableSize = CGSizeMake(m_width, m_height);
```

Получение изображения:

```objc
id<CAMetalDrawable> drawable = [m_layer nextDrawable];
if (!drawable) return nullptr;   // окно свёрнуто
```

Одна строка вместо всей нашей схемы с заборами и семафорами. Ожидание освобождения происходит
внутри `nextDrawable`.

### 8.3. Три места, где формы объектов не совпадают

**Пайплайн разнесён на три части** — разобрано в части II. `MetalPipeline` владеет
`MTLRenderPipelineState` и `MTLDepthStencilState`, помнит состояния растеризатора и применяет
всё в `setRenderPipeline()`.

**Командный буфер владеет собой.** В Metal он создаётся заново каждый кадр и утилизируется
драйвером. В Vulkan это **заимствованный** объект из пула очереди. Отсюда разные деструкторы:
Metal освобождает, Vulkan только закрывает запись.

**Инициализация ImGui.** Metal-бэкенду ImGui нужно только устройство; Vulkan-бэкенду —
очередь, пул дескрипторов, число изображений свопчейна и совместимый проход. Поэтому сигнатура
общая:

```cpp
bool initImgui(const std::shared_ptr<SwapChain>& swapChain);
```

Свопчейн знает всё перечисленное. Metal просто достаёт из него устройство. Это пример
проектирования по **более требовательной** платформе — и потребовало добавить в `SwapChain`
публичные `getDevice()`, `getCommandQueue()`, `getSurface()`.

### 8.4. Порядок вызовов как часть контракта

Из предыдущего пункта следует, что `initImgui` **обязан** вызываться после создания свопчейна.
На Metal порядок безразличен, на Vulkan — нет. Значит, порядок становится частью контракта и
документируется:

```cpp
/**
 * @note Вызывать после создания свопчейна: одному из бэкендов нужны его число изображений
 *       и совместимый проход рендеринга.
 */
bool initImgui(const std::shared_ptr<SwapChain>& swapChain);
```

Общее правило проектирования кроссплатформенных API: **контракт задаётся по самой строгой
платформе**, иначе код, написанный на мягкой, ломается на строгой.

## Выпуск 9. Интеграция ImGui и первый двухплатформенный запуск

### 9.1. Зачем ImGui в курсе

Не ради красоты. Панель — это способ **менять параметры без пересборки**, а значит проверять
гипотезы за секунды. Дальше в курсе почти каждая новая возможность получает переключатель, и
сравнение «включено/выключено» — основной инструмент проверки.

### 9.2. Обвязка

Четыре функции, по одной на этап:

```cpp
bool initImgui(const std::shared_ptr<SwapChain>& swapChain);
bool newFrameImgui(const std::shared_ptr<RenderPassDescriptor>& passDesc);
bool renderInternalImgui(const std::shared_ptr<CommandBuffer>& cmdBuffer);
bool shutdownImgui();
```

`newFrameImgui` принимает дескриптор прохода, потому что Metal-бэкенду ImGui нужно знать формат
цели. Vulkan-бэкенд его игнорирует — но параметр остаётся, чтобы сигнатура была общей.

### 9.3. Ловушка завершения

При первой сборке на macOS всё работало. При запуске с включёнными слоями валидации на Windows
в логе появились четыре ошибки:

```
vkDestroyBuffer(): can't be called on VkBuffer ... that is currently in use
vkFreeDescriptorSets(): ... currently in use
vkDestroyPipeline(): ... currently in use
```

Первая реакция — «ошибка в наших буферах». Неверно: перечисленные объекты принадлежат **ImGui**.
Его функция завершения уничтожает свой пайплайн, буферы геометрии и дескрипторный набор — а
последний отправленный кадр всё ещё выполняется.

```cpp
bool ShutdownImguiVulkan() {
    // Metal держит ресурсы живыми до завершения команд, Vulkan — нет.
    if (g_imguiDevice) {
        vkDeviceWaitIdle(g_imguiDevice);
    }
    ImGui_ImplVulkan_Shutdown();
    // ...
}
```

**Методический вывод для видео:** сообщение валидации называет объект, а не виновника. Прежде
чем чинить свой код, стоит понять, **чей** это объект. Здесь разница между «полдня искать в
своём коде» и «одна строка».

### 9.4. Точка входа

Финальный `main.cpp` после всей работы:

```cpp
#include "FastRenderer.hpp"

int main() {
    try {
        dmrender::run_loop();
    } catch (const std::exception& e) {
        std::cerr << "ERROR: " << e.what() << std::endl;
        return 1;
    }
    return 0;
}
```

Всё, что было платформенным, ушло за интерфейсы.

### 9.5. Проверка — главная в этой части

На Windows и macOS собирается **один и тот же** `FastRenderer.cpp` и даёт одинаковую сетку.
Ни одного `#ifdef` вне `RenderHelper.cpp`.

Это момент, ради которого писались две предыдущие части.
