# dmrender — справочник по API

Полное описание обобщённого графического API библиотеки: что он умеет, как этим пользоваться
и — что важнее — **почему он устроен именно так**. Почти каждое решение здесь продиктовано
поведением реального железа, и без понимания этого поведения API выглядит произвольным.

Документ описывает только публичный слой `render_pipeline/`. Внутреннее устройство бэкендов
намеренно не раскрывается: код приложения не должен от него зависеть.

## 1. Модель работы с GPU

### 1.1. Асинхронность — главное, что нужно понять

CPU и GPU работают независимо. Приложение не «рисует» — оно **записывает список команд** и
отдаёт его GPU, после чего немедленно продолжает работу. GPU выполнит эти команды когда-то
потом. Из этого следует всё остальное:

* Ресурс, который вы «уже нарисовали», может всё ещё читаться видеокартой. Уничтожить или
  перезаписать его в этот момент — ошибка, которая проявляется как случайные мерцания или
  падения раз в сотню запусков.
* Между «отправил команды» и «картинка на экране» проходит один-два кадра. Это не задержка
  библиотеки, это конвейер.
* Любая операция, которая заставляет CPU дождаться GPU, разрушает конвейер. В API такие
  операции есть (`readback`, загрузка данных), и они намеренно выглядят «тяжёлыми».

Библиотека берёт на себя всю синхронизацию: приложение не создаёт ни одного примитива
синхронизации и не пишет ни одного барьера. Но понимать, что синхронизация *происходит*,
необходимо — иначе непонятно, почему одни операции дешёвые, а другие останавливают всё.

### 1.2. Кадры «в полёте»

Библиотека позволяет CPU опережать GPU ровно на **один кадр**: пока GPU рисует кадр N,
CPU записывает кадр N+1. Глубже конвейер не делается намеренно — это увеличило бы задержку
ввода без выигрыша в пропускной способности на типичной нагрузке.

Практическое следствие: все ресурсы, которые меняются каждый кадр, существуют внутри
библиотеки **в двух экземплярах**. Приложение этого не видит — оно просто пишет в буфер, —
но именно поэтому запись в динамический буфер не портит кадр, который сейчас исполняется.

### 1.3. Иерархия объектов

```
Surface   ── окно, в которое рисуем
   │
Device    ── логическое устройство: создаёт все ресурсы
   │
   ├── CommandQueue ── принимает работу; владеет переиспользуемыми ресурсами кадра
   │        │
   │        └── CommandBuffer ── запись команд одного кадра
   │
   ├── SwapChain ── очередь изображений для показа на экране
   │
   └── ресурсы: GBuffer, GImage, GSampler, ShaderFunction, Pipeline
```

Порядок создания важен и не произволен: `Surface` → `Device` → `CommandQueue` → `SwapChain`.
Устройство выбирается **с учётом** поверхности: не всякий GPU в системе умеет выводить
изображение в конкретное окно (типичный случай — ноутбук с двумя видеокартами, где к экрану
подключена только одна из них).

## 2. Жизненный цикл кадра

Канонический кадр выглядит так:

```cpp
// 1. Получить изображение для рисования.
//    Здесь же библиотека дожидается, пока освободится слот кадра.
std::shared_ptr<GImage> target = swapChain->acquireNextImage();
if (!target) continue;               // окно свёрнуто или изменило размер — кадр пропускаем

// 2. Описать, куда и как рисуем.
auto pass = helper::createRenderPassDescriptor();
pass->setColorAttachment(0, target, /*clear=*/true, ClearValue{0.1f, 0.1f, 0.1f, 1.0f});

// 3. Обновить данные, меняющиеся каждый кадр.
uniformBuffer->update(&uniforms, sizeof(uniforms));

// 4. Записать команды.
auto cmd = helper::createCommandBuffer(queue);
cmd->beginRenderPass(pass);
    cmd->setRenderPipeline(pipeline);
    cmd->setVertexBuffer(0, vertexBuffer);
    cmd->setUniformBuffer(1, ShaderStage::Fragment, uniformBuffer);
    cmd->drawIndexed(indexBuffer, IndexType::UInt16, indexCount);
cmd->endRenderPass();

// 5. Показать и отправить.
cmd->present(target);
cmd->commit();
```

### 2.1. Почему `acquireNextImage()` может вернуть `nullptr`

Это не ошибка. Так библиотека сообщает: «в этом кадре рисовать некуда». Причины — свёрнутое
окно (нулевой размер) или изменение размера, потребовавшее пересоздания цепочки изображений.
Правильная реакция — пропустить кадр целиком (`continue`), не создавая командный буфер.

### 2.2. Почему `present()` вызывается до `commit()`

`present()` ничего не делает немедленно — он лишь помечает, какое изображение показать, когда
записанная работа завершится. `commit()` отправляет всё сразу. Разделение существует потому,
что показ изображения обязан произойти **после** отрисовки, а не в момент вызова.

### 2.3. Ресайз окна

Обрабатывается вызовом `swapChain->recreate(width, height)`. Внутри библиотека дожидается
завершения всей работы GPU и пересоздаёт изображения. Все цели рендеринга, созданные
приложением под размер окна, нужно пересоздать самостоятельно — библиотека не знает, какие из
ваших изображений привязаны к размеру экрана.

## 3. Устройство (`Device`)

Точка создания всех ресурсов и источник информации о возможностях железа.

### 3.1. Создание

```cpp
auto surface = helper::createSurface(window, ImageFormat::BGRA8_UNORM);
auto device  = helper::createDefaultDevice(surface);
```

`createDefaultDevice` выбирает первый подходящий GPU. «Подходящий» означает: умеет рисовать,
умеет показывать в **эту** поверхность и поддерживает всё, что библиотека считает
обязательным.

### 3.2. Запросы возможностей

```cpp
MemoryBudget budget = device->queryMemoryBudget();
SampleCount  maxAA  = device->maxSupportedSampleCount();
uint32_t     maxAF  = device->maxSupportedAnisotropy();
const DeviceId& id  = device->getDeviceId();   // имя и идентификатор GPU
```

**`maxSupportedSampleCount()`** возвращает максимальное сглаживание, поддерживаемое и для
цвета, и для глубины одновременно. Четыре сэмпла есть везде на десктопе; восемь и шестнадцать
встречаются, но не гарантированы. Спрашивайте, а не предполагайте.

**`maxSupportedAnisotropy()`** — 16 практически на любом настольном GPU, 1 если возможности нет.
Спрашивать нужно только когда число само по себе важно: `SamplerDesc::maxAnisotropy` и так
обрезается до предела, поэтому просить 16 безопасно везде.

### 3.3. Фабрики ресурсов

```cpp
device->createBuffer(type, usage, size, initialData, debugName);
device->createImage(desc, initialData);
device->createSampler(desc, debugName);
```

Отдельными фабриками в `helper::` создаются объекты, которым нужен не только `Device`:
поверхность, свопчейн, очередь, командный буфер, шейдеры, пайплайны и дескрипторы проходов.

## 4. Поверхность и свопчейн

### 4.1. `Surface`

Обёртка над окном. Создаётся до устройства, потому что устройство выбирается с учётом
способности выводить изображение именно в это окно.

При создании указывается желаемый формат пикселей. Библиотека постарается получить именно его;
если железо такой формат не отдаёт, будет выбран ближайший доступный. Формат влияет на
цветопередачу: линейные форматы (`BGRA8_UNORM`) отдают то, что записал шейдер, без
преобразований.

### 4.2. `SwapChain`

Очередь изображений, циклически показываемых на экране. Пока одно показывается, в другое
рисуется — иначе был бы виден процесс отрисовки.

```cpp
auto swapChain = helper::createSwapChain(device, queue, surface, width, height);

std::shared_ptr<GImage> image = swapChain->acquireNextImage();
uint32_t w = swapChain->width();
uint32_t h = swapChain->height();
swapChain->recreate(newWidth, newHeight);
```

Показ синхронизирован с обновлением экрана (вертикальная синхронизация). Это ограничивает
частоту кадров частотой монитора и полностью исключает разрывы изображения.

Изображение, полученное из свопчейна, — особенное: в него можно рисовать, но его **нельзя**
ни прочитать в память CPU, ни использовать как текстуру. Если нужен скриншот финального кадра,
рисуйте в собственное изображение и копируйте его на экран.

## 5. Очередь и командный буфер

### 5.1. `CommandQueue`

Принимает записанную работу. Владеет всем, что переиспользуется от кадра к кадру, и следит,
чтобы переиспользование было безопасным. Приложение обычно создаёт одну очередь и больше о ней
не думает.

### 5.2. `CommandBuffer`

Запись команд одного кадра.

```cpp
auto cmd = helper::createCommandBuffer(queue);   // запись уже открыта
```

Важное свойство: **все методы записи только записывают**. Ни один из них не выполняет работу
на GPU в момент вызова. `commit()` отправляет весь список целиком.

Полный набор:

| Метод | Назначение |
|---|---|
| `beginRenderPass(pass)` | Начать проход: задать цели, очистить их |
| `setRenderPipeline(pipeline)` | Выбрать шейдеры и все фиксированные состояния |
| `setVertexBuffer(slot, buffer, offset)` | Привязать буфер геометрии |
| `setUniformBuffer(slot, stage, buffer, offset)` | Привязать буфер констант |
| `setTexture(slot, stage, image, sampler)` | Привязать текстуру и способ её чтения |
| `setPushConstants(stage, data, size, offset)` | Записать малые данные прямо в поток команд |
| `draw(...)` | Отрисовка без индексов |
| `drawIndexed(...)` | Отрисовка по индексам |
| `drawIndirect(...)` / `drawIndexedIndirect(...)` | Отрисовка с параметрами из буфера |
| `endRenderPass()` | Завершить проход |
| `present(image)` | Пометить изображение к показу |
| `commit()` | Отправить всё на исполнение |

Проходов в одном командном буфере может быть несколько — именно так строятся многопроходные
схемы (рисуем в текстуру, затем читаем её в следующем проходе).

## 6. Память

### 6.1. Два вида памяти

У дискретной видеокарты есть собственная память (VRAM), и она **не адресуется процессором**.
Данные попадают в неё только копированием через промежуточный буфер. Есть и память, видимая
процессору напрямую, но GPU читает её медленнее — через системную шину.

Библиотека не заставляет выбирать вручную. Вы описываете *намерение*, она выбирает размещение:

| Намерение | Размещение | Как работает обновление |
|---|---|---|
| `BufferUsage::Static` | VRAM | Через промежуточный буфер и копирование на GPU |
| `BufferUsage::Dynamic` | Память, видимая CPU | Прямая запись в памяти |
| `BufferUsage::Stream` | Память, видимая CPU | Прямая запись в памяти |

Логика проста: `Static` пишется один раз и читается тысячи раз — разовая стоимость копирования
окупается всеми последующими чтениями. `Dynamic` переписывается каждый кадр — копирование
обошлось бы дороже, чем более медленное чтение.

Куда ресурс попал на самом деле, показывает `memoryLocation()`. Это **результат**, а не запрос:
на встроенной графике вся память общая, а при нехватке VRAM библиотека разместит статический
буфер в системной памяти, а не откажет в создании.

### 6.2. Бюджет видеопамяти

```cpp
MemoryBudget b = device->queryMemoryBudget();

b.deviceLocalTotalBytes;      // размер видеопамяти
b.deviceLocalBudgetBytes;     // сколько процессу разумно занимать
b.deviceLocalUsedBytes;       // сколько занято сейчас
b.availableBytes();           // сколько ещё можно
b.unifiedMemory;              // общая память с CPU (встроенная графика)
b.preciseBudget;              // цифры настоящие, а не оценка
b.nativeAllocationCount;      // число крупных блоков памяти
b.reservedBytes;              // сколько зарезервировано под эти блоки
```

Цифры меняются: другие процессы тоже занимают память. Опрашивайте заново после крупных
выделений, а не вычитайте из предыдущего значения.

**Проверка вместимости встроена в создание ресурсов.** Буфер, который не помещается,
размещается в системной памяти. Изображение — нет: текстура вне VRAM бессмысленна, поэтому
создание завершается ошибкой с указанием, сколько не хватило.

### 6.3. Почему количество выделений имеет значение

`nativeAllocationCount` — это не диагностика ради диагностики. Драйверы ограничивают, сколько
раз процесс может запросить у системы блок видеопамяти; типичный предел — около четырёх тысяч,
и он жёсткий. Библиотека выделяет несколько крупных блоков и раздаёт куски внутри них, поэтому
число остаётся маленьким и почти не растёт с количеством ресурсов. Если оно растёт линейно —
что-то не так.

## 7. Буферы (`GBuffer`)

Линейный блок памяти на GPU.

### 7.1. Создание

```cpp
auto vb = device->createBuffer(BufferType::Vertex,  BufferUsage::Static,  size, data, "Vertices");
auto ib = device->createBuffer(BufferType::Index,   BufferUsage::Static,  size, data, "Indices");
auto ub = device->createBuffer(BufferType::Uniform, BufferUsage::Dynamic, size, nullptr, "Uniforms");
auto arg = device->createBuffer(BufferType::Indirect, BufferUsage::Static, size, cmds, "DrawArgs");
auto inst = device->createBuffer(BufferType::Storage, BufferUsage::Dynamic, size, nullptr, "Instances");
```

| Тип | Назначение |
|---|---|
| `Vertex` | Геометрия. Читается вершинным шейдером по индексу вершины |
| `Index` | Индексы вершин |
| `Uniform` | Константы, общие для множества вершин или фрагментов. Предел **16 КиБ** |
| `Storage` | Массив, индексируемый по-разному в каждой нити: инстансы, кости, таблицы |
| `Indirect` | Параметры команд отрисовки, читаемые самим GPU |

`Uniform` годится и на роль storage-буфера — его аллокация несёт оба назначения, — поэтому
отдельный тип нужен главным образом чтобы сказать, что это за данные, в месте создания.

### 7.2. Обновление

```cpp
buffer->update(data, size);              // весь буфер
buffer->update(&value, sizeof(value), offsetof(Uniforms, field));  // частично
```

**Частичное обновление полностью корректно.** Байты, которых вы не касались, сохраняют прежние
значения — независимо от того, как библиотека размещает память под капотом. Это стоит одной
дополнительной внутренней копии для динамических буферов, поэтому если структура меняется
целиком, дешевле записать её целиком.

Для `Static` буфера `update()` — медленная операция: данные едут через промежуточный буфер, и
вызов ждёт завершения копирования. Это осознанно: то, что меняется часто, должно быть
`Dynamic`.

### 7.3. Чтение обратно

```cpp
buffer->readback(destination, size, offset);
```

Забирает данные из GPU в память CPU. Останавливает конвейер: сначала дожидается завершения всей
работы, потом копирует. Инструмент отладки и оснастки, не операция для каждого кадра.

## 8. Изображения (`GImage`)

Текстуры и цели рендеринга — один и тот же тип объекта.

### 8.1. Создание

```cpp
ImageDesc desc{};
desc.type        = ImageType::Image2D;   // Image1D / Image2D / Image3D / CubeMap
desc.format      = ImageFormat::RGBA8_UNORM;
desc.width       = 1024;
desc.height      = 1024;
desc.depth       = 1;                    // > 1 только для Image3D
desc.arrayLayers = 1;                    // слои массива; у CubeMap всегда 6
desc.mipLevels   = kFullMipChain;        // 0 = полная цепочка до 1x1
desc.sampleCount = SampleCount::One;
desc.usage       = ImageUsage::Sampled;
desc.debugName   = "Albedo";

auto image = device->createImage(desc, pixels);
```

### 8.2. Назначение (`ImageUsage`)

Битовая маска, задаваемая **при создании и навсегда**. Расширить её позже нельзя: железо
раскладывает данные в памяти по-разному в зависимости от того, как их будут использовать.

| Флаг | Значение |
|---|---|
| `Sampled` | Читается шейдером как текстура |
| `ColorTarget` | В него рисует проход рендеринга |
| `DepthStencil` | Буфер глубины/трафарета |
| `Storage` | Произвольная запись из шейдера |
| `TransferSrc` | Можно прочитать в память CPU или скопировать из него |
| `TransferDst` | Можно записать из памяти CPU |

Типичные сочетания: `Sampled` для текстуры из файла, `ColorTarget | Sampled` для
промежуточной цели, `ColorTarget | Sampled | TransferSrc` если нужен ещё и скриншот.

### 8.3. Загрузка данных

```cpp
image->update(pixels, size);                  // 2D: весь уровень
image->update(voxels, size);                  // 3D: весь объём разом
image->update(facePixels, size, 0, faceIndex); // куб/массив: один слой
image->generateMipmaps();                     // достроить цепочку на GPU
```

Данные должны лежать плотно, без выравнивания строк. Сколько байт ожидается — считает
`imageLevelBytes(format, width, height, depth)`.

Один вызов покрывает:
* **2D** — весь уровень;
* **3D** — весь объём, срезы подряд;
* **массив или куб** — один слой. Грани куба идут в порядке `+X, −X, +Y, −Y, +Z, −Z`.

### 8.4. Мип-уровни

Мип-цепочка — это заранее уменьшенные копии текстуры. Без неё текстура, показанная мелко,
превращается в шум: пиксель экрана накрывает десятки текселей, а читается из них один.

`generateMipmaps()` строит цепочку на GPU из нулевого уровня. Работает только для несжатых
форматов — сжатые уровни нужно готовить заранее и загружать по одному.

### 8.5. Сглаживание (MSAA)

Многосэмпловое изображение хранит несколько значений на пиксель и сглаживает края геометрии.

```cpp
ImageDesc msaa{};
msaa.sampleCount = SampleCount::Four;
msaa.usage       = ImageUsage::ColorTarget;   // только цель, не текстура
```

Три правила, вытекающие из природы многосэмплового хранения:

* его **нельзя читать шейдером** — сначала нужно свести к обычному изображению;
* у него **не бывает мип-уровней**;
* оно **не может быть сжатым**.

Сведение (resolve) описывается в проходе рендеринга и не стоит отдельной отрисовки — железо
делает его при завершении прохода.

### 8.6. Форматы

**Несжатые:**

| Формат | Байт/пиксель | Назначение |
|---|---|---|
| `RGBA8_UNORM`, `BGRA8_UNORM` | 4 | Обычный цвет, линейные данные |
| `RGBA8_SRGB`, `BGRA8_SRGB` | 4 | Цвет: аппаратура преобразует sRGB ↔ линейное бесплатно |
| `RGBA16_FLOAT` | 8 | HDR, когда нужен альфа-канал или отрицательные значения |
| `R11G11B10_FLOAT` | 4 | HDR-цвет без альфы. Вдвое дешевле `RGBA16_FLOAT` |
| `RGB10A2_UNORM` | 4 | Нормали в G-буфере: 10 бит на ось, ступеней не видно |
| `RG16_FLOAT` | 4 | Двухканальные данные высокой точности: буфер скоростей |
| `R32_FLOAT` | 4 | Одноканальные данные: линейная глубина, карты теней большой сцены |
| `RG8_UNORM` | 2 | Два канала: октаэдральные нормали |
| `R16_FLOAT` | 2 | Один канал: карты теней, промежуточные величины |
| `R8_UNORM` | 1 | Маски, затенение, любой одноканальный признак |
| `D32_FLOAT`, `D24_UNORM_S8_UINT`, `D16_UNORM` | 4 / 4 / 2 | Глубина и трафарет |

Выбор формата цели рендеринга — это **прямой выбор пропускной способности**. При 2560×1440 и
60 кадрах в секунду каждый байт на пиксель стоит около 0.22 ГБ/с на запись и столько же на
чтение. Замена одной цели G-буфера с `RGBA16_FLOAT` на `RGB10A2_UNORM` экономит 1.8 ГБ/с.

`RGB10A2_UNORM` беззнаковый: нормаль надо отобразить из [-1, 1] в [0, 1] при записи и обратно
при чтении.

**Сжатые блоками 4×4:**

| Формат | Бит/тексель | Назначение |
|---|---|---|
| `BC1_RGBA_UNORM` / `_SRGB` | 4 | Цвет, альфа 1 бит. Самый дешёвый |
| `BC3_UNORM` / `_SRGB` | 8 | Цвет с плавной альфой |
| `BC4_UNORM` | 4 | Один канал: карты высот, маски |
| `BC5_UNORM` | 8 | Два канала: карты нормалей |
| `BC7_UNORM` / `_SRGB` | 8 | Максимальное качество цвета |

Сжатие даёт выигрыш **в 4–8 раз** по памяти, и GPU распаковывает блоки при чтении бесплатно.
Именно так реальный набор текстур помещается в бюджет видеопамяти.

Варианты `_SRGB` (как сжатые, так и несжатые) при чтении преобразуют значения из sRGB в линейное
пространство, а при записи — обратно. Это то, что нужно цветовым (альбедо) текстурам и
поверхности свопчейна. Данные, не являющиеся цветом — карты нормалей, шероховатости, маски, —
должны использовать `_UNORM`.

Преобразование не только бесплатно, но и **точнее ручного `pow()`**: аппаратура делает его до
фильтрации, а шейдер — после, и смесь двух sRGB-значений не равна sRGB от смеси линейных.

Проверить формат можно через `isSrgbFormat()`. Делать преобразование дважды — самая частая
ошибка: картинка получается слишком тёмной, но правдоподобной.

Три ограничения сжатых форматов вытекают из блочной природы: в них **нельзя рисовать**,
их **нельзя сглаживать**, и их **мип-уровни нельзя построить на GPU**.

Вспомогательные функции: `formatInfo()`, `isCompressedFormat()`, `isSrgbFormat()`,
`imageLevelBytes()`, `rowPitch()`, `bytesPerPixel()` (только для несжатых).

### 8.7. Чтение обратно

```cpp
image->readback(destination, size, mipLevel, arrayLayer);
```

Требует `ImageUsage::TransferSrc`. Останавливает конвейер. Не работает для многосэмпловых
изображений и для изображений свопчейна.

## 9. Сэмплеры (`GSampler`)

Описывают **как** шейдер читает текстуру: фильтрацию и поведение за границами.

```cpp
SamplerDesc desc{};
desc.minFilter = SamplerFilter::Linear;   // уменьшение
desc.magFilter = SamplerFilter::Linear;   // увеличение
desc.mipFilter = SamplerFilter::Linear;   // между мип-уровнями
desc.addressU  = SamplerAddressMode::Repeat;
desc.addressV  = SamplerAddressMode::ClampToEdge;
desc.minLod    = 0.0f;
desc.maxLod    = 1000.0f;
desc.maxAnisotropy = 16;                  // 1 — выключено

auto sampler = device->createSampler(desc, "Trilinear16x");
```

Сэмплер — отдельный от текстуры объект, потому что так устроено железо: один сэмплер
обслуживает сколько угодно текстур. Создайте несколько и переиспользуйте.

* `Linear` + `Linear` для `mipFilter` даёт трилинейную фильтрацию — плавные переходы между
  мип-уровнями без видимых границ.
* `Nearest` полезен, когда нужна пиксель-в-пиксель точность (промежуточные цели того же
  размера, что экран) или намеренная «пиксельность».
* `ClampToEdge` обязателен для граней кубических карт — иначе на швах подмешивается соседняя
  грань.

### 9.1. Анизотропная фильтрация

Поверхность, видимая под скользящим углом — пол, уходящий к горизонту, — накрывается пикселем в
виде **вытянутого** следа: несколько текселей поперёк, десятки вдоль. Трилинейная фильтрация
умеет выбирать только квадратный участок, поэтому берёт мип-уровень по длинной оси и размывает
вместе с ней короткую. Анизотропная делает несколько выборок вдоль длинной оси и сохраняет
резкость.

```cpp
desc.maxAnisotropy = 16;                        // обрезается до предела устройства
const uint32_t supported = device->maxSupportedAnisotropy();   // 16 почти везде, 1 если нет
```

* Значения выше предела **обрезаются**, а не отвергаются: писать 16 безопасно везде.
* Платит только **минификация**. Текстура, видимая вблизи, не дорожает ни на такт.
* Плата — пропускная способность, пропорционально числу выборок, и только на тех пикселях, где
  след действительно вытянут.
* **Без мип-цепочки не работает**: выбирать не из чего.
* Разница между 1× и 4× огромна, между 8× и 16× почти незаметна. 8 — разумное умолчание.

## 10. Шейдеры (`ShaderFunction`)

```cpp
auto vs = helper::createShaderFunction(device, SHADER_DIR "/PlaneShader", "plane_vertex_shader");
auto fs = helper::createShaderFunction(device, SHADER_DIR "/PlaneShader", "plane_fragment_shader");
```

Путь передаётся **без расширения**, точка входа — по логическому имени. Как именно бэкенд
находит и готовит код, приложения не касается: одна и та же строка работает везде.

Практическое следствие: исходники шейдеров для разных бэкендов лежат отдельно, но имена точек
входа общие, и код приложения их не различает.

## 11. Пайплайн (`Pipeline`)

Пайплайн собирает шейдеры и **все** фиксированные состояния в один неизменяемый объект.
Создавать его дорого, привязывать — дёшево. Создавайте заранее, не в цикле кадра.

```cpp
PipelineDesc desc{};
desc.vertexFunction   = vs;
desc.fragmentFunction = fs;
desc.targetFormat     = RenderTargetFormat::singleTarget(ImageFormat::BGRA8_UNORM);
desc.blendStates      = { BlendState::alphaBlend() };
desc.depthStencil     = DepthStencilState::depthTestAndWrite();
desc.rasterizer.cullMode = CullMode::Back;
desc.debugName        = "Opaque";

auto pipeline = helper::createPipeline(device, desc);
```

Для простого непрозрачного рендеринга есть короткая форма:

```cpp
auto pipeline = helper::createPipeline(device, vs, fs, targetFormat);
```

### 11.1. Форматы целей (`RenderTargetFormat`)

```cpp
std::vector<ImageFormat> colorFormats;   // по одному на выход фрагментного шейдера
ImageFormat depthFormat;
ImageFormat stencilFormat;
SampleCount sampleCount;
```

**Это часть идентичности пайплайна.** Пайплайн действителен только в проходе с такими же
целями. Число форматов обязано совпадать с числом выходов шейдера и с числом вложений прохода.

Отсюда важное практическое следствие: **включить сглаживание или добавить цель на лету
нельзя** — нужен отдельный пайплайн для каждой конфигурации. Создавайте их заранее.

Помощники: `RenderTargetFormat::singleTarget(color, depth, samples)` и
`multiTarget({colors...}, depth, samples)`.

### 11.2. Смешивание (`BlendState`)

По одному состоянию на цель — проход с несколькими целями может смешивать одну и перезаписывать
другую.

```cpp
BlendState::alphaBlend();   // обычная прозрачность
BlendState::additive();     // свечение, частицы
BlendState{};               // непрозрачно (по умолчанию)
```

Полная форма даёт раздельные множители и операции для цвета и альфы, а также маску записи
каналов (`ColorComponent`).

### 11.3. Глубина и трафарет (`DepthStencilState`)

```cpp
DepthStencilState::depthTestAndWrite();   // непрозрачная геометрия
DepthStencilState::depthTestOnly();       // прозрачная: проверяем, но не пишем
```

Полная форма: включение теста и записи, функция сравнения, полное описание операций трафарета
раздельно для лицевых и обратных граней.

Тест глубины требует, чтобы у прохода была цель глубины и чтобы пайплайн объявил её формат.
Запрос теста без цели — ошибка с внятным сообщением, а не тихая порча кадра.

### 11.4. Растеризация (`RasterizerState`)

```cpp
desc.rasterizer.cullMode            = CullMode::Back;   // None / Front / Back
desc.rasterizer.frontFace           = FrontFace::CounterClockwise;
desc.rasterizer.polygonMode         = PolygonMode::Fill; // Fill / Line
desc.rasterizer.depthBiasConstant   = 0.0f;
desc.rasterizer.depthBiasSlope      = 0.0f;
```

Отсечение граней (`CullMode::Back`) выбрасывает невидимые задние грани до растеризации и
экономит заметную долю работы на замкнутой геометрии. По умолчанию отсечения нет — так порядок
обхода вершин не может испортить картинку.

Смещение глубины нужно почти исключительно теневым картам: без него поверхность затеняет сама
себя из-за конечной точности буфера глубины.

## 12. Проход рендеринга (`RenderPassDescriptor`)

Описывает, куда идёт результат и что сделать с целями в начале прохода.

```cpp
auto pass = helper::createRenderPassDescriptor();

pass->setColorAttachment(0, colorTarget, /*clear=*/true, clearValue);
pass->setColorAttachment(1, normalTarget, true, clearValue);        // MRT
pass->setResolveAttachment(0, resolvedTarget);                      // сведение MSAA
pass->setDepthStencilAttachment(depthTarget, true, 1.0f, false, 0);
uint32_t count = pass->colorAttachmentCount();
```

### 12.1. Несколько целей (MRT)

Фрагментный шейдер может писать в несколько изображений за один проход. Так строится
отложенное освещение: за один проход по геометрии записываются цвет, нормали и параметры
материала, а освещение считается потом.

Цели задаются **подряд с нуля**, без пропусков. Все обязаны совпадать по размеру и числу
сэмплов.

### 12.2. Очистка

Флаг `clear` — не косметика. Очистка **дешевле** сохранения предыдущего содержимого: железо
не читает старые данные из памяти. Если вы всё равно перезаписываете весь экран, очищайте.

### 12.3. Сведение MSAA

```cpp
pass->setColorAttachment(0, msaaTarget, true, clearValue);
pass->setResolveAttachment(0, ordinaryTarget);
```

Многосэмпловые данные усредняются в обычное изображение при завершении прохода. Отдельной
отрисовки это не требует, а сами сэмплы после сведения отбрасываются — что позволяет железу
вообще не записывать их в память.

### 12.4. Слои массива

```cpp
pass->setColorAttachment(0, cubeMap, true, clearValue, /*arrayLayer=*/faceIndex);
```

Так заполняется грань кубической карты или срез каскада теней.

### 12.5. Многопроходные схемы

Несколько проходов в одном командном буфере — обычное дело. Запись в изображение в одном
проходе и чтение его в следующем **синхронизируются автоматически**: приложение не пишет ни
одного барьера.

```cpp
cmd->beginRenderPass(gbufferPass);   /* рисуем геометрию */   cmd->endRenderPass();
cmd->beginRenderPass(lightingPass);  /* читаем g-буфер */     cmd->endRenderPass();
```

Единственное, чего делать нельзя, — читать изображение, которое **сейчас** является целью
текущего прохода.

## 13. Модель привязки ресурсов

### 13.1. Слоты

Ресурсы привязываются к нумерованным слотам, и номер слота — это то, что видит шейдер.
Буферы и текстуры нумеруются **независимо**: текстура в слоте 0 и буфер в слоте 0 — разные
привязки.

| Вызов | Слоты | Что видит шейдер |
|---|---|---|
| `setVertexBuffer(0, …)` | 0…7 | Массив геометрии, индексируемый номером вершины |
| `setStorageBuffer(n, …)` | 0…7 | Массив, индексируемый по-разному в каждой нити |
| `setUniformBuffer(n, …)` | 0…7 | Блок констант, одинаковый для всех нитей |
| `setTexture(n, …)` | 0…7 | Текстура вместе с сэмплером |

Геометрия читается шейдером **как массив по номеру вершины**, а не через фиксированное
описание вершинных атрибутов. Это даёт полную свободу в раскладке вершины — но требует, чтобы
структура в шейдере совпадала со структурой в C++ побайтово.

#### Тип слота объявляет пайплайн

Storage-буфер это или uniform-блок, решается при создании пайплайна, а не при привязке:

```cpp
PipelineDesc desc{};
desc.bufferSlots = defaultBufferSlotLayout();        // 0 — storage, 1…7 — uniform
desc.bufferSlots[2] = BufferBindingType::Storage;    // слот 2 тоже storage
```

Объявленное обязано совпадать с тем, что написано в шейдере, слот в слот. Иначе — ошибка
валидации или неверная картинка.

Почему это нельзя вывести из того, что привязали: на Vulkan тип дескриптора зашит в раскладку
дескрипторного набора, против которой **компилируется пайплайн**. К моменту вызова отрисовки,
когда наконец известно, что привязано, раскладка уже выбрана. На Metal разницы нет вовсе — там и
то и другое просто буфер по индексу, различается лишь квалификатор адресного пространства.
Устройство держит кеш раскладок, поэтому распространённые комбинации строятся по одному разу.

Следствие: **сеттеры взаимозаменяемы**. Тип берётся из пайплайна, а `setUniformBuffer()` и
`setStorageBuffer()` различаются только читаемостью на месте вызова. Проверяется одно: буфер,
чья аллокация не годится для запрошенной роли, вызывает понятную ошибку.

#### Что куда класть

| | Uniform-блок | Storage-буфер |
|---|---|---|
| Размер | **16 КиБ** переносимо | гигабайты |
| Доступ | все нити по одному адресу | у каждой нити свой индекс |
| Скорость | быстрее при одинаковом адресе | не хуже при разном |
| Для чего | матрицы камеры, свет, параметры прохода | вершины, инстансы, кости, таблицы |
| MSL | `constant T& u [[buffer(n)]]` | `const device T* p [[buffer(n)]]` |
| GLSL | `layout(std140, …) uniform` | `layout(std430, …) readonly buffer` |

16 КиБ — это 204 матрицы 4×4. Именно поэтому инстансы и кости живут в storage-буфере: с uniform
потолок наступает на двухсотой копии.

### 13.2. Push-константы

Самый дешёвый способ передать данные, свои для каждой отрисовки:

```cpp
cmd->setPushConstants(ShaderStage::Vertex, &constants, sizeof(constants));
```

Ничего не выделяется, ничего не привязывается — байты едут внутри самого потока команд.
Идеально для матрицы преобразования, индекса материала, оттенка. Гарантированный объём —
**128 байт**; больше не переносимо.

Для данных, общих у множества отрисовок, — uniform-буфер. Для больших массивов, индексируемых
per-thread, — storage-буфер.

### 13.3. Эффективность привязок

Библиотека кэширует внутреннее представление набора привязок в пределах кадра. Практическое
следствие: **отрисовки, отличающиеся только push-константами, почти бесплатны** — именно
поэтому per-draw данные стоит класть туда, а не в отдельные буферы.

## 14. Команды отрисовки

### 14.1. Обычная отрисовка

```cpp
cmd->draw(vertexCount, instanceCount, firstVertex, firstInstance);

cmd->drawIndexed(indexBuffer, IndexType::UInt16,
                 indexCount, instanceCount,
                 firstIndexOffsetBytes, vertexOffset, firstInstance);
```

`instanceCount` рисует геометрию многократно за один вызов; шейдер различает копии по номеру
экземпляра. Это основной механизм для травы, толп, частиц и любых повторяющихся объектов —
одна команда вместо тысячи.

Смещение первого индекса задаётся **в байтах**, а не в индексах.

### 14.2. Непрямая отрисовка

Параметры отрисовки читаются GPU **из буфера**, а не передаются из кода:

```cpp
DrawIndexedIndirectCommand cmdArgs{};
cmdArgs.indexCount    = 36;
cmdArgs.instanceCount = 1000;
cmdArgs.firstIndex    = 0;
cmdArgs.vertexOffset  = 0;
cmdArgs.firstInstance = 0;

auto argBuffer = device->createBuffer(BufferType::Indirect, BufferUsage::Static,
                                      sizeof(cmdArgs), &cmdArgs, "Args");

cmd->drawIndexedIndirect(indexBuffer, IndexType::UInt16, argBuffer, /*drawCount=*/1);
```

Смысл — в том, что CPU **не сообщает**, сколько рисовать. Уже сегодня это позволяет подготовить
список отрисовок один раз и переиспользовать его; в перспективе — заполнять его прямо на GPU,
не возвращая данные процессору.

Сможет ли железо выдать все команды за один вызов, зависит от него самого; если нет, библиотека
выдаст их по одной. Результат одинаков, отличается только нагрузка на CPU.

## 15. Соглашения для шейдеров

Шейдер, написанный под эту библиотеку, видит **один** набор соглашений. Там, где нижележащие
API расходятся, расхождение устраняется библиотекой.

### 15.1. Пространство отсечения: +X вправо, +Y вверх, Z в диапазоне [0, 1]

Матрица проекции пишется один раз и работает везде. Ни переворачивать Y, ни пересчитывать
диапазон глубины не нужно.

### 15.2. Позиция фрагмента: пиксели, начало в левом верхнем углу

Встроенная позиция фрагмента — координата во фреймбуфере, в пикселях, с началом в левом верхнем
углу и выборкой в центрах пикселей.

### 15.3. Координаты текстуры: (0, 0) — верхний левый тексель

В сочетании с «+Y вверх» это означает, что перевод позиции из пространства отсечения в
координату текстуры **всегда инвертирует Y**:

```glsl
uv = vec2(position.x * 0.5 + 0.5, 0.5 - position.y * 0.5);
```

### 15.4. Порядок обхода вершин

Одинаков на всех бэкендах: `FrontFace::CounterClockwise` отбирает одни и те же треугольники
везде.

### 15.5. Раскладка данных

Структуры констант обязаны совпадать с C++ **побайтово**. Главная ловушка — векторы в блоках
констант выравниваются по 8 или 16 байт, из-за чего поля разъезжаются. Надёжный приём —
объявлять поля скалярами:

```glsl
// Соответствует struct { float viewport[2]; float scale; float pan[2]; }
layout(std140, binding = 1) uniform Uniforms {
    float viewportX;
    float viewportY;
    float scale;
    float panX;
    float panY;
};
```

Массивы геометрии в буфере, читаемом вершинным шейдером, выравниваются по 16 байт для
трёхкомпонентных векторов — структуру в C++ нужно дополнять до того же размера.

## 16. Ограничения и то, чего нет

Честный список. Всё перечисленное — отсутствующие возможности, а не скрытые ошибки.

### 16.1. Жёсткие ограничения

| Ограничение | Значение |
|---|---|
| Кадров в полёте | 2 |
| Цветовых целей на проход | 8 |
| Слотов буферов | 8, тип каждого объявляется в `PipelineDesc::bufferSlots` |
| Uniform-блок | 16 КиБ переносимо (у storage-буфера предела нет) |
| Слотов текстур | 8 |
| Push-константы | 128 байт |
| Многосэмплово | Только цели, без чтения и мипов |
| Сжатые форматы | Только чтение, мипы готовятся заранее |

### 16.2. Чего нет

**Вычислительные шейдеры.** `ShaderStage::Compute` объявлен, но отвергается. Отсечение
геометрии на GPU, симуляция частиц, скиннинг, кластерное освещение — недоступны. Пост-обработка
при этом возможна: она делается фрагментными проходами.

**Описание вершинных атрибутов.** Раскладка вершины задаётся структурой в шейдере, поэтому
произвольная модель должна приводиться к единому формату при загрузке.

**Рендеринг в срез 3D-текстуры.** В слои массивов — можно, в глубину объёма — нет.

**Сэмплеры сравнения.** Аппаратная фильтрация теней недоступна; сравнение глубины пишется в
шейдере вручную.

**Запросы времени и перекрытия.** Измерить время работы GPU или сделать отсечение по
перекрытию нельзя.

**Одна очередь.** Загрузка данных останавливает графическую работу — это приемлемо при
инициализации и неприемлемо для потоковой подгрузки.

**Однопоточная запись команд.** Список команд формируется одним потоком, что становится
узким местом при тысячах вызовов отрисовки.

**Кэш пайплайнов.** Пайплайны компилируются заново при каждом запуске.

**Устойчивость.** Потеря устройства не обрабатывается, потокобезопасности нет.

**Целочисленные форматы.** Выбор пикселя, реализуемый через целочисленную цель, приходится
упаковывать в нормализованные каналы.

**Сдвиг уровня мипа (`mipLodBias`).** Резкость подстраивается только грубо, через `minLod`.

**Чтение буфера глубины.** Изображение с назначением `DepthStencil` нельзя привязать как
текстуру: оно отдыхает в состоянии вложения глубины. Линейную глубину и карты теней приходится
писать в цветовую цель самостоятельно — что, впрочем, даёт настройкам смещения физический смысл.

**Рендеринг в уровень мипа.** В слои массивов — можно, в мип-уровень — нет, поэтому цепочки
уменьшения строятся из отдельных изображений.

**Подпроходы и memoryless-цели.** На тайловой архитектуре (Apple Silicon) промежуточные цели
могли бы не покидать чип вовсе. Без этого отложенный рендеринг там платит полный трафик
G-буфера — то есть работает как на дискретной карте, теряя главное преимущество платформы.

**`alphaToCoverage`.** Края геометрии с альфа-маской остаются ступенчатыми даже при включённом
MSAA.

**Область отсечения (scissor).** Ограничить отрисовку прямоугольником экрана нельзя.
