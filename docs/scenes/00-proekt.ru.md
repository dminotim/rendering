# Часть 0. Проект

> **Цель главы.** Собрать пустой проект, который подключает `dmrender` как зависимость, и довести
> его до кадра с очищенным экраном. Разобрать `CMakeLists.txt` построчно — каждая строка отвечает
> за конкретную вещь, и почти каждая из них когда-нибудь сломается, поэтому знать, за что именно
> она отвечает, полезнее, чем скопировать файл целиком. К концу главы будет окно, которое
> закрашивается выбранным цветом, и каркас, в который глава 2 добавит треугольник.

Эта глава — не про графику. Она про то, чтобы дальше не тратить время на сборку.

---

## 0.1. Что где лежит

Обёртка живёт в отдельном репозитории. Раньше она лежала в том же дереве, что и приложение, в
каталогах `render_pipeline/`, `render_vulkan/`, `render_metal/`; теперь это библиотека `dmrender`,
а приложение — один из её потребителей.

Разделение не косметическое. Оно означает, что приложение **физически не может** дотянуться до
Vulkan или Metal: заголовки бэкендов не устанавливаются и не попадают в пути включения. Если
что-то из кода приложения захотело `VkDevice`, это ошибка компиляции, а не вопрос дисциплины.

```
dmwrapper/                   ← библиотека dmrender, отдельный репозиторий
  render_pipeline/           публичный API: Device, SwapChain, CommandBuffer, Pipeline, GBuffer…
  render_vulkan/             реализация на Vulkan   (Windows)  — приватная
  render_metal/              реализация на Metal    (macOS)    — приватная
  external/glfw, external/imgui
  docs/                      справочник по API, книга 1, обзор пайплайна

my-renderer/                 ← ваш проект
  CMakeLists.txt
  main.cpp
  shaders/metal, shaders/glsl
```

Оба каталога рядом — это то, что предполагают значения по умолчанию. Другое расположение задаётся
одной переменной, см. 0.4.

### Что нужно установить

| | Windows | macOS |
|---|---|---|
| Компилятор | MSVC 2019+ | Xcode Command Line Tools |
| CMake | 3.20+ | 3.20+ |
| API | Vulkan SDK (в нём же `glslc`) | ничего, Metal в системе |

Vulkan SDK нужен целиком, а не только рантайм: из него берётся `glslc`, компилятор GLSL в SPIR-V.
На macOS аналога не требуется — Metal компилирует шейдеры в рантайме.

### Забрать обёртку

```sh
git clone --recurse-submodules https://github.com/dminotim/dmwrapper.git
```

**Про имена.** Репозиторий называется `dmwrapper`, а библиотека и её цель в CMake — `dmrender`.
Это не опечатка: имя репозитория и имя пакета — разные вещи, и второе встречается в коде, а первое
только в командах git. В `CMakeLists.txt` вы пишете `dmrender::dmrender` независимо от того, в
какой каталог склонировали.

Каталог по умолчанию ищется рядом с проектом — сначала `../dmwrapper`, потом `../dmrender`, так что
обычный `git clone` подходит. Любое другое расположение задаётся через `DMRENDER_DIR`.

`--recurse-submodules` обязателен: GLFW и Dear ImGui подключены подмодулями. Если уже склонировали
без него:

```sh
cd dmwrapper && git submodule update --init --recursive
```

Симптом забытых подмодулей — `FATAL_ERROR` от CMake с явным текстом про то, какой каталог пуст.
Это сделано специально: без проверки ошибка выглядела бы как отсутствующий заголовок `glfw3.h` из
середины сборки.

## 0.2. Минимальный `CMakeLists.txt`

Сначала целиком, потом построчно.

```cmake
cmake_minimum_required(VERSION 3.20)

project(MyRenderer LANGUAGES C CXX)
if(APPLE)
    enable_language(OBJCXX)
endif()

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)

# --- обёртка ---
set(DMRENDER_DIR "${CMAKE_CURRENT_SOURCE_DIR}/../dmwrapper"
        CACHE PATH "Source checkout of the dmrender wrapper")

find_package(dmrender QUIET CONFIG)
if(NOT dmrender_FOUND)
    add_subdirectory("${DMRENDER_DIR}" "${CMAKE_BINARY_DIR}/dmrender")
endif()

# --- приложение ---
add_executable(MyRenderer main.cpp)

target_link_libraries(MyRenderer PRIVATE
        dmrender::dmrender
        glfw
        imgui)
```

Двадцать строк. Дальше — за что отвечает каждая.

## 0.3. Разбор: преамбула

### `cmake_minimum_required(VERSION 3.20)`

Задаёт не «версию CMake, которая нужна», а **набор правил поведения**. CMake хранит десятки
политик совместимости, и эта строка включает те, что действовали в 3.20. Понизить её, чтобы
«работало на старом CMake», нельзя безболезненно: часть политик изменит поведение целей.

3.20 выбрано потому, что начиная с неё `OBJCXX` — полноценный язык первого класса, а `find_package`
корректно работает с пакетами, экспортированными через `install(EXPORT)`. И то и другое нам нужно.

### `project(MyRenderer LANGUAGES C CXX)`

Первый вызов `project()` — момент, когда CMake определяет платформу, ищет компиляторы и заполняет
переменные вроде `APPLE`, `WIN32`, `MSVC`.

`C` в списке нужен не приложению, а GLFW: он написан на C, и без включённого языка `C` его
подкаталог не соберётся.

### `if(APPLE) enable_language(OBJCXX) endif()`

**Это та строка, которую почти все пишут неправильно, включая нас в первой версии проекта.**

Естественно хочется написать так:

```cmake
if(APPLE)
    project(MyRenderer LANGUAGES C CXX OBJC OBJCXX)   # ← неверно
else()
    project(MyRenderer LANGUAGES C CXX)
endif()
```

`APPLE` устанавливается **внутри** `project()`. До первого его вызова переменная пуста, и на macOS
условие уходит в `else()` — Objective-C++ не включается.

Коварство в том, что сборка при этом может пройти. Файлы `.mm` CMake отдаёт компилятору C++, а
clang сам определяет Objective-C++ по расширению, так что на AppleClang всё скомпилируется — по
случайности, а не потому что настроено. Именно так этот проект и жил какое-то время. Ломается это
позже и не там: у языка нет своих флагов, `CMAKE_OBJCXX_FLAGS` ни на что не влияет, настройки ARC
и стандарта задаются не тому языку, а на другом компиляторе или в другом генераторе `.mm` просто
не соберётся.

`enable_language(OBJCXX)` делает то же самое, но после `project()`, когда `APPLE` уже известна, — и
тогда это настроено, а не совпало. На Windows строка не исполняется.

### `set(CMAKE_CXX_STANDARD 20)` и рядом

`CMAKE_CXX_STANDARD_REQUIRED ON` превращает стандарт из пожелания в требование: без него CMake
молча соберёт кодом C++17, если компилятор не умеет 20, и вы узнаете об этом по странной ошибке в
`std::span`.

`CMAKE_CXX_EXTENSIONS OFF` выключает `-std=gnu++20` в пользу `-std=c++20`. Смысл — не собрать
случайно код, который компилируется только у вас.

## 0.4. Разбор: подключение обёртки

### `set(DMRENDER_DIR … CACHE PATH …)`

Объявляет **кешируемую** переменную: она попадает в `CMakeCache.txt`, видна в GUI и переопределяется
из командной строки.

```sh
cmake -S . -B build -DDMRENDER_DIR=/opt/src/dmwrapper
```

`CACHE PATH` вместо обычного `set()` — чтобы значение переопределялось снаружи. Без `CACHE`
переменная локальна для конфигурации, и флаг `-D` её не изменит.

Значение по умолчанию `../dmwrapper` предполагает, что оба репозитория лежат рядом. В
`CMakeLists.txt` просмотрщика вместо одного пути перебирается короткий список имён — `dmwrapper`,
потом `dmrender`, — чтобы результат не зависел от того, переименовали каталог при клонировании или
нет.

### `find_package(dmrender QUIET CONFIG)`

Ищет **установленную** обёртку: файл `dmrenderConfig.cmake`, который создаётся при
`cmake --install`. Находит — определяет цель `dmrender::dmrender`, и локальная копия исходников
не нужна вообще.

- `CONFIG` — искать только пакет, поставляемый самой библиотекой, и не пытаться подобрать
  `Finddmrender.cmake`. Не найдёт — сообщит об этом, а не будет угадывать.
- `QUIET` — не считать отсутствие ошибкой. Мы сами обработаем оба случая ниже.

Если обёртка установлена в нестандартный префикс, путь подсказывается так:

```sh
cmake -S . -B build -DCMAKE_PREFIX_PATH=/opt/dmrender-install
```

### `if(NOT dmrender_FOUND) add_subdirectory(…) endif()`

Резервный путь: собрать обёртку из исходников как часть нашей сборки.

Два аргумента, и второй важен. `add_subdirectory(<источник> <каталог сборки>)` — без второго
аргумента CMake попытается сложить объектные файлы обёртки внутрь её собственного дерева
исходников (потому что оно вне нашего), и откажется. `"${CMAKE_BINARY_DIR}/dmrender"` даёт им
место в нашем `build/`.

Разница между двумя ветками важна не только для сборки:

| | `find_package` (установлена) | `add_subdirectory` (исходники) |
|---|---|---|
| `dmrender::dmrender` | есть | есть |
| цели `glfw`, `imgui` | **нет** | есть |
| правка кода обёртки | нет | да, пересобирается вместе с приложением |
| выбор бэкенда | зафиксирован при установке | при каждой конфигурации |

Во второй строке — практическое следствие. Обёртка собирает GLFW и ImGui для себя, и в сборке из
исходников их цели становятся доступны и приложению. У установленной библиотеки их нет, и GLFW с
ImGui нужно принести самому. Поэтому `add_subdirectory` — обычный режим работы, а `find_package` —
для случая, когда обёртка стабильна и лежит в системе.

### Что можно передать обёртке

Переменные ставятся **до** `add_subdirectory`:

```cmake
set(DMRENDER_VALIDATION ON CACHE BOOL "" FORCE)   # слой валидации Vulkan
add_subdirectory("${DMRENDER_DIR}" "${CMAKE_BINARY_DIR}/dmrender")
```

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `DMRENDER_VALIDATION` | `OFF` | слой валидации Vulkan: ловит неверное использование API ценой скорости |
| `DMRENDER_GLFW_DIR` | `external/glfw` | своя копия GLFW вместо подмодуля |
| `DMRENDER_IMGUI_DIR` | `external/imgui` | своя копия Dear ImGui |
| `DMRENDER_BUILD_SAMPLES` | `OFF` | примеры библиотеки |

Валидацию стоит включить на всё время работы над главами 2–5 и выключить перед замерами. Она
находит ровно тот класс ошибок, который иначе выглядит как «иногда мигает».

### Если GLFW и ImGui уже есть у вас

Обёртка создаёт эти цели только если их ещё нет:

```cmake
if(NOT TARGET glfw)
    add_subdirectory(...)
endif()
```

Значит, порядок в вашем `CMakeLists.txt` определяет, чья копия используется. Добавите свой GLFW
раньше — обёртка возьмёт ваш.

Проверка существует не для удобства. Определить в одной сборке две цели с одним именем — сразу
ошибка CMake, и это лучший из исходов. Хуже, если две копии ImGui попадут в сборку под разными
именами целей: у ImGui глобальный контекст, и тогда их станет два — приложение будет писать в
свой, обёртка рисовать из своего, и совпадать они перестанут. Одна сборка GLFW и одна сборка ImGui
на процесс.

## 0.5. Разбор: цель приложения

### `add_executable(MyRenderer main.cpp)`

Ничего особенного, кроме одного: `.mm`-файлы в этот список **не нужны**. Весь Objective-C++ —
внутри обёртки. Приложение остаётся чистым C++ на обеих платформах.

### `target_link_libraries(… PRIVATE dmrender::dmrender glfw imgui)`

`dmrender::dmrender` — имя с двойным двоеточием, значит **импортированная цель**. Помимо самой
библиотеки она приносит с собой:

- пути включения `render_pipeline/` — поэтому `#include "Device.hpp"` работает без указания путей
  в вашем файле;
- зависимости для компоновки: `Vulkan::Vulkan` или фреймворки Apple;
- требования к стандарту языка.

Практический смысл: **у приложения нет ни одной строки про Vulkan или Metal.** Ни путей, ни
`find_package(Vulkan)`, ни `-framework Metal`. Всё это — свойства цели обёртки, и они
распространяются автоматически.

`glfw` и `imgui` перечислены отдельно, хотя обёртка их уже использует. Причина не в компоновке, а в
честности: приложение обращается к ним **напрямую** — само создаёт окно и рисует свой интерфейс, —
поэтому объявляет их своими зависимостями, а не полагается на то, что они просочатся из обёртки.
Публичные заголовки обёртки не подключают ни `glfw3.h`, ни `imgui.h`: `GLFWwindow` в них объявлен
вперёд (`struct GLFWwindow;`).

`PRIVATE` — потому что `MyRenderer` исполняемый файл, и никто не «наследует» его зависимости.

## 0.6. Шейдеры: единственное место, где платформы расходятся

Metal компилирует `.metal` в рантайме. Vulkan так не умеет — GLSL надо превратить в SPIR-V заранее.
Обёртка это скрывает: вызов один и тот же на обеих платформах,

```cpp
helper::createShaderFunction(device, SHADER_DIR "/Mesh", "mesh_vertex_shader");
```

но артефакты обязаны лежать там, где их ищут:

```
macOS:    ${SHADER_DIR}/Mesh.metal                            ← исходник, точка входа по имени
Windows:  ${SHADER_DIR}/Mesh.mesh_vertex_shader.spv           ← отдельный модуль на точку входа
```

Отсюда — соглашение об именах `<стем>.<имя функции>.spv`, и вся возня в CMake ниже существует
только чтобы его соблюсти.

```cmake
if(APPLE)
    set(SHADER_DIR "${CMAKE_CURRENT_SOURCE_DIR}/shaders/metal")
else()
    set(SHADER_DIR "${CMAKE_BINARY_DIR}/shaders")
endif()
target_compile_definitions(MyRenderer PRIVATE SHADER_DIR="${SHADER_DIR}")
```

На macOS путь указывает на **исходники**: они используются на месте. На Windows — на **вывод
сборки**, потому что там лежат скомпилированные `.spv`. `target_compile_definitions` вместо
глобального `add_compile_definitions` — потому что это свойство приложения, а не всего дерева;
обёртка пути к шейдерам принимает аргументом и про `SHADER_DIR` ничего не знает.

Компиляция на Windows:

```cmake
if(NOT APPLE)
    find_program(GLSLC_EXECUTABLE NAMES glslc glslc.exe
            HINTS "$ENV{VULKAN_SDK}/Bin" "$ENV{VULKAN_SDK}/bin")
    if(NOT GLSLC_EXECUTABLE)
        message(FATAL_ERROR "glslc не найден. Установите Vulkan SDK или задайте VULKAN_SDK.")
    endif()

    add_custom_command(
            OUTPUT  "${SHADER_DIR}/Mesh.mesh_vertex_shader.spv"
            COMMAND ${CMAKE_COMMAND} -E make_directory "${SHADER_DIR}"
            COMMAND "${GLSLC_EXECUTABLE}" --target-env=vulkan1.2
                    -o "${SHADER_DIR}/Mesh.mesh_vertex_shader.spv"
                    "${CMAKE_CURRENT_SOURCE_DIR}/shaders/glsl/Mesh.vert"
            DEPENDS "${CMAKE_CURRENT_SOURCE_DIR}/shaders/glsl/Mesh.vert"
            VERBATIM)

    add_custom_target(Shaders DEPENDS "${SHADER_DIR}/Mesh.mesh_vertex_shader.spv")
    add_dependencies(MyRenderer Shaders)
endif()
```

Здесь важны четыре вещи, и каждая из них — способ потерять время:

- **`DEPENDS` на исходник.** Без него правка шейдера не вызывает перекомпиляцию: вы меняете GLSL,
  собираете, ничего не меняется на экране, и ищете ошибку в шейдере, которого GPU не видел.
- **`OUTPUT` — то, за чем следит CMake.** Правило исполняется, когда файла нет или он старше
  зависимости, и только тогда.
- **`add_dependencies`, а не просто `add_custom_target`.** Отдельная цель сама по себе в сборку не
  входит; связь говорит, что шейдеры собираются раньше приложения.
- **`VERBATIM`.** Аргументы экранируются по правилам платформы. Первый же путь с пробелом — а
  `C:/Program Files/` встречается — без него разъедется.

Одну точку входа удобно компилировать дважды с разными определениями: вариант с альфа-тестом
отличается одной строкой, и держать два почти одинаковых файла синхронными руками — верный способ
их однажды рассинхронизировать.

```cmake
"${GLSLC_EXECUTABLE}" --target-env=vulkan1.2 -DALPHA_TEST=1
        -o "${SHADER_DIR}/Mesh.mesh_fragment_masked.spv"
        "${CMAKE_CURRENT_SOURCE_DIR}/shaders/glsl/Mesh.frag"
```

Полный вариант с таблицей шейдеров и циклом — в `CMakeLists.txt` просмотрщика.

## 0.7. Проверка сборки

```sh
cmake -S . -B build
cmake --build build --config Debug
```

В выводе конфигурации обёртка сообщает, какой бэкенд выбрала:

```
-- dmrender: Vulkan backend
-- Configuring done
-- Generating done
```

на macOS — `Metal backend`. Эта строка печатается один раз при конфигурации, и она самая полезная в
выводе: если там окажется не то, что ожидалось, дальше всё будет непонятно.

Про то, откуда взялась сама обёртка, минимальный файл не сообщает — обе ветки `find_package` /
`add_subdirectory` молчаливы. Стоит добавить строку, потому что перепутать установленную копию с
локальной легко, а последствия неочевидны:

```cmake
find_package(dmrender QUIET CONFIG)
if(dmrender_FOUND)
    message(STATUS "Using installed dmrender ${dmrender_VERSION}")
else()
    message(STATUS "Using dmrender from source: ${DMRENDER_DIR}")
    add_subdirectory("${DMRENDER_DIR}" "${CMAKE_BINARY_DIR}/dmrender")
endif()
```

## 0.8. Первый кадр: очищенный экран

Теперь про рендеринг. Цель — не треугольник (это глава 2), а более скромная и более важная вещь:
**замкнутый цикл кадра**. Окно, свопчейн, проход, который ничего не рисует, показ. Как только это
работает, треугольник — это добавить пайплайн и один вызов.

Порядок создания не произволен, и в главе 2 он разобран подробно. Здесь достаточно одного правила:
**поверхность создаётся раньше устройства**, потому что выбор физической видеокарты зависит от
того, умеет ли она рисовать в эту поверхность.

```cpp
#include <GLFW/glfw3.h>
#include "RenderHelper.hpp"

using namespace dmrender;

constexpr ImageFormat kColorFormat = ImageFormat::BGRA8_UNORM;

int main()
{
    if (!glfwInit()) return 1;

    // Ни Vulkan, ни Metal не хотят контекста OpenGL, который GLFW создаёт по умолчанию.
    glfwWindowHint(GLFW_CLIENT_API, GLFW_NO_API);
    GLFWwindow* window = glfwCreateWindow(1280, 720, "My Renderer", nullptr, nullptr);
    if (!window) { glfwTerminate(); return 1; }

    // 1. Поверхность — раньше устройства.
    auto surface = helper::createSurface(window, kColorFormat);
    // 2. Устройство, выбранное с учётом того, что оно должно уметь рисовать в эту поверхность.
    auto device = helper::createDefaultDevice(surface);
    // 3. Очередь: канал, по которому командные буферы уходят на исполнение.
    auto queue = helper::createCommandQueue(device);
    // 4. Свопчейн: изображения, которые по очереди показываются на экране.
    auto swapChain = helper::createSwapChain(device, queue, surface, 1280, 720);

    while (!glfwWindowShouldClose(window)) {
        glfwPollEvents();

        // Кадр начинается с получения изображения. Может не получиться — окно свёрнуто,
        // идёт изменение размера. Это нормальное состояние, а не ошибка.
        std::shared_ptr<GImage> target = swapChain->acquireNextImage();
        if (!target) continue;

        auto cmd = helper::createCommandBuffer(queue);

        // Проход без единого вызова отрисовки. Всё, что он делает, — очищает цель.
        auto pass = helper::createRenderPassDescriptor();
        ClearValue clear{};
        clear.color[0] = 0.16f;  clear.color[1] = 0.20f;
        clear.color[2] = 0.28f;  clear.color[3] = 1.0f;
        pass->setColorAttachment(0, target, /*clear=*/true, clear);

        cmd->beginRenderPass(pass);
        // Здесь в главе 2 появится setRenderPipeline + draw.
        cmd->endRenderPass();

        cmd->present(target);
        cmd->commit();
    }

    glfwDestroyWindow(window);
    glfwTerminate();
    return 0;
}
```

Синевато-серое окно — правильный результат. Ни одной строки, специфичной для платформы: тот же файл
собирается через Vulkan на Windows и через Metal на macOS.

Двадцать строк CMake из 0.2 и этот файл — полный проект. Он собран и запущен ровно в таком виде,
без единого дополнительного заголовка и без правок.

### Что здесь стоит заметить

**`GLFW_NO_API`.** Без этой подсказки GLFW создаст контекст OpenGL, который никому не нужен и на
macOS помешает слою Metal.

**`acquireNextImage()` возвращает `nullptr` штатно.** Свёрнутое окно, изменение размера — кадра
просто нет. Обрабатывать это как ошибку значит падать при сворачивании.

**Проход, который ничего не рисует, — не пустая операция.** Он очищает изображение, а на тайловой
архитектуре Apple ещё и определяет, надо ли вообще загружать содержимое тайла из памяти. Очистка
дешевле загрузки, и глава 1 объясняет, почему.

**`present()` до `commit()`.** `present` записывает показ **в командный буфер**, а не выполняет его;
`commit` отправляет всё на исполнение. Наоборот — показ никогда не произойдёт.

**Изменение размера** здесь не обработано, чтобы не загромождать пример. Один вызов
`swapChain->recreate(w, h)` из колбэка GLFW; разбор — в разделе 2.10.

## 0.9. Что обычно ломается

| Симптом | Причина |
|---|---|
| CMake: `dmrender not found` | обёртка не рядом; задайте `-DDMRENDER_DIR=…` |
| CMake: `FATAL_ERROR` про пустой `external/glfw` | забыт `--recurse-submodules` |
| Не найден `glfw3.h` при сборке обёртки | то же самое, подмодули не инициализированы |
| Ошибки компиляции в `.mm` на macOS | `enable_language(OBJCXX)` вызван до `project()` или не вызван |
| `glslc` не найден | нет Vulkan SDK или не задана `VULKAN_SDK` |
| Шейдер правится, картинка не меняется | нет `DEPENDS` на исходник в `add_custom_command` |
| Интерфейс не реагирует на мышь | две копии ImGui: свою цель надо объявить **до** `add_subdirectory` обёртки |
| Пустое чёрное окно, ошибок нет | забыт `commit()`, либо `present()` после него |
| Падение при сворачивании окна | `nullptr` из `acquireNextImage()` не обработан |
| Ссылка на `VkDevice` не компилируется в приложении | так и задумано: бэкенды приватны |

## 0.10. Проверка

Прежде чем идти дальше:

1. `cmake -S . -B build` печатает ожидаемый бэкенд.
2. Сборка проходит без предупреждений о стандарте языка.
3. Окно открывается и закрашивается выбранным цветом.
4. Изменение цвета в `ClearValue` видно после пересборки.
5. На Windows: включите `DMRENDER_VALIDATION=ON` и убедитесь, что консоль чиста.

Пятый пункт стоит отдельного упоминания. Чистая консоль на очищенном экране — это база, от которой
считаются все последующие сообщения валидатора. Если что-то шумит уже здесь, то в главе 8, где
проходов станет шесть, разбираться будет нечем.

## Итог

Проект подключает обёртку одной строкой `add_subdirectory` (или `find_package`, если она
установлена) и одной строкой `target_link_libraries`. Всё остальное в `CMakeLists.txt` — про
шейдеры, и это единственное место, где Windows и macOS расходятся.

Приложение не знает, какой графический API под ним. Это проверяемое утверждение, а не заявление о
намерениях: заголовки бэкендов приватны, и попытка обратиться к ним не компилируется.

Каркас из 0.8 — окно, поверхность, устройство, очередь, свопчейн, цикл с проходом и показом — до
конца книги не изменится. Всё дальнейшее добавляется внутрь.
