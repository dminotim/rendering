# Часть II. Треугольник

> **Цель главы.** Довести до экрана первый треугольник и разобрать каждый вызов — не как
> заклинание, а как конкретное действие в конвейере из главы 1. К концу главы будет работающий
> каркас приложения, в который дальше добавляется всё остальное, и полное понимание модели

> ломается.

---

## 2.1. Что вообще должно произойти

Прежде чем писать код, зафиксируем цепочку. Чтобы на экране появился треугольник, нужно:

1. **Окно** и связанная с ним **поверхность** — то, куда операционная система разрешает рисовать.
2. **Устройство** — логическое соединение с видеокартой, через которое создаются ресурсы.
3. **Очередь команд** — канал, по которому командные буферы уходят на исполнение.
4. **Свопчейн** — набор изображений, которые по очереди показываются на экране.
5. **Шейдеры**, скомпилированные в машинный код GPU.
6. **Пайплайн** — объект, в котором «запечены» шейдеры и всё фиксированное состояние.
7. **Проход рендеринга** — описание того, куда пишем и что делаем с содержимым в начале и конце.
8. **Буфер вершин** — геометрия.
9. Собственно **вызов отрисовки**, и **показ** результата.

Порядок не произволен. Поверхность создаётся **до** устройства, потому что выбор физической
видеокарты зависит от того, умеет ли она рисовать в эту поверхность (на ноутбуке с двумя GPU это
не формальность). Свопчейн создаётся после очереди, потому что показ кадра — это операция в
очереди.

## 2.2. Каркас приложения

Весь код главы живёт в одной функции. Начнём с обвязки — она не изменится до конца книги.

```cpp
#include <GLFW/glfw3.h>
#include "RenderHelper.hpp"

using namespace dmrender;

// Формат цветовой цели. Должен совпадать с тем, что просит поверхность.
constexpr ImageFormat kColorFormat = ImageFormat::BGRA8_UNORM;

void FramebufferSizeCallback(GLFWwindow* window, int width, int height)
{
    auto* chain = static_cast<std::shared_ptr<SwapChain>*>(glfwGetWindowUserPointer(window));
    if (*chain) {
        (*chain)->recreate(width, height);
    }
}

void run()
{
    if (!glfwInit()) return;

    // GLFW не должен создавать контекст OpenGL — рисовать будем сами.
    glfwWindowHint(GLFW_CLIENT_API, GLFW_NO_API);
    GLFWwindow* window = glfwCreateWindow(1280, 720, "Triangle", nullptr, nullptr);
    if (!window) { glfwTerminate(); return; }

    // 1. Поверхность — до устройства.
    std::shared_ptr<Surface> surface = helper::createSurface(window, kColorFormat);

    // 2. Устройство выбирается с учётом того, что оно должно уметь рисовать в surface.
    std::shared_ptr<Device> device = helper::createDefaultDevice(surface);

    // 3. Очередь.
    std::shared_ptr<CommandQueue> queue = helper::createCommandQueue(device);

    // 4. Свопчейн. Размер берём в пикселях кадрового буфера, а не в логических точках окна:
    //    на Retina-экране они различаются вдвое.
    int fbWidth = 0, fbHeight = 0;
    glfwGetFramebufferSize(window, &fbWidth, &fbHeight);
    std::shared_ptr<SwapChain> swapChain =
        helper::createSwapChain(device, queue, surface, fbWidth, fbHeight);

    glfwSetWindowUserPointer(window, &swapChain);
    glfwSetFramebufferSizeCallback(window, FramebufferSizeCallback);

    // ... создание ресурсов главы ...

    while (!glfwWindowShouldClose(window)) {
        glfwPollEvents();
        // ... кадр ...
    }

    glfwDestroyWindow(window);
    glfwTerminate();
}
```

Про `glfwGetFramebufferSize` стоит сказать отдельно, потому что на этом спотыкаются почти все,
кто пишет на Mac. `glfwGetWindowSize` возвращает логический размер в точках; на дисплее Retina
кадровый буфер вдвое больше. Если создать свопчейн по размеру окна, картинка будет занимать
четверть экрана. Всегда `glfwGetFramebufferSize`.

## 2.3. Модель привязок: главное, что надо запомнить

Здесь наша обёртка отличается от того, к чему приучают уроки по Vulkan, и отличается осознанно.
Разберём подробно — почти все ошибки следующих глав будут родом отсюда.

### Геометрия читается как массив, а не как атрибуты

В классическом конвейере вершинный шейдер получает атрибуты (`position`, `normal`, `uv`) через
описание раскладки вершин, которое задаётся при создании пайплайна. Наша обёртка так **не
делает**. Вместо этого вершинный шейдер получает **указатель на массив структур** и сам
индексируется по номеру вершины:

```metal
vertex VertexOut my_vertex(const device Vertex* vertices [[buffer(0)]],
                           uint vid [[vertex_id]])
{
    Vertex v = vertices[vid];
    ...
}
```

Это модель Metal, перенесённая на Vulkan (там это storage-буфер, читаемый по `gl_VertexIndex`).
Плюс: не нужно описывать раскладку вершин в C++ вообще, и добавление поля в вершину не требует
трогать код создания пайплайна. Минус: раскладка теперь живёт **в шейдере**, и C++-структура
обязана совпадать с ней **побайтово**. Про это — раздел 2.6.

Индексный буфер при этом самый обычный: `drawIndexed()` подставляет значение из него в
`vertex_id`, а кеш пост-трансформации из главы 1 работает как всегда.

### Таблица слотов

Это правила, а не рекомендации. Нарушение даёт либо ошибку слоя валидации на Windows, либо
молчаливо неверную картинку.

| Вызов C++ | Диапазон слота | Что это на бэкенде | Как объявляется в MSL |
|---|---|---|---|
| `setVertexBuffer(0, buf)` | **только 0** | storage-буфер, **виден только вершинному шейдеру** | `const device T* p [[buffer(0)]]` |
| `setUniformBuffer(s, stage, buf)` | **1…7** | uniform-буфер, виден обеим стадиям | `constant T& u [[buffer(s)]]` |
| `setTexture(s, stage, img, smp)` | 0…7 | текстура + сэмплер, обе стадии | `texture2d<float> t [[texture(s)]]`, `sampler s [[sampler(s)]]` |
| `setPushConstants(stage, p, n)` | — | ≤ 128 байт прямо в поток команд | `constant T& c [[buffer(8)]]` |

Четыре следствия, каждое из которых кого-нибудь да укусит:

**Storage-буфер ровно один, и он в слоте 0.** Нельзя положить матрицы инстансов вторым
storage-буфером — в раскладке дескрипторов слоты 1…7 объявлены как uniform. Попытка вызвать
`setVertexBuffer(2, …)` запишет дескриптор не того типа. Для больших массивов данных придётся
использовать uniform-буферы, а они ограничены (раздел 2.7). Это реальное ограничение обёртки; в
главе 13 сказано, как его снять.

**Слоты буферов и слоты текстур — независимые пространства.** `[[buffer(0)]]` и `[[texture(0)]]`
не конфликтуют.

**Слот текстуры и слот сэмплера всегда одинаковые.** `setTexture(2, …)` означает
`[[texture(2)]]` и `[[sampler(2)]]`. Разнести их нельзя.

**Push-константы занимают `[[buffer(8)]]`.** Не используйте восьмой слот ни для чего другого.
Именно поэтому uniform-буферы ограничены семёркой.

### Про стадии

На Metal привязки устанавливаются раздельно для вершинной и фрагментной стадии, на Vulkan один
дескриптор покрывает обе. Обёртка сглаживает это так: **вызывайте для каждой стадии, которая
читает данные**. На Vulkan второй вызов окажется идемпотентным, на Metal он обязателен.

```cpp
buffer->setPushConstants(ShaderStage::Vertex,   &constants, sizeof(constants));
buffer->setPushConstants(ShaderStage::Fragment, &constants, sizeof(constants));
```

Забытый второй вызов — классическая ошибка, которая **работает на Windows и ломается на Mac**.
Симптом: фрагментный шейдер читает мусор, цвет случайный или чёрный.

## 2.4. Шейдер

Файл `shaders/metal/Triangle.metal`:

```metal
#include <metal_stdlib>
using namespace metal;

// Раскладка вершины. Обязана совпадать со структурой в C++ побайтово.
// packed_float3 — ровно 12 байт, без выравнивания до 16. Обычный float3 занял бы 16.
struct Vertex {
    packed_float3 position;
    packed_float3 color;
};

// Push-константы: до 128 байт, всегда в buffer(8).
struct Constants {
    float4x4 transform;
    float4   tint;
};

struct VertexOut {
    float4 clipPosition [[position]];   // обязателен: это выход в clip-пространство
    float3 color;                       // произвольный атрибут, будет интерполирован
};

vertex VertexOut triangle_vertex(const device Vertex* vertices [[buffer(0)]],
                                 constant Constants&  constants [[buffer(8)]],
                                 uint                 vid       [[vertex_id]])
{
    // ВНИМАНИЕ: имя `vertex` использовать нельзя — это квалификатор функции в MSL.
    Vertex v = vertices[vid];

    VertexOut out;
    out.clipPosition = constants.transform * float4(float3(v.position), 1.0);
    out.color = float3(v.color);
    return out;
}

fragment float4 triangle_fragment(VertexOut in [[stage_in]],
                                  constant Constants& constants [[buffer(8)]])
{
    return float4(in.color * constants.tint.rgb, 1.0);
}
```

Разбор квалификаторов — по одному, потому что каждый что-то значит физически:

`[[buffer(0)]]` — номер слота из таблицы выше. `const device T*` означает «указатель в память
устройства, только чтение». `device` — это адресное пространство: память, доступная всем нитям и
достаточно большая. Есть ещё `constant` — небольшая область, оптимизированная под то, что **все
нити читают один и тот же адрес**. Для массива, индексируемого по номеру вершины, нужен `device`;
для одинаковых для всех констант — `constant`. Перепутать местами — значит потерять
производительность на ровном месте.

`[[vertex_id]]` — номер вершины. Для `draw()` это просто счётчик, для `drawIndexed()` — значение
из индексного буфера.

`[[position]]` в структуре выхода — обязательный атрибут: именно эту величину растеризатор
использует для определения покрытия. Она в **clip-пространстве**, до деления на `w`. Деление
аппаратура сделает сама.

`[[stage_in]]` — «эти поля пришли с предыдущей стадии и уже интерполированы». Интерполяция —
фиксированная функция и идёт с коррекцией перспективы: то, что для растеризатора линейно в
экранных координатах, для нас нелинейно вдоль треугольника, и аппаратура это учитывает.

### Системы координат

Обёртка выравнивает конвенции между бэкендами, поэтому одно правило действует везде:

- **Clip-пространство:** +X вправо, **+Y вверх**, Z в диапазоне [0, 1].
- **Координаты фрагмента** (`[[position]]` во фрагментном шейдере): пиксели, начало в **верхнем
  левом** углу.
- **Текстурные координаты:** (0,0) — **верхний левый** тексель.

Из первого и третьего следует, что перевод clip-позиции в текстурную координату всегда
инвертирует Y:

```metal
float2 uv = float2(clip.x * 0.5 + 0.5, 0.5 - clip.y * 0.5);
```

Запомните эту строчку — она понадобится в каждом полноэкранном проходе, начиная с главы 7.

## 2.5. Сборка шейдера

На Metal шейдер компилируется **во время выполнения** из исходника. Обёртка ищет файл, добавляя
расширение `.metal`, если его нет:

```cpp
const std::filesystem::path shaderPath = std::filesystem::path(SHADER_DIR) / "Triangle";

std::shared_ptr<ShaderFunction> vertexFn =
    helper::createShaderFunction(device, shaderPath, "triangle_vertex");
std::shared_ptr<ShaderFunction> fragmentFn =
    helper::createShaderFunction(device, shaderPath, "triangle_fragment");
```

Второй аргумент — путь **без расширения**, третий — имя точки входа.

Практическое последствие компиляции во время выполнения: **ошибка в шейдере не ломает сборку
проекта**. Она проявится при запуске, сообщением вида

```
Shader compilation error: program_source:40:19: error: expected unqualified-id
```

`program_source` — это и есть признак того, что компилируется строка, а не файл; номер строки
относится к исходнику шейдера. Всегда проверяйте, что `createShaderFunction` не вернул `nullptr`
— иначе `createPipeline` упадёт позже и в менее понятном месте.

## 2.6. Геометрия

Структура в C++ обязана совпадать с той, что в шейдере:

```cpp
struct Vertex {
    float position[3];
    float color[3];
};
static_assert(sizeof(Vertex) == 24, "должно совпадать с packed-раскладкой в шейдере");

const Vertex vertices[] = {
    { {  0.0f,  0.6f, 0.0f }, { 1.0f, 0.2f, 0.2f } },
    { { -0.6f, -0.4f, 0.0f }, { 0.2f, 1.0f, 0.2f } },
    { {  0.6f, -0.4f, 0.0f }, { 0.2f, 0.2f, 1.0f } },
};

std::shared_ptr<GBuffer> vertexBuffer = device->createBuffer(
    BufferType::Vertex, BufferUsage::Static,
    sizeof(vertices), vertices, "TriangleVertices");
```

`BufferUsage::Static` означает «записали один раз, читаем каждый кадр». Обёртка положит буфер в
видеопамять и зальёт данные через промежуточный буфер. `Dynamic` — для того, что меняется каждый
кадр; такой буфер живёт в памяти, видимой процессору, и `update()` для него — обычный `memcpy`.

### Про выравнивание — самая частая ошибка книги

`packed_float3` в MSL занимает 12 байт. Обычный `float3` — **16**, потому что векторы в шейдерных
языках выровнены по своему размеру, округлённому вверх до степени двойки. Если объявить в шейдере

```metal
struct Vertex {
    float3 position;   // смещение 0, размер 16 (!)
    float3 color;      // смещение 16
};                     // итого 32 байта
```

а в C++ оставить структуру на 24 байта, шейдер начнёт читать цвет из позиции следующей вершины.
Картинка получится «взорванной» или скошенной — характерный симптом, который стоит научиться
узнавать сразу.

Два надёжных способа не попасться:

1. **`packed_*` типы** — как в примере выше. Точное соответствие, никакого невидимого дополнения.
2. **Явное дополнение до кратности 16** — как сделано в `MeshVertex` нашего проекта: три поля
   `float3` превращаются в 48 байт с полями-заполнителями. Чуть больше памяти, зато раскладка
   совпадает с правилами и для storage-буферов Vulkan.

Второй способ надёжнее, если шейдер должен работать на обоих бэкендах, и именно поэтому
`mesh/Mesh.hpp` устроен так:

```cpp
struct MeshVertex {
    float position[3];
    float pad0 = 0.0f;
    float normal[3];
    float pad1 = 0.0f;
    float uv[2];
    float pad2[2] = { 0.0f, 0.0f };
};
static_assert(sizeof(MeshVertex) == 48, "");
```

Всегда пишите `static_assert` на размер. Он ловит ошибку в момент компиляции, а не после часа
разглядывания странной картинки.

## 2.7. Push-константы против uniform-буферов

Раз уж мы объявили `Constants` в шейдере, надо решить, как их передавать. Вариантов два, и выбор
между ними — не вкусовщина.

**Push-константы.** Байты кладутся прямо в поток команд. Ни выделения памяти, ни дескриптора, ни
синхронизации между кадрами. Ограничение — **128 байт**, и это гарантированный минимум, на
который обёртка сознательно опирается. Хватает ровно на матрицу 4×4 (64 байта) плюс четыре
`float4`.

**Uniform-буфер.** Обычный буфер, привязанный к слоту 1…7. Ограничение по размеру гораздо мягче
— гарантированный минимум спецификации Vulkan составляет 16 КиБ, на реальных настольных
драйверах 64 КиБ. Но за это платим: буфер надо создать, обновлять и следить за тем, чтобы не
переписать данные, которые GPU ещё читает.

Правило, которым будем пользоваться всю книгу:

> **Push-константы — для того, что меняется от вызова к вызову.** Матрица объекта, индекс
> материала, цветовой оттенок.
>
> **Uniform-буфер — для того, что общее на весь проход.** Матрицы камеры, список источников
> света, параметры тонмаппинга.

Разница практическая: 500 объектов с push-константами — это 500 записей по 128 байт в поток
команд, и никакой синхронизации. Те же 500 объектов через uniform-буфер потребуют либо 500
буферов, либо одного большого со смещениями, либо 500 перезаписей одного буфера — а последнее
просто не работает, потому что GPU ещё не дочитал предыдущее значение.

Для нашего треугольника:

```cpp
struct Constants {
    float transform[16];
    float tint[4];
};
static_assert(sizeof(Constants) <= kMaxPushConstantBytes, "не влезает в push-константы");
```

80 байт из 128 — с запасом.

## 2.8. Пайплайн

```cpp
PipelineDesc desc{};
desc.vertexFunction   = vertexFn;
desc.fragmentFunction = fragmentFn;
desc.targetFormat     = RenderTargetFormat::singleTarget(kColorFormat);
desc.rasterizer.cullMode = CullMode::None;   // пока не заботимся о порядке обхода
desc.debugName = "TrianglePipeline";

std::shared_ptr<Pipeline> pipeline = helper::createPipeline(device, desc);
```

`RenderTargetFormat` — это **контракт**. Он должен совпадать с проходом рендеринга по трём
пунктам одновременно:

1. Число цветовых целей = число вложений в проходе = число выходов фрагментного шейдера.
2. Форматы совпадают.
3. Число выборок (`sampleCount`) совпадает.

Несовпадение любого из трёх — ошибка. Особенно коварен третий: **число выборок запечено в
пайплайн**, поэтому переключатель «MSAA вкл/выкл» в интерфейсе требует **двух заранее созданных
пайплайнов**, а не смены состояния. Так и сделано в `FastRenderer.cpp`.

Создание пайплайна — это компиляция шейдеров в машинный код GPU. Она занимает от миллисекунд до
секунд. **Никогда не создавайте пайплайн внутри цикла кадра.** Все пайплайны создаются на старте
или лениво с кешированием.

## 2.9. Кадр

```cpp
float time = 0.0f;

while (!glfwWindowShouldClose(window)) {
    glfwPollEvents();

    // 1. Забираем следующее изображение свопчейна.
    //    Здесь же происходит ожидание вертикальной синхронизации.
    std::shared_ptr<GImage> target = swapChain->acquireNextImage();
    if (!target) { continue; }        // окно свёрнуто или свопчейн устарел

    // 2. Описываем проход: одна цветовая цель, очищаем.
    std::shared_ptr<RenderPassDescriptor> pass = helper::createRenderPassDescriptor();
    ClearValue clear{};
    clear.color[0] = 0.09f; clear.color[1] = 0.10f;
    clear.color[2] = 0.12f; clear.color[3] = 1.0f;
    pass->setColorAttachment(0, target, /*clear=*/true, clear);

    // 3. Константы.
    time += 0.016f;
    Constants constants{};
    identity(constants.transform);
    rotateZ(constants.transform, time);
    constants.tint[0] = constants.tint[1] = constants.tint[2] = constants.tint[3] = 1.0f;

    // 4. Записываем команды.
    std::shared_ptr<CommandBuffer> cmd = helper::createCommandBuffer(queue);

    cmd->beginRenderPass(pass);
    cmd->setRenderPipeline(pipeline);
    cmd->setVertexBuffer(0, vertexBuffer);
    cmd->setPushConstants(ShaderStage::Vertex,   &constants, sizeof(constants));
    cmd->setPushConstants(ShaderStage::Fragment, &constants, sizeof(constants));
    cmd->draw(3);
    cmd->endRenderPass();

    // 5. Показываем и отправляем.
    cmd->present(target);
    cmd->commit();
}
```

Несколько важных замечаний по этому коду.

**`acquireNextImage()` может вернуть `nullptr`.** Так бывает при сворачивании окна и в момент
изменения размера, когда свопчейн уже устарел. Это не ошибка. Правильная реакция — пропустить
кадр через `continue`. Неправильная — продолжить и попытаться рисовать в `nullptr`.

**Именно `acquireNextImage()` ждёт вертикальной синхронизации**, а не `present()`. Это неочевидно
и будет важно в главе 10: если измерить время между началом и концом кадра, почти всё оно
окажется в этом вызове, и это нормально — GPU и монитор диктуют темп.

**`commit()` не ждёт GPU.** Он отдаёт буфер команд драйверу и возвращается. Процессор уходит
готовить следующий кадр, пока видеокарта рисует текущий.

**Порядок `present()` перед `commit()` обязателен.** `present` — это команда в потоке, а не
отдельное действие. Записать её после `commit()` невозможно.

**Не забудьте `endRenderPass()`.** Пропуск не даст осмысленной диагностики на Metal, а на Vulkan
даст лавину сообщений слоя валидации.

## 2.10. Изменение размера окна

Обработчик из каркаса вызывает `swapChain->recreate(width, height)`. Этого достаточно для самого
свопчейна, но есть тонкость, из-за которой в проекте уже был баг.

Начиная со следующей главы у нас появятся собственные цели рендеринга — буфер глубины, цели
MSAA, G-буфер. Все вложения одного прохода **обязаны быть одного размера**. И вот ключевой
момент: размер надо брать **у свопчейна, а не у окна**.

```cpp
// ПРАВИЛЬНО
const int width  = static_cast<int>(swapChain->width());
const int height = static_cast<int>(swapChain->height());

// НЕПРАВИЛЬНО — в момент изменения размера расходится со свопчейном на кадр
int width, height;
glfwGetFramebufferSize(window, &width, &height);
```

Свопчейн выбирает свой размер по возможностям поверхности, и во время перетаскивания рамки окна
он может на один кадр не совпасть с тем, что сообщает оконная система. Симптом — сообщение вида
«depth 884×561 vs framebuffer 1484×911» и падение. Всегда берите размер у свопчейна.

---

## 2.11. Что обычно ломается

| Симптом | Причина |
|---|---|
| Чёрный экран, ошибок нет | Треугольник за пределами clip-пространства, или матрица не инициализирована (нули) |
| Треугольник исчез после включения `CullMode::Back` | Порядок обхода вершин по часовой стрелке при `FrontFace::CounterClockwise` |
| Геометрия «взорвана» или скошена | Раскладка вершины в C++ и в шейдере не совпадает |
| Цвет случайный | Не вызван `setPushConstants` для фрагментной стадии |
| Работает на Windows, чёрное на Mac | То же самое: на Vulkan один дескриптор покрывает обе стадии, на Metal — нет |
| `createPipeline` падает | `createShaderFunction` вернул `nullptr`; проверьте путь и имя точки входа |
| Картинка в четверти окна на Mac | Свопчейн создан по `glfwGetWindowSize`, а не `glfwGetFramebufferSize` |
| Ошибка про несовпадение размеров при ресайзе | Цели созданы по размеру окна, а не свопчейна |
| `expected unqualified-id` в MSL | Переменная названа `vertex`, `fragment` или `kernel` — это квалификаторы |

---

## 2.12. Проверка

Три проверки, каждая из которых что-то доказывает:

1. **Треугольник видно, и он вращается.** Доказывает, что push-константы доходят до вершинного
   шейдера.
2. **Цвета интерполируются между вершинами.** Доказывает, что `[[stage_in]]` работает и что
   растеризатор интерполирует атрибуты, — то есть весь конвейер собран правильно.
3. **Поменяйте `constants.tint` на `{1, 0, 0, 1}`.** Треугольник должен стать красным. Доказывает,
   что push-константы доходят и до фрагментного шейдера. Если этот шаг не работает, а первые два
   работают — вы забыли второй вызов `setPushConstants`. Именно поэтому проверка разделена на три.

Дополнительно на Windows: запустите со слоями валидации и убедитесь, что лог пуст. Пустой лог на
этом этапе — залог того, что дальнейшие ошибки будут вашими новыми, а не накопленными.

## Итог

Собран каркас, который дальше не меняется: окно → поверхность → устройство → очередь → свопчейн,
и цикл «забрать изображение, описать проход, записать команды, показать».

Главное, что нужно унести:

1. **Геометрия читается из storage-буфера в слоте 0 по `[[vertex_id]]`.** Раскладка живёт в
   шейдере, и C++-структура обязана совпадать побайтово. `static_assert` на размер — обязателен.
2. **Слоты: 0 — storage (только вершинный), 1…7 — uniform, текстуры 0…7 отдельно,
   push-константы в `[[buffer(8)]]`.**
3. **Привязки задаются для каждой стадии отдельно.** Забытая фрагментная стадия — ошибка,
   которая проявляется только на Mac.
4. **Push-константы — на вызов, uniform-буфер — на проход.**
5. **Размеры целей берём у свопчейна.**
