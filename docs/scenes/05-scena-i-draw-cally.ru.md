# Часть V. Сцена и вызовы отрисовки

> **Цель главы.** Разобраться, что на самом деле стоит вызов отрисовки, и научиться доводить их
> число до разумного там, где сцена состоит из сотен подмножеств и тысяч объектов. Отсечение по
> пирамиде видимости, сортировка, инстансинг и непрямая отрисовка — четыре инструмента, и каждый
> решает свою задачу.

---

## 5.1. Сколько стоит вызов отрисовки

Вопрос сформулирован неточно, и в этом корень большинства заблуждений. Вызов отрисовки стоит
**двух разных вещей одновременно**, и упереться можно в любую.

### Стоимость на процессоре

`drawIndexed()` — это запись команды в буфер. Плюс всё, что предшествовало: проверка изменившихся
привязок, обновление дескрипторов, запись push-констант. В нашей обёртке это порядка сотен
наносекунд на вызов при неизменном состоянии и заметно больше при смене привязок — там появляется
поиск в кеше дескрипторов и, при промахе, выделение нового набора.

Порядок величины: **несколько тысяч вызовов на кадр** проходят незаметно, **десятки тысяч**
съедают целый кадр процессорного времени. Sponza с её 25 материалами — это ничто. San Miguel с
сотнями подмножеств — всё ещё немного. Лес из 10 000 отдельных деревьев — уже проблема.

### Стоимость на видеокарте

Здесь дело не в самом вызове, а в **смене состояния**. Конвейер GPU глубокий: пока
растеризуются последние треугольники предыдущего вызова, вершинный шейдер уже обрабатывает
следующие. Смена пайплайна эту конвейеризацию прерывает — новое состояние нельзя применить, пока
старое не отработало.

Отсюда иерархия стоимости, от дорогого к дешёвому:

| Что меняем | Относительная стоимость | Почему |
|---|---|---|
| Пайплайн (`setRenderPipeline`) | самое дорогое | Полный барьер состояния |
| Проход рендеринга (`beginRenderPass`) | ещё дороже | На TBDR — выгрузка и загрузка тайлов |
| Текстуры (`setTexture`) | средне | Запись дескрипторов, возможно новый набор |
| Uniform-буфер | средне | То же |
| Push-константы | почти бесплатно | Байты в поток команд |
| Ничего (только `draw`) | бесплатно | |

Из этой таблицы напрямую следует стратегия сортировки.

## 5.2. Сортировка

Задача: упорядочить подмножества так, чтобы дорогие смены состояния происходили как можно реже.
Классический приём — собрать ключ сортировки, где старшие биты отвечают за самое дорогое.

```cpp
struct DrawItem {
    uint32_t subsetIndex   = 0;
    uint32_t materialIndex = 0;
    float    viewDepth     = 0.0f;   // расстояние до камеры
    bool     transparent   = false;

    uint64_t sortKey() const
    {
        // Биты, сверху вниз:
        //  63    : прозрачность — прозрачное всегда после непрозрачного
        //  62-48 : пайплайн (двусторонний, альфа-маска, обычный)
        //  47-24 : материал
        //  23-0  : глубина
        const uint64_t depthBits = static_cast<uint64_t>(
            std::clamp(viewDepth, 0.0f, 1.0f) * 16777215.0f);

        // Непрозрачное — спереди назад (ради early-Z),
        // прозрачное — сзади наперёд (ради корректности смешивания).
        const uint64_t depth = transparent ? (16777215ull - depthBits) : depthBits;

        return (static_cast<uint64_t>(transparent)   << 63)
             | (static_cast<uint64_t>(pipelineId())  << 48)
             | (static_cast<uint64_t>(materialIndex) << 24)
             |  depth;
    }
};

std::sort(items.begin(), items.end(),
          [](const DrawItem& a, const DrawItem& b) { return a.sortKey() < b.sortKey(); });
```

Смысл каждого уровня:

**Прозрачность в старшем бите.** Прозрачная геометрия обязана рисоваться после всей непрозрачной,
иначе она смешается с фоном вместо того, что за ней. Это не оптимизация, это корректность.

**Пайплайн следующий.** Самая дорогая смена состояния должна происходить реже всего.

**Материал после пайплайна.** Внутри одного пайплайна группируем по текстурам.

**Глубина в младших битах.** Внутри материала непрозрачное сортируем спереди назад: Hi-Z из главы
1 тогда отбрасывает целыми блоками, и overdraw падает почти до единицы.

Направление сортировки по глубине для прозрачного — обратное, и это единственный правильный
порядок для смешивания «поверх». Подробно в главе 9.

### Насколько это помогает

Возьмите Sponza и посчитайте число смен пайплайна за кадр до и после сортировки. Без сортировки
подмножества идут в порядке файла, и двусторонние материалы перемешаны с обычными — смен
столько же, сколько подмножеств. После сортировки — ровно столько, сколько пайплайнов, то есть
две-три.

Это стоит измерить и показать в кадре, а не принять на веру:

```cpp
struct FrameStats {
    uint32_t drawCalls        = 0;
    uint32_t pipelineChanges  = 0;
    uint32_t textureBinds     = 0;
    uint32_t trianglesSubmitted = 0;
    uint32_t subsetsCulled    = 0;
};
```

Такая структура, выведенная в ImGui, окупается стократно: почти каждая оптимизация в этой главе
проверяется её показаниями, а не ощущениями.

## 5.3. Отсечение по пирамиде видимости

Самая выгодная оптимизация из всех: работа, которая не выполняется, бесплатна абсолютно.

### Извлечение плоскостей

Шесть плоскостей пирамиды видимости извлекаются напрямую из матрицы `viewProjection` — приём
Гриба–Хартманна. Смысл: строка матрицы, сложенная со строкой `w` или вычтенная из неё, даёт
коэффициенты плоскости в мировом пространстве.

```cpp
struct Plane { float nx, ny, nz, d; };

// Матрица хранится по столбцам: m[c*4 + r].
std::array<Plane, 6> extractFrustumPlanes(const Mat4& m)
{
    auto row = [&](int r) {
        return std::array<float, 4>{ m[0 * 4 + r], m[1 * 4 + r], m[2 * 4 + r], m[3 * 4 + r] };
    };

    const auto r0 = row(0), r1 = row(1), r2 = row(2), r3 = row(3);

    auto make = [](const std::array<float, 4>& a,
                   const std::array<float, 4>& b, bool add) {
        Plane p{ add ? a[0] + b[0] : b[0] - a[0],
                 add ? a[1] + b[1] : b[1] - a[1],
                 add ? a[2] + b[2] : b[2] - a[2],
                 add ? a[3] + b[3] : b[3] - a[3] };
        // Нормируем, чтобы расстояние получалось в мировых единицах.
        const float length = std::sqrt(p.nx * p.nx + p.ny * p.ny + p.nz * p.nz);
        if (length > 1e-9f) { p.nx /= length; p.ny /= length; p.nz /= length; p.d /= length; }
        return p;
    };

    return {
        make(r0, r3, true),    // левая
        make(r0, r3, false),   // правая
        make(r1, r3, true),    // нижняя
        make(r1, r3, false),   // верхняя
        make(r2, r3, true),    // ближняя
        make(r2, r3, false),   // дальняя
    };
}
```

**Внимание при reverse-Z.** Ближняя и дальняя плоскости меняются местами: при обычном Z ближняя
получается из `r2 + r3`, при reverse-Z — из `r3 - r2`. Ошибка здесь коварна: отсекаться будет всё,
что **внутри** сцены, а видно останется то, что позади камеры. Симптом узнаваемый — геометрия
появляется, только когда отворачиваешься.

### Тест ограничивающего параллелепипеда

```cpp
struct Aabb { Vec3 min, max; };

bool insideFrustum(const std::array<Plane, 6>& planes, const Aabb& box)
{
    for (const Plane& p : planes) {
        // «Положительная вершина» — угол параллелепипеда, самый дальний
        // вдоль нормали плоскости. Если даже он снаружи, снаружи весь бокс.
        const Vec3 positive {
            p.nx >= 0.0f ? box.max.x : box.min.x,
            p.ny >= 0.0f ? box.max.y : box.min.y,
            p.nz >= 0.0f ? box.max.z : box.min.z,
        };
        if (p.nx * positive.x + p.ny * positive.y + p.nz * positive.z + p.d < 0.0f) {
            return false;
        }
    }
    return true;
}
```

Тест консервативный: он может пропустить объект, который на самом деле не виден (бокс пересекает
пирамиду, а геометрия внутри бокса — нет), но никогда не отсечёт видимый. Это ровно то, что нужно.

### Нужны границы подмножеств

Наш `Mesh` хранит границы всей модели, но не отдельных подмножеств. Для отсечения нужны именно
подмножества — иначе тест ничего не даст: Sponza целиком почти всегда в кадре.

Добавляем в `MeshSubset`:

```cpp
struct MeshSubset {
    uint32_t firstIndex = 0;
    uint32_t indexCount = 0;
    int32_t  materialIndex = -1;

    float boundsMin[3] = {  1e30f,  1e30f,  1e30f };
    float boundsMax[3] = { -1e30f, -1e30f, -1e30f };
};
```

И считаем при загрузке, одним проходом по индексам подмножества.

**Гранулярность важнее алгоритма.** Sponza целиком — один бокс, отсечение бесполезно. Sponza по
подмножествам — 25 боксов, уже лучше, но арки и колонны в одном материале, и бокс материала
«мрамор» покрывает весь атриум. Настоящий выигрыш появляется, когда подмножества дополнительно
разбиты пространственно — на сетку или на дерево. Для курса достаточно подмножеств; для San Miguel
в главе 12 добавим сетку.

### Что это даёт

```
Sponza, камера смотрит в одну арку:
    без отсечения:   25 вызовов, 262 тыс. треугольников
    по подмножествам: 18 вызовов, 190 тыс. треугольников
    по сетке 8×8×8:   6 вызовов,   41 тыс. треугольников
```

Числа зависят от ракурса; выводите их в интерфейс и наблюдайте при движении камеры — это самая
наглядная демонстрация во всём курсе.

## 5.4. Инстансинг

Когда один и тот же объект рисуется много раз с разными трансформациями, отдельный вызов на
каждый — расточительство. Инстансинг делает один вызов на все копии.

```cpp
cmd->drawIndexed(indexBuffer, IndexType::UInt32,
                 indexCount,
                 /*instanceCount*/ 1000,
                 firstIndexBytes, 0, /*firstInstance*/ 0);
```

Шейдер получает `[[instance_id]]` и по нему выбирает свою трансформацию:

```metal
struct InstanceData {
    float4x4 model;
    float4   color;
};

// Инстансы приходят uniform-буфером в слоте 1.
vertex VertexOut instanced_vertex(const device MeshVertex*  vertices  [[buffer(0)]],
                                  constant     InstanceBlock& instances [[buffer(1)]],
                                  constant     SceneBlock&    scene     [[buffer(2)]],
                                  uint vid [[vertex_id]],
                                  uint iid [[instance_id]])
{
    MeshVertex   v = vertices[vid];
    InstanceData d = instances.items[iid];

    VertexOut out;
    const float4 world = d.model * float4(float3(v.position), 1.0);
    out.clipPosition = scene.viewProjection * world;
    out.worldPosition = world.xyz;
    out.worldNormal  = (d.model * float4(float3(v.normal), 0.0)).xyz;
    out.uv           = float2(v.uv);
    out.color        = d.color;
    return out;
}
```

### Ограничение обёртки, которое здесь болит

В главе 2 мы разобрали таблицу слотов: **storage-буфер только один и только в слоте 0**, занят
вершинами. Инстансы приходится класть в uniform-буфер, а он ограничен по размеру:

- **Гарантированный минимум спецификации Vulkan — 16 КиБ.**
- На реальных настольных драйверах и на Metal — как правило 64 КиБ.

При `InstanceData` в 80 байт (матрица плюс цвет) в гарантированные 16 КиБ помещается 204
инстанса. Не 10 000.

Три способа жить с этим:

**1. Уплотнить данные инстанса.** Матрица 4×4 избыточна: нижняя строка почти всегда `(0,0,0,1)`.
Три колонки `float4` — 48 байт вместо 64. Ещё компактнее — позиция, кватернион и масштаб: 32
байта, и 512 инстансов в гарантированный минимум.

```metal
struct InstanceData {
    float4 row0, row1, row2;    // 48 байт: матрица 4×3
};

float4x4 unpackModel(InstanceData d)
{
    return float4x4(float4(d.row0.x, d.row1.x, d.row2.x, 0.0),
                    float4(d.row0.y, d.row1.y, d.row2.y, 0.0),
                    float4(d.row0.z, d.row1.z, d.row2.z, 0.0),
                    float4(d.row0.w, d.row1.w, d.row2.w, 1.0));
}
```

**2. Разбить на пакеты со смещением в буфере.** Это самое чистое решение, и оно работает потому,
что `setUniformBuffer` принимает смещение:

```cpp
constexpr uint32_t kInstancesPerBatch = 200;
// Выравнивание смещения uniform-буфера: драйвер требует кратности
// (обычно 256 байт). Берём с запасом.
constexpr size_t kBatchStride =
    ((kInstancesPerBatch * sizeof(InstanceData) + 255) / 256) * 256;

// Один большой буфер, заполненный один раз.
std::shared_ptr<GBuffer> instanceBuffer = device->createBuffer(
    BufferType::Uniform, BufferUsage::Static,
    kBatchStride * batchCount, packedData.data(), "Instances");

for (uint32_t batch = 0; batch < batchCount; ++batch) {
    const uint32_t count = std::min(kInstancesPerBatch, total - batch * kInstancesPerBatch);

    cmd->setUniformBuffer(1, ShaderStage::Vertex, instanceBuffer, batch * kBatchStride);
    cmd->drawIndexed(indexBuffer, IndexType::UInt32, indexCount, count,
                     firstIndexBytes, 0, 0);
}
```

10 000 инстансов превращаются в 50 вызовов вместо 10 000. Смена состояния между ними — только
смещение uniform-буфера, то есть самая дешёвая из возможных.

**Про выравнивание смещения.** Драйверы требуют, чтобы смещение uniform-буфера было кратно
`minUniformBufferOffsetAlignment` — обычно 256 байт, иногда 64. Обёртка это значение не сообщает,
поэтому округляем до 256 и не думаем об этом. Потери памяти на выравнивание при пакетах по 200
инстансов пренебрежимы.

**3. Расширить обёртку.** Добавить `setStorageBuffer(slot, …)` и объявить слоты 1…7 в раскладке
дескрипторов как storage. Пункт списка из главы 13; работы — на полчаса, и снимает ограничение
полностью.

### Когда инстансинг не помогает

Если объектов много, но все они разные — инстансинг неприменим по определению. Sponza именно
такая: там нет повторяющейся геометрии. Инстансинг — инструмент для растительности, толпы,
частиц, модульной архитектуры. На сценах архива он пригодится в главе 12 для листвы San Miguel,
где один и тот же лист повторяется тысячами.

## 5.5. Непрямая отрисовка

Следующий уровень: аргументы вызова читаются **самим GPU** из буфера, а процессор их даже не
видит.

```cpp
std::vector<DrawIndexedIndirectCommand> commands;
for (const MeshSubset& subset : visibleSubsets) {
    DrawIndexedIndirectCommand cmd{};
    cmd.indexCount    = subset.indexCount;
    cmd.instanceCount = 1;
    cmd.firstIndex    = subset.firstIndex;      // в ИНДЕКСАХ, не в байтах
    cmd.vertexOffset  = 0;
    cmd.firstInstance = 0;
    commands.push_back(cmd);
}

std::shared_ptr<GBuffer> argumentBuffer = device->createBuffer(
    BufferType::Indirect, BufferUsage::Dynamic,
    commands.size() * sizeof(DrawIndexedIndirectCommand),
    commands.data(), "DrawArguments");

cmd->drawIndexedIndirect(indexBuffer, IndexType::UInt32,
                         argumentBuffer, static_cast<uint32_t>(commands.size()));
```

Обратите внимание: в структуре `firstIndex` задаётся **в индексах**, а в `drawIndexed()` пятый
параметр — **в байтах**. Разные соглашения, потому что каждое повторяет соглашение соответствующего
API. Перепутать легко, результат — тот же «взрыв» геометрии.

### Что это даёт сейчас и что потом

Сегодня выигрыш умеренный: список всё равно строит процессор, экономится лишь запись команд. Один
`drawIndexedIndirect` на 500 подмножеств вместо 500 вызовов `drawIndexed` — заметно, но не
революционно.

Настоящий смысл в другом. Раз аргументы лежат в буфере, их может записать **вычислительный
шейдер**: отсечь невидимое, выбрать уровень детализации, выставить `instanceCount = 0` для
отбракованных — и процессор ни о чём не узнает. Это то, как устроен рендеринг в современных
движках, и это тот случай, когда рост числа объектов перестаёт стоить процессорного времени
вообще.

**Вычислительных шейдеров в обёртке нет** — `ShaderStage::Compute` объявлен, но не реализован. То
есть непрямая отрисовка у нас работает, но её главная возможность недоступна. Честное состояние
дел; в главе 13 оценена трудоёмкость.

Одно ограничение, о котором стоит знать: **push-константы одни на весь непрямой вызов**. Нельзя
задать разный материал каждой команде. Обход — сложить параметры материалов в uniform-буфер
массивом и передавать индекс через... а вот через что? `firstInstance` попадает в
`[[instance_id]]` как базовое значение — вот и канал. Хитро, но работает:

```cpp
cmd.firstInstance = materialIndex;   // используем как индекс материала
```

```metal
// iid == firstInstance, потому что instanceCount == 1
constant Material& m = materials.items[iid];
```

Приём стоит знать, но применять осторожно: он неочевиден и требует комментария в коде.

## 5.6. Собираем: система отрисовки

```cpp
class SceneRenderer {
public:
    void render(const std::shared_ptr<CommandBuffer>& cmd,
                const Mat4& viewProjection, const Vec3& cameraPosition)
    {
        m_stats = FrameStats{};

        // 1. Отсечение
        const auto planes = extractFrustumPlanes(viewProjection);
        m_visible.clear();
        for (uint32_t i = 0; i < m_subsets.size(); ++i) {
            if (!insideFrustum(planes, m_subsets[i].bounds)) { ++m_stats.subsetsCulled; continue; }

            DrawItem item;
            item.subsetIndex   = i;
            item.materialIndex = m_subsets[i].materialIndex;
            item.viewDepth     = distance(center(m_subsets[i].bounds), cameraPosition) / m_sceneRadius;
            item.transparent   = m_materials[item.materialIndex].transparent;
            m_visible.push_back(item);
        }

        // 2. Сортировка
        std::sort(m_visible.begin(), m_visible.end(),
                  [](const DrawItem& a, const DrawItem& b) { return a.sortKey() < b.sortKey(); });

        // 3. Отрисовка с отслеживанием состояния
        Pipeline* boundPipeline = nullptr;
        int32_t   boundMaterial = -1;

        cmd->setVertexBuffer(0, m_vertexBuffer);

        for (const DrawItem& item : m_visible) {
            const MeshMaterial& material = m_materials[item.materialIndex];
            Pipeline* wanted = pipelineFor(material);

            if (wanted != boundPipeline) {
                cmd->setRenderPipeline(sharedFor(wanted));
                boundPipeline = wanted;
                ++m_stats.pipelineChanges;
                boundMaterial = -1;      // смена пайплайна сбрасывает привязки
            }

            if (item.materialIndex != boundMaterial) {
                cmd->setTexture(0, ShaderStage::Fragment,
                                m_cache.get(material.albedoTexture), m_sampler);
                cmd->setTexture(1, ShaderStage::Fragment,
                                m_cache.get(material.alphaTexture), m_sampler);
                boundMaterial = item.materialIndex;
                m_stats.textureBinds += 2;
            }

            DrawConstants constants = makeConstants(item, viewProjection);
            cmd->setPushConstants(ShaderStage::Vertex,   &constants, sizeof(constants));
            cmd->setPushConstants(ShaderStage::Fragment, &constants, sizeof(constants));

            const MeshSubset& subset = m_subsets[item.subsetIndex];
            cmd->drawIndexed(m_indexBuffer, IndexType::UInt32, subset.indexCount, 1,
                             subset.firstIndex * sizeof(uint32_t), 0, 0);

            ++m_stats.drawCalls;
            m_stats.trianglesSubmitted += subset.indexCount / 3;
        }
    }
};
```

Строка `boundMaterial = -1;` после смены пайплайна — не перестраховка. Наша обёртка кеширует
наборы дескрипторов по хешу состояния привязок, и смена пайплайна означает другую раскладку
дескрипторов. Отслеживание «уже привязано» обязано сбрасываться. Пропуск этой строки даёт
редкий, зависящий от порядка сортировки баг: часть объектов рисуется с текстурой соседа.

---

## 5.7. Что обычно ломается

| Симптом | Причина |
|---|---|
| Геометрия появляется, когда отворачиваешься | Ближняя и дальняя плоскости перепутаны при reverse-Z |
| Объекты пропадают у края экрана | Плоскости не нормированы, или бокс подмножества посчитан неверно |
| Отсечение ничего не отсекает | Гранулярность: один бокс на всю сцену |
| Часть объектов с чужой текстурой | Не сброшено отслеживание материала после смены пайплайна |
| Инстансы все в одной точке | Uniform-буфер меньше, чем читает шейдер: вышли за размер |
| Больше 204 инстансов — мусор | Тот же лимит в 16 КиБ |
| Ошибка про выравнивание смещения | Смещение uniform-буфера не кратно 256 |
| Непрямая отрисовка рисует не то | `firstIndex` в индексах, а не в байтах — в отличие от `drawIndexed` |
| Прозрачное исчезло за непрозрачным | Прозрачность не в старшем бите ключа сортировки |

---

## 5.8. Проверка

1. **Выведите `FrameStats` в интерфейс.** Число смен пайплайна должно равняться числу
   пайплайнов, а не числу вызовов. Если больше — сортировка не работает.
2. **Отсечение.** Поворачивайте камеру и следите за `subsetsCulled`. При взгляде в стену должно
   отсекаться большинство.
3. **Измерьте overdraw.** Отрисуйте сцену с сортировкой спереди назад и в обратном порядке, сравните
   время кадра. На интерьере разница должна быть заметной — это работа Hi-Z. На Apple Silicon
   разница будет меньше: там есть аппаратное удаление скрытых поверхностей (глава 1).
4. **Инстансинг.** 10 000 копий модели через пакеты по 200 — 50 вызовов. Сравните с 10 000
   отдельных вызовов по времени процессора.

---

## Итог

1. Вызов отрисовки стоит **на процессоре** (запись команд) и **на видеокарте** (смена состояния).
   Иерархия: проход > пайплайн > дескрипторы > push-константы ≈ 0.
2. Сортируйте по составному ключу: прозрачность → пайплайн → материал → глубина. Непрозрачное
   спереди назад ради Hi-Z, прозрачное сзади наперёд ради корректности.
3. Отсечение по пирамиде — самая выгодная оптимизация. **Гранулярность важнее алгоритма.**
   Осторожно с ближней/дальней плоскостью при reverse-Z.
4. Инстансинг ограничен размером uniform-буфера: планируйте на **16 КиБ**. Пакеты со смещением в
   одном большом буфере — рабочее решение.
5. Непрямая отрисовка работает, но без вычислительных шейдеров раскрывается лишь наполовину.
6. Отслеживание привязанного состояния **обязано сбрасываться** при смене пайплайна.
