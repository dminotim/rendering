## 10.1. Железо и конвейер: где на самом деле время

Это самый недооценённый раздел книги. Начнём с того, что происходит с кадром физически.

```
CPU:   [ кадр N ][ кадр N+1 ][ кадр N+2 ]
                 ↓ commit    ↓ commit    ↓ commit
GPU:            [ кадр N ][ кадр N+1 ][ кадр N+2 ]
                          ↓ present   ↓ present
Монитор:                        [ N ]      [ N+1 ]
                                 ↑          ↑
                            вертикальная синхронизация
```

Три независимых временных шкалы. Процессор ушёл вперёд на два кадра — это то самое «два кадра в
полёте», которое наша обёртка поддерживает через слоты кадра. `commit()` **не ждёт** видеокарту.

Из этого следуют два неочевидных факта.

**Факт первый: ожидание происходит в `acquireNextImage()`.** Не в `present()` и не в `commit()`.
Изображения свопчейна конечны; когда все заняты, `acquireNextImage()` блокируется до
освобождения, а освобождение происходит по вертикальной синхронизации.

Измерьте по частям — результат выглядит так:

```
acquireNextImage   30.93 мс   ← почти всё время здесь
запись команд       0.13 мс
commit              0.08 мс
────────────────────────────
кадр               31.22 мс
```

Это **нормальная** картина полностью здорового рендерера, работающего на полной частоте
обновления. 31.25 мс — период монитора на 32 Гц. Первая реакция «acquire тормозит, надо
оптимизировать» — ошибочна: там просто ждут монитор.

Отсюда практическое правило диагностики: **сначала выясните частоту обновления вашего дисплея, и
только потом делайте выводы о производительности.** Ноутбук в режиме экономии, удалённый рабочий
стол, внешний монитор через переходник — все они легко дают не 60 Гц, и время кадра, «застрявшее»
на подозрительном значении, обычно означает ровно один период обновления.

**Факт второй: `glfwGetTime()` измеряет не то, что вы думаете.** Он даёт время на процессоре,
который идёт впереди. Разница между двумя вызовами — это интервал между началами подготовки
кадров, а не между их показами.

В среднем эти интервалы совпадают: за секунду показывается ровно столько кадров, сколько
подготовлено. Но **по отдельности они гуляют**. Процессор то опережает, то догоняет; ОС даёт
квант не вовремя; сборка команд занимает то 0.1 мс, то 0.4 мс.

## 10.2. Микродрожание: как оно возникает и как выглядит

Классическая ошибка — привязать движение к измеренному на процессоре `deltaTime`:

```cpp
yaw += rotationSpeed * deltaTime;      // выглядит правильно
```

Пусть монитор идёт ровно 16.67 мс, а измеренные интервалы получились такими:

```
кадр 1:  deltaTime = 16.2 мс → поворот на 0.972 шага
кадр 2:  deltaTime = 17.1 мс → поворот на 1.026
кадр 3:  deltaTime = 16.4 мс → поворот на 0.984
кадр 4:  deltaTime = 16.9 мс → поворот на 1.014
```

Каждый кадр показывается ровно через 16.67 мс, а объект поворачивается каждый раз на **разную**
величину. Глаз воспринимает это как дрожание — не как пропущенные кадры, а как неровность
движения. Счётчик FPS при этом показывает идеальные 60.

Это одна из самых коварных проблем в реальном времени: **все метрики в норме, а глазу плохо**.

### Три способа лечения

**1. Не анимировать от `deltaTime` там, где это не нужно.**

Самое надёжное. Если объект вращается по ползунку в интерфейсе, привязывать поворот ко времени
не нужно вовсе: значение задаёт человек, и дрожания нет по построению. Именно так устроен наш
`FastRenderer.cpp` — там нет автоматического вращения, и это не упрощение, а осознанное решение.

**2. Сглаживать `deltaTime`.**

```cpp
class FrameClock {
public:
    float tick()
    {
        const double now = glfwGetTime();
        float raw = static_cast<float>(now - m_lastTime);
        m_lastTime = now;

        // Отбросить выбросы: первый кадр, точка останова в отладчике,
        // возврат из свёрнутого состояния.
        if (raw > 0.25f) raw = m_smoothed;

        // Экспоненциальное сглаживание. 0.1 — компромисс между
        // устойчивостью и откликом на реальное изменение частоты.
        m_smoothed = m_smoothed * 0.9f + raw * 0.1f;
        return m_smoothed;
    }
private:
    double m_lastTime = glfwGetTime();
    float  m_smoothed = 1.0f / 60.0f;
};
```

Сглаживание убирает дрожание почти полностью. Плата — задержка отклика при реальной смене
частоты кадров, что для анимации несущественно.

**Не сглаживайте `deltaTime` для камеры под управлением человека.** Там важна отзывчивость, и
сглаживание даёт ощущение «плывущего» управления.

**3. Фиксированный шаг с интерполяцией.**

Промышленный подход, обязательный при физике:

```cpp
constexpr float kFixedStep = 1.0f / 120.0f;
float accumulator = 0.0f;

accumulator += clock.tick();

// Ограничение числа шагов: без него после долгой паузы
// симуляция уйдёт в «спираль смерти», пытаясь догнать время.
int steps = 0;
while (accumulator >= kFixedStep && steps < 8) {
    previousState = currentState;
    simulate(currentState, kFixedStep);
    accumulator -= kFixedStep;
    ++steps;
}

// Рисуем интерполированное состояние между двумя шагами симуляции.
const float alpha = accumulator / kFixedStep;
renderState = lerp(previousState, currentState, alpha);
```

Даёт воспроизводимость (одинаковый ввод — одинаковый результат) и полную независимость от частоты
кадров. Для чисто визуальной анимации избыточно; для физики обязательно.

## 10.3. Динамические буферы и кадры в полёте

Вот проблема, которая в наивной реализации даёт разрывы картинки.

Процессор идёт впереди на два кадра. Если каждый кадр писать матрицы в один и тот же
uniform-буфер, то запись для кадра N+1 попадёт в буфер, из которого видеокарта **ещё читает**
кадр N. Результат — «разъезжающаяся» геометрия или мерцание.

Наша обёртка решает это внутри. `BufferUsage::Dynamic` создаёт буфер, физически состоящий из
нескольких областей — по одной на слот кадра, — и `update()` пишет в область текущего слота, а
привязка направляет шейдер туда же. Приложению об этом знать не нужно.

Одна тонкость документирована и стоит того, чтобы её понимать. **Частичное обновление**
динамического буфера:

```cpp
buffer->update(&value, sizeof(value), offsetof(Uniforms, exposure));
```

Записываются указанные байты, а **все остальные сохраняют прежнее содержимое** — то, что было
записано в любом предыдущем кадре, а не то, что случайно оказалось в области этого слота. Для
этого обёртка при частичном обновлении переносит содержимое предыдущей области. Стоит одной
дополнительной копии.

Практический вывод: **если меняется вся структура, пишите её целиком одним вызовом** — это
дешевле, чем несколько частичных обновлений.

```cpp
// Хорошо: одна запись
SceneUniforms uniforms = buildUniforms(camera, lights, exposure);
uniformBuffer->update(&uniforms, sizeof(uniforms));

// Хуже: три записи, каждая с переносом предыдущего содержимого
uniformBuffer->update(&viewProjection, 64, 0);
uniformBuffer->update(&cameraPosition, 12, 64);
uniformBuffer->update(&exposure, 4, 76);
```

**Не используйте `BufferUsage::Static` для того, что меняется каждый кадр.** Там `update()`
проходит через промежуточный буфер и **ждёт** завершения копирования на GPU — то есть выкидывает
весь выигрыш от асинхронности и превращает 31 мс ожидания монитора в 31 мс ожидания плюс
простой.

## 10.4. Анимация трансформаций

Простейший и самый полезный вид анимации: объекты движутся, вращаются, масштабируются как целое.

```cpp
struct Keyframe {
    float time = 0.0f;
    Vec3  position;
    Quat  rotation;
    Vec3  scale { 1, 1, 1 };
};

struct TransformTrack {
    std::vector<Keyframe> keys;

    Keyframe sample(float time) const
    {
        if (keys.empty()) return {};
        if (time <= keys.front().time) return keys.front();
        if (time >= keys.back().time)  return keys.back();

        size_t next = 1;
        while (next < keys.size() && keys[next].time < time) ++next;

        const Keyframe& a = keys[next - 1];
        const Keyframe& b = keys[next];
        const float t = (time - a.time) / (b.time - a.time);

        Keyframe result;
        result.position = lerp(a.position, b.position, t);
        // Поворот интерполируется СФЕРИЧЕСКИ. Линейная интерполяция
        // кватернионов даёт неравномерную угловую скорость: середина
        // поворота проходится быстрее краёв.
        result.rotation = slerp(a.rotation, b.rotation, t);
        result.scale    = lerp(a.scale, b.scale, t);
        return result;
    }
};
```

**Почему кватернионы, а не углы Эйлера.** У углов Эйлера две беды: шарнирный замок (при наклоне
90° две оси совпадают и одна степень свободы теряется) и невозможность корректно интерполировать
— результат зависит от порядка применения осей. Кватернион и то, и другое снимает.

**Почему `slerp`, а не `lerp`.** Линейная интерполяция кватернионов даёт правильные ориентации на
концах, но неравномерную угловую скорость между ними. На повороте в 90° это заметно; на 180° —
очевидно.

## 10.5. Скиннинг на GPU

### Идея

У каждой вершины есть до четырёх костей, влияющих на неё, с весами в сумме равными единице.
Итоговая позиция — взвешенная сумма позиций, преобразованных матрицами этих костей.

```
p' = Σ wᵢ · Mᵢ · p
```

`Mᵢ` — матрица кости, уже включающая обратную матрицу привязки (bind pose), то есть
преобразование «из исходной позы в текущую».

Работа целиком вершинная, и на неё замечательно ложится GPU: 100 000 вершин × 4 кости × ~30
операций = 12 млн операций на кадр, доли процента от бюджета.

### Вершина скиннингованной модели

Наш `MeshVertex` в 48 байт места под кости не имеет. Но раскладка вершины живёт **в шейдере**
(глава 2), поэтому достаточно объявить другую структуру и создать под неё отдельный пайплайн.

```cpp
struct SkinnedVertex {
    float    position[3];
    float    pad0 = 0.0f;
    float    normal[3];
    float    pad1 = 0.0f;
    float    uv[2];
    float    pad2[2] = { 0.0f, 0.0f };
    uint32_t boneIndices[4];     // 16
    float    boneWeights[4];     // 16
};
static_assert(sizeof(SkinnedVertex) == 80, "должно совпадать с шейдером");
```

80 байт против 48 — на 67 % больше памяти под геометрию. Уплотнить можно: индексы костей
помещаются в четыре байта (моделей с более чем 256 костями почти не бывает), веса — в четыре
полукратных float, причём четвёртый вес выводится из первых трёх. Итого 8 байт вместо 32. Для
персонажа в 100 тысяч вершин разница — 2.4 МБ; заниматься этим стоит, когда персонажей десятки.

### Матрицы костей

Здесь снова упирается ограничение из главы 5: **storage-буфер только один, и он занят вершинами.**
Матрицы костей идут в uniform-буфер.

```metal
// Гарантированный минимум uniform-буфера — 16 КиБ.
//   float4x4 → 64 байта → 256 костей
//   4×3      → 48 байт  → 341 кость
// Берём компактную форму: нижняя строка матрицы кости всегда (0,0,0,1).
constant constexpr uint kMaxBones = 256;

struct BoneMatrices {
    float4 rows[kMaxBones * 3];      // по 3 строки float4 на кость
};
```

256 костей хватает на человекоподобного персонажа с запасом (типично 60–120, с пальцами — до
160). Не хватит на толпу в одном вызове — там нужен storage-буфер, то есть доработка обёртки из
главы 13.

### Шейдер

```metal
struct SkinnedVertex {
    packed_float3 position;  float pad0;
    packed_float3 normal;    float pad1;
    packed_float2 uv;        packed_float2 pad2;
    uint4         boneIndices;
    float4        boneWeights;
};

float4x4 boneMatrix(constant BoneMatrices& bones, uint index)
{
    const float4 r0 = bones.rows[index * 3 + 0];
    const float4 r1 = bones.rows[index * 3 + 1];
    const float4 r2 = bones.rows[index * 3 + 2];
    // Собираем по столбцам: MSL хранит float4x4 по столбцам.
    return float4x4(float4(r0.x, r1.x, r2.x, 0.0),
                    float4(r0.y, r1.y, r2.y, 0.0),
                    float4(r0.z, r1.z, r2.z, 0.0),
                    float4(r0.w, r1.w, r2.w, 1.0));
}

vertex GBufferVertexOut skinned_vertex(const device SkinnedVertex* vertices  [[buffer(0)]],
                                       constant BoneMatrices&      bones     [[buffer(1)]],
                                       constant DrawConstants&     constants [[buffer(8)]],
                                       uint                        vid       [[vertex_id]])
{
    SkinnedVertex v = vertices[vid];

    // Линейное смешивание матриц (Linear Blend Skinning). Смешиваются
    // МАТРИЦЫ, а не результаты — так вдвое меньше умножений вектора.
    float4x4 skin = boneMatrix(bones, v.boneIndices.x) * v.boneWeights.x;
    skin += boneMatrix(bones, v.boneIndices.y) * v.boneWeights.y;
    skin += boneMatrix(bones, v.boneIndices.z) * v.boneWeights.z;
    skin += boneMatrix(bones, v.boneIndices.w) * v.boneWeights.w;

    const float4 skinnedPosition = skin * float4(float3(v.position), 1.0);
    // Нормаль преобразуется той же матрицей с нулевой w: перенос не применяется.
    const float3 skinnedNormal   = (skin * float4(float3(v.normal), 0.0)).xyz;

    GBufferVertexOut out;
    out.clipPosition = constants.modelViewProjection * skinnedPosition;
    out.worldNormal  = normalize((constants.model * float4(skinnedNormal, 0.0)).xyz);
    out.uv           = float2(v.uv);
    out.viewDepth    = -(constants.modelView * skinnedPosition).z;
    return out;
}
```

**Про «эффект конфеты».** Линейное смешивание матриц имеет известный дефект: при повороте сустава
на большой угол объём в районе сгиба схлопывается — локоть или запястье «пережимается». Причина в
том, что линейная комбинация двух матриц поворота — уже не поворот.

Правильное лечение — двойные кватернионы (dual quaternion skinning), у которых смешивание
сохраняет жёсткость преобразования. Стоит дороже и требует другой подготовки данных. Практическое
смягчение — добавлять вспомогательные кости в местах сильных сгибов, и именно так поступает
большинство игр.

### Чего в проекте нет: формата с анимацией

Скажем прямо: **наш загрузчик анимацию не читает**. OBJ, STL и PLY — статические форматы, и в
сценах архива анимации нет вовсе.

Чтобы дойти до анимированного персонажа, нужен формат со скелетом: **glTF 2.0** — очевидный
выбор. Он открытый, компактный, повсеместно поддерживаемый, и для него есть однофайловые
библиотеки: `cgltf` (C, одна голова) или `tinygltf` (C++). Интеграция сопоставима по объёму с
тем, что мы сделали с `tinyobjloader` в главе 4.

Что придётся написать сверх загрузки: перевод иерархии узлов glTF в плоский массив матриц костей
в правильном порядке (родитель раньше ребёнка), применение обратных матриц привязки и выборку
дорожек анимации. Это отдельный выпуск, и он честно выходит за рамки «отрисовать архив
casual-effects», который весь статический.

## 10.6. Инстансированная анимация

Толпа одинаковых объектов с разными фазами. Схема из главы 5 (пакеты по 200 инстансов со
смещением в uniform-буфере) работает, но для скиннинга слот 1 уже занят матрицами костей.
Остаются слоты 2…7, и данные инстанса идут туда:

```metal
vertex GBufferVertexOut skinned_instanced(const device SkinnedVertex* vertices  [[buffer(0)]],
                                          constant BoneMatrices&      bones     [[buffer(1)]],
                                          constant InstanceBlock&     instances [[buffer(2)]],
                                          constant DrawConstants&     constants [[buffer(8)]],
                                          uint vid [[vertex_id]],
                                          uint iid [[instance_id]])
```

Ограничение существенное: **у всех инстансов в одном вызове одна и та же поза**. Толпа будет
двигаться синхронно. Разные позы требуют либо вызова на позу (тогда инстансинг вырождается), либо
storage-буфера с матрицами всех поз — то есть опять доработки обёртки.

Практичный компромисс — три-четыре набора поз, инстансы разбиты на группы по набору, вызов на
группу. Синхронность разбивается, а число вызовов остаётся малым. Так делают в играх со зрителями
на трибунах.

## 10.7. Что обычно ломается

| Симптом | Причина |
|---|---|
| Дрожание при равномерном движении, FPS идеальный | Движение привязано к несглаженному `deltaTime` |
| Время кадра «застряло» на странном значении | Это период вашего монитора. Проверьте частоту обновления |
| `acquireNextImage` занимает почти всё время | Норма: там ждут вертикальной синхронизации |
| Скачок анимации после отладочной паузы | Не отброшен выброс `deltaTime` |
| Приложение «догоняет время» и виснет | Нет ограничения числа шагов фиксированной симуляции |
| Геометрия «разъезжается» при обновлении буфера | `Static` вместо `Dynamic` для того, что меняется каждый кадр |
| Просадка при обновлении uniform-буфера | То же: `Static` ждёт GPU на каждом `update()` |
| Модель схлопнулась в точку | Веса костей не нормированы, либо индексы вне диапазона |
| Пережатие в локтях и запястьях | Дефект линейного смешивания матриц; нужны вспомогательные кости |
| Мусор при более чем 256 костях | Вышли за uniform-буфер |
| Неравномерная скорость поворота | `lerp` вместо `slerp` для кватернионов |

## 10.8. Проверка

1. **Тест на дрожание.** Медленно вращающийся объект с чёткой вертикальной гранью. Смотрите на
   край. Несглаженный `deltaTime` даст едва заметное «подрагивание» — сравните со сглаженным,
   разница видна.
2. **Измерьте кадр по частям** и найдите частоту обновления своего дисплея. Убедитесь, что время
   кадра равно одному периоду. Это калибровка всех дальнейших измерений.
3. **Тест частичного обновления.** Заполните динамический буфер значениями `{1,2,3,4}`, потом
   частично обновите второй и четвёртый элементы. Прочитайте через `readback()`: должно быть
   `{1,20,3,40}`, а не `{0,20,0,40}`. Проверяет перенос содержимого между слотами кадра.
4. **Проверка весов скиннинга.** Выведите цветом `sum(boneWeights)`. Везде должна быть единица.
   Отклонения — ошибка при подготовке данных, и они дают тянущиеся вершины.
5. **Проверка предела костей.** Модель с 300 костями при `kMaxBones = 256` должна разваливаться
   заметно, а не тихо. Добавьте проверку при загрузке.

## Итог

1. Три временных шкалы — процессор, видеокарта, монитор — не совпадают. Ожидание живёт в
   `acquireNextImage()`, и это **норма**.
2. Измеренный на процессоре `deltaTime` неравномерен, даже когда кадры показываются идеально
   ровно. Отсюда дрожание при нормальном FPS. Лечится сглаживанием, фиксированным шагом или
   отказом от привязки ко времени там, где она не нужна.
3. **Всегда узнавайте частоту обновления дисплея перед выводами о производительности.**
4. `BufferUsage::Dynamic` для всего, что меняется каждый кадр. Частичные обновления корректны, но
   писать структуру целиком дешевле.
5. Скиннинг: своя раскладка вершины (80 байт), матрицы костей в uniform-буфере, **предел 256
   костей** — следствие того, что storage-буфер занят вершинами.
6. Кватернионы и `slerp`. Углы Эйлера и `lerp` дают известные и неисправимые дефекты.
7. **Анимацию наш загрузчик не читает.** Нужен glTF; сцены архива статические.
