## 13.1. Что ломается на масштабе

На Sponza (260 тыс. треугольников, 40 текстур) всё написанное работает без единой оговорки. На
San Miguel ломается сразу несколько вещей: загрузчик отказывается открыть файл, дедупликация
требует гигабайта, пул дескрипторов заканчивается посреди первого кадра, а отсечение по
подмножествам перестаёт что-либо отсекать.

Ниже — измеренные значения, а не оценки: всё в этой главе проверено на обоих вариантах San Miguel
из архива, на настольной видеокарте с 8 ГиБ видеопамяти, в сборке Release.

| | san-miguel-low-poly | san-miguel (полный) |
|---|---|---|
| Размер OBJ | 599 МБ текста | **1.1 ГБ текста** |
| Треугольников | 5 617 451 | **9 980 699** |
| Вершин после дедупликации | 5 858 709 | 9 021 391 |
| Подмножеств / материалов | 1722 / 281 | 2203 / 287 |
| Разбор OBJ | 4.9 с | **9.0 с** |
| Загрузка из бинарного кеша | **0.14 с** | 0.27 с |
| Геометрия в памяти (24 Б/вершину) | 198 МиБ | 321 МиБ |
| Текстуры (266 файлов, потоками) | 442 МиБ за 0.51 с | те же |
| Материалов, определённых вырезаемыми по пикселям | 97 | 95 |
| Всего видеопамяти под сцену | ~870 МиБ | ~1090 МиБ |

Два числа из этой таблицы стоит выделить. **Кеш даёт разницу в тридцать раз** — 9 секунд против
0.27. И **текстуры грузятся полсекунды** благодаря распаковке в потоках; последовательно те же
266 файлов заняли бы несколько секунд, и это была бы самая долгая часть старта после разбора.

Разберём по порядку.

## 13.2. Компактная вершина

Начнём с того, что даёт самый большой выигрыш при наименьших усилиях.

`MeshVertex` занимает 48 байт, из которых 12 — заполнители. Мы ввели их в главе 2, чтобы
раскладка совпадала с правилами выравнивания векторов в шейдере. Но раскладка живёт **в шейдере**,
и никто не заставляет нас использовать векторные типы.

```cpp
struct SceneVertex {
    float    position[3];    // 12 — полная точность обязательна
    uint32_t packedNormal;   //  4 — октаэдральная упаковка, 2×16 бит
    uint32_t packedUv;       //  4 — два полукратных float
};
static_assert(sizeof(SceneVertex) == 20, "должно совпадать с шейдером");
```

**20 байт вместо 48 — в 2.4 раза меньше.** Но прежде чем брать это число, дочитайте до
предупреждения про UV ниже: в проекте в итоге используется вариант на **24 байта**, с координатой
полной точности. На полном San Miguel это 321 МиБ вместо 642 — вдвое, а не в 2.4 раза, и это
правильный размен.

Почему это законно с точки зрения выравнивания: все поля — четырёхбайтовые скаляры, поэтому
выравнивание структуры равно 4, и шаг массива равен её размеру, 20 байт. Заполнители нужны были
только из-за `vec3`, у которого выравнивание 16. Убрали векторы — убрали и заполнители.

### Упаковка нормали

Октаэдральная проекция: единичная сфера разворачивается на квадрат. Две 16-битные компоненты
дают точность около 0.1 градуса — заметно лучше, чем нужно для затенения.

```cpp
uint32_t packNormal(float x, float y, float z)
{
    const float invL1 = 1.0f / (std::abs(x) + std::abs(y) + std::abs(z));
    float px = x * invL1;
    float py = y * invL1;

    if (z < 0.0f) {
        const float tx = (1.0f - std::abs(py)) * (px >= 0.0f ? 1.0f : -1.0f);
        const float ty = (1.0f - std::abs(px)) * (py >= 0.0f ? 1.0f : -1.0f);
        px = tx; py = ty;
    }

    const auto quantise = [](float v) {
        return static_cast<uint32_t>(
            std::lround(std::clamp(v, -1.0f, 1.0f) * 32767.0f)) & 0xFFFFu;
    };
    return quantise(px) | (quantise(py) << 16);
}
```

```metal
float3 unpackNormal(uint packed)
{
    const float2 e = float2(float(int(short(packed & 0xFFFF))),
                            float(int(short(packed >> 16)))) / 32767.0;

    float3 n = float3(e, 1.0 - abs(e.x) - abs(e.y));
    if (n.z < 0.0) {
        n.xy = (1.0 - abs(n.yx)) * select(float2(-1.0), float2(1.0), n.xy >= 0.0);
    }
    return normalize(n);
}

float2 unpackUv(uint packed)
{
    return float2(as_type<half2>(packed));
}
```

**Осторожно с UV в полукратной точности.** У `half` около трёх значащих цифр. Для координат в
[0, 1] этого достаточно; для тайлящихся текстур с координатами вроде 50.0 — уже нет, шаг между
соседними значениями становится 0.03 текстуры. В сценах архива такие координаты встречаются на
полах и стенах. Решение: приводить UV к диапазону [0, 1] при загрузке, вынося целую часть в
материал, либо оставить UV в полной точности (24 байта вместо 20 — всё равно вдвое лучше 48).

Именно так и сделано в проекте: позиция и координата полной точности, упакована только нормаль —
24 байта. Полукратные UV дают ещё четыре байта, но у San Miguel координаты на полах и стенах
доходят до десятков, и рябь на плитке того не стоит. Начните с полной точности и переходите на
упаковку, только измерив, что упираетесь в память.

## 13.3. Бинарный кеш сцены

Разбор текстового OBJ на 1 ГБ — это десятки секунд, из которых:

- чтение и лексический разбор — примерно половина;
- дедупликация вершин — вторая половина (см. следующий раздел: структура здесь важнее, чем
  кажется);
- построение подмножеств и границ — остальное.

Ускорять разбор текста бессмысленно: правильный ответ — **разобрать один раз и сохранить
результат в формате, который читается за одно чтение**.

```cpp
struct SceneCacheHeader {
    char     magic[8]    = { 'D','M','S','C','E','N','E','1' };
    uint32_t version     = 3;      // менять при ЛЮБОМ изменении раскладки
    uint32_t vertexCount = 0;
    uint32_t indexCount  = 0;
    uint32_t subsetCount = 0;
    uint32_t materialCount = 0;
    uint64_t sourceWriteTime = 0;  // время изменения исходного OBJ
    uint64_t sourceFileSize  = 0;
    float    boundsMin[3]{};
    float    boundsMax[3]{};
};

bool saveSceneCache(const std::filesystem::path& path, const Mesh& mesh,
                    const std::filesystem::path& source)
{
    std::ofstream out(path, std::ios::binary);
    if (!out) return false;

    SceneCacheHeader header;
    header.vertexCount   = static_cast<uint32_t>(mesh.vertices.size());
    header.indexCount    = static_cast<uint32_t>(mesh.indices.size());
    header.subsetCount   = static_cast<uint32_t>(mesh.subsets.size());
    header.materialCount = static_cast<uint32_t>(mesh.materials.size());
    header.sourceWriteTime = static_cast<uint64_t>(
        std::filesystem::last_write_time(source).time_since_epoch().count());
    header.sourceFileSize = std::filesystem::file_size(source);

    out.write(reinterpret_cast<const char*>(&header), sizeof(header));
    out.write(reinterpret_cast<const char*>(mesh.vertices.data()),
              mesh.vertices.size() * sizeof(SceneVertex));
    out.write(reinterpret_cast<const char*>(mesh.indices.data()),
              mesh.indices.size() * sizeof(uint32_t));
    // Подмножества — POD, пишутся блоком. Материалы содержат строки,
    // поэтому сериализуются по одному: длина, затем байты.
    // ...
    return out.good();
}
```

Три обязательных поля в заголовке, без которых кеш становится источником загадочных багов:

**`magic`** — иначе однажды кешем окажется чужой файл, и вы получите падение при чтении мусора.

**`version`** — увеличивайте при **любом** изменении раскладки структур. Забытое обновление
версии даёт чтение старого кеша новым кодом, то есть тихую порчу данных. Это самая частая ошибка
при работе с кешами.

**Время изменения и размер исходника** — если OBJ переэкспортировали, кеш устарел. Проверка обоих
полей надёжнее проверки только времени: некоторые системы контроля версий восстанавливают время.

Результат для San Miguel: **9.0 секунды превращаются в 0.27**, потому что чтение сводится к трём
крупным `read()` в заранее выделенные векторы. Это разница между «запускаю и иду за кофе» и
«запускаю и работаю», а на неё уходит примерно двести строк.

### Первое препятствие: загрузчик просто откажется

До всякой оптимизации разбор упирается в защиту внутри tinyobjloader:

```
input stream too large (628033664 bytes exceeds limit 268435456 bytes)
```

Ограничение в 256 МиБ — разумная защита от того, чтобы повреждённый файл был целиком прочитан в
память, и оно намеренно сделано настраиваемым. Поднимается макросом в той единице трансляции, где
подключается реализация, — вендоренный код при этом не трогается:

```cpp
#define TINYOBJLOADER_STREAM_READER_MAX_BYTES \
    (size_t(4) * size_t(1024) * size_t(1024) * size_t(1024))
#define TINYOBJLOADER_IMPLEMENTATION
#include "tiny_obj_loader.h"
```

Стоит поднять до значения, которое всё ещё что-то значит (4 ГиБ), а не до максимума: смысл
проверки в том, чтобы поймать мусор, а не в конкретном числе.

### Ускорение самого разбора

Когда кеша ещё нет, разбор всё равно надо пережить. Два места дают почти весь выигрыш:

**Резервируйте.** Без этого любая хеш-таблица перехеширует десятки раз на миллионах вставок,
каждый раз перестраивая себя целиком. Одна строка, и её стоит добавить всегда.

**А вот от хеш-таблицы здесь лучше отказаться совсем.** Ключ дедупликации — тройка индексов
(позиция, нормаль, координата), и таблица, рассчитанная на тридцать миллионов вершин-граней San
Miguel, стоит около гигабайта ещё до того, как в неё что-то положили. Это больше, чем сама
геометрия.

Структура, которая обходится десятками мегабайт, опирается на то, где комбинации **на самом деле**
группируются: у одной позиции обычно одна–шесть различных пар (нормаль, координата), потому что
различаются они только на швах и жёстких рёбрах. Значит каждая позиция может владеть коротким
списком уже созданных из неё вершин:

```cpp
std::vector<int32_t> head;       // по одному int на позицию: начало цепочки, или -1
std::vector<int32_t> next;       // по одному на созданную вершину
std::vector<int32_t> normal;     // ключ: индекс нормали
std::vector<int32_t> texCoord;   // ключ: индекс координаты
std::vector<uint32_t> vertex;    // результат: индекс в Mesh::vertices

// Поиск: пройти цепочку head[position], сравнивая пару (normal, texCoord).
for (int32_t e = head[position]; e >= 0; e = next[e]) {
    if (normal[e] == n && texCoord[e] == t) return vertex[e];
}
```

Память: четыре байта на позицию плюс шестнадцать на каждую созданную вершину. Для San Miguel это
десятки мегабайт вместо гигабайта, а поиск остаётся O(длины цепочки), то есть практически
константой.

## 13.4. Загрузка текстур: время и память

### Время

`GImage::update()` синхронен: отправляет копирование и ждёт. Для трёхсот текстур San Miguel
последовательная загрузка занимает минуты, причём **процессор при этом почти не занят** — он
ждёт видеокарту.

Раскладываем задачу на две части с разными свойствами:

```cpp
// Распаковка PNG/JPG — чистый счёт на процессоре, прекрасно распараллеливается.
// Создание изображений трогает устройство и остаётся на главном потоке.
struct DecodedTexture {
    std::filesystem::path path;
    std::vector<uint8_t>  pixels;
    uint32_t width = 0, height = 0;
};

std::vector<DecodedTexture> decodeAll(const std::vector<std::filesystem::path>& paths)
{
    std::vector<DecodedTexture> results(paths.size());
    const unsigned threadCount = std::max(1u, std::thread::hardware_concurrency());

    std::atomic<size_t> next{0};
    std::vector<std::thread> workers;
    for (unsigned t = 0; t < threadCount; ++t) {
        workers.emplace_back([&] {
            for (size_t i = next++; i < paths.size(); i = next++) {
                int w = 0, h = 0, c = 0;
                stbi_uc* data = stbi_load(paths[i].string().c_str(), &w, &h, &c, 4);
                if (!data) continue;
                results[i].path   = paths[i];
                results[i].width  = static_cast<uint32_t>(w);
                results[i].height = static_cast<uint32_t>(h);
                results[i].pixels.assign(data, data + size_t(w) * h * 4);
                stbi_image_free(data);
            }
        });
    }
    for (std::thread& worker : workers) worker.join();
    return results;
}
```

`stbi_load` не хранит глобального состояния между вызовами, поэтому вызывать его из разных потоков
на **разные файлы** безопасно.

**Создание изображений оставляем на главном потоке.** Обёртка не документирует потокобезопасность
`Device::createImage()`, а оба бэкенда за ним обращаются к общим объектам — пулу команд, очереди,
аллокатору. Без явных гарантий это гонка.

Выигрыш на восьмиядерном процессоре — примерно вчетверо-впятеро по времени распаковки. Плюс
пиковый расход памяти: все распакованные пиксели держатся одновременно. Для сотен текстур 2048²
это гигабайты, поэтому распаковывайте **пакетами** — по числу потоков, а не всё сразу.

### Память

Считаем для San Miguel без сжатия:

```
Геометрия (SceneVertex 20 Б):  10 млн × 20 Б  =  200 МБ
Индексы:                       30 млн ×  4 Б  =  120 МБ
Текстуры (≈300 шт., в среднем 1024², с мипами):  ~1.7 ГБ
                                                 ───────
                                                 ~2 ГБ
```

Мало какая машина это переварит вместе с G-буфером, HDR, картами теней и постобработкой из глав
8–11. Три рычага, по убыванию отдачи:

**1. BC-сжатие текстур** (глава 5) — деление на 4–8. 1.7 ГБ → 250–400 МБ. Это **решает** проблему,
и это единственный рычаг, который её решает. Всё остальное — косметика.

**2. Ограничение разрешения текстур.** Уменьшение каждой вдвое даёт вчетверо. Для сцены, которую
разглядывают с расстояния, 1024 вместо 2048 почти незаметно.

**3. Компактная вершина** (раздел 13.2) — 480 МБ → 200 МБ.

Обязательно следите за бюджетом и говорите вслух, когда вышли за него:

```cpp
const MemoryBudget budget = device->queryMemoryBudget();
if (budget.availableBytes() < requiredBytes) {
    std::fprintf(stderr,
        "ВНИМАНИЕ: требуется %.0f МиБ, доступно %.0f МиБ. "
        "Ресурсы будут размещены в системной памяти — ожидается падение скорости.\n",
        requiredBytes / 1048576.0, budget.availableBytes() / 1048576.0);
}
```

Обёртка при нехватке видеопамяти **не падает**: она размещает ресурс в памяти, видимой
процессору, и продолжает работать медленнее. Удобно, но именно поэтому надо проверять
`memoryLocation()` явно — иначе окажется, что «на этой машине почему-то в три раза медленнее», и
причину придётся искать.

## 13.5. Пространственное отсечение

На Sponza отсечение по подмножествам работало. На San Miguel — почти нет: подмножество «листва»
охватывает весь двор, и его ограничивающий параллелепипед всегда в кадре.

Нужно резать **пространственно**, независимо от материала.

### Равномерная сетка

Простейшая структура, дающая 80 % пользы:

```cpp
class SpatialGrid {
public:
    void build(const Mesh& mesh, uint32_t cellsPerAxis)
    {
        m_cellsPerAxis = cellsPerAxis;
        m_boundsMin = mesh.boundsMin;
        m_cellSize  = (mesh.boundsMax - mesh.boundsMin) / float(cellsPerAxis);
        m_cells.assign(cellsPerAxis * cellsPerAxis * cellsPerAxis, {});

        // Каждый треугольник попадает в ячейку по своему центру.
        // Треугольники крупнее ячейки обрабатываются отдельно (см. ниже).
        for (size_t tri = 0; tri < mesh.indices.size() / 3; ++tri) {
            const Vec3 centre = triangleCentre(mesh, tri);
            m_cells[cellIndex(centre)].triangles.push_back(uint32_t(tri));
        }

        // Внутри ячейки треугольники группируются по материалу —
        // так на ячейку получается по вызову на материал, а не на треугольник.
        for (Cell& cell : m_cells) buildDrawRanges(cell, mesh);
    }

    template <typename Fn>
    void queryVisible(const std::array<Plane, 6>& planes, Fn&& callback) const
    {
        for (size_t i = 0; i < m_cells.size(); ++i) {
            if (m_cells[i].triangles.empty()) continue;
            if (!insideFrustum(planes, cellBounds(i))) continue;
            callback(m_cells[i]);
        }
    }
};
```

**Крупные треугольники — известная ловушка.** Пол San Miguel может быть двумя треугольниками на
всю сцену. Отнесённые к ячейке по центру, они пропадут, когда камера смотрит в угол, где их центра
нет. Два решения: разрезать такие треугольники при подготовке (правильно) или записывать их во все
пересекаемые ячейки (проще). Для курса достаточно второго.

**Размер ячейки.** Слишком крупные — отсечение бесполезно. Слишком мелкие — вызовов больше, чем
сэкономленных треугольников. Разумное начало: ячейка примерно в 1/16 габарита сцены (сетка
16×16×16), дальше подбирать по замерам числа вызовов и треугольников.

### Отсечение по объёму каскада

Отдельная и очень выгодная оптимизация для главы 9. Проход теней рисует сцену **четыре раза** (по
каскаду). Наивно — целиком каждый раз.

Но каждый каскад накрывает свой участок, и в него нужно рисовать только то, что может отбросить
тень **в этот участок**. Тест — тот же `insideFrustum` с плоскостями ортографического объёма
каскада, только объём надо продлить в сторону источника: объект вне каскада может отбрасывать
тень внутрь него.

На San Miguel это сокращает проход теней в разы, и это самая выгодная оптимизация всей главы после
BC-сжатия.

## 13.6. Уровни детализации

Из главы 1: растеризация идёт квадами 2×2, и треугольник мельче пикселя тратит до 75 % работы
впустую. На дальних объектах San Miguel и особенно на Hairball это доминирующая стоимость.

`meshoptimizer` умеет упрощать:

```cpp
std::vector<uint32_t> buildLod(const std::vector<SceneVertex>& vertices,
                               const std::vector<uint32_t>& indices,
                               float targetRatio)
{
    std::vector<uint32_t> lod(indices.size());
    const size_t targetCount = size_t(indices.size() * targetRatio);

    float resultError = 0.0f;
    const size_t count = meshopt_simplify(
        lod.data(), indices.data(), indices.size(),
        &vertices[0].position[0], vertices.size(), sizeof(SceneVertex),
        targetCount, /*targetError*/ 0.01f, /*options*/ 0, &resultError);

    lod.resize(count);
    return lod;
}
```

Три уровня (100 %, 50 %, 20 %), выбор по экранному размеру ограничивающей сферы:

```cpp
uint32_t selectLod(const Aabb& bounds, const Vec3& cameraPosition,
                   float screenHeight, float tanHalfFov)
{
    const float radius   = boundingRadius(bounds);
    const float distance = std::max(0.001f, length(centre(bounds) - cameraPosition));

    // Приблизительная высота объекта в пикселях.
    const float screenSize = (radius / distance) * (screenHeight * 0.5f / tanHalfFov);

    if (screenSize > 300.0f) return 0;
    if (screenSize > 80.0f)  return 1;
    return 2;
}
```

**Резкое переключение уровня заметно** — объект «дёргается». Промышленные решения: плавный
переход по прозрачности между уровнями или геоморфинг. Для курса достаточно гистерезиса —
переключать вверх и вниз при разных порогах, чтобы объект на границе не мигал каждый кадр.

## 13.7. Профилирование: как найти узкое место

Прежде чем оптимизировать, надо знать, во что упираемся. Есть простой и надёжный метод, не
требующий никаких инструментов.

**Меняем один параметр и смотрим на время кадра.**

| Изменение | Время упало заметно → упираемся в |
|---|---|
| Разрешение вдвое меньше | Фрагментный шейдер или пропускную способность |
| Отключить половину геометрии | Вершинный шейдер или растеризацию |
| Текстуры вдвое меньше | Пропускную способность |
| Число источников вдвое меньше | Освещение (арифметика) |
| Убрать постобработку | Полноэкранные проходы (память) |
| Ничего не помогло | Процессор — измеряйте на нём |

Работает потому, что каждый параметр нагружает свой блок. Половина оптимизаций в жизни делается
не там, где надо, — а этот метод занимает пять минут и указывает направление точно.

### Оговорка о самом методе

Всё, что здесь измеряется, измеряется в обход свопчейна — рендерингом в собственное изображение с
`readback()` в конце, потому что в интерактивном цикле время кадра показывает период монитора
(глава 11). Это правильный способ мерить, и у него есть цена, которую надо знать.

Обходной путь — это **второй путь рендеринга**. Если он не исполняет тот же код, что путь на
экран, он измеряет и проверяет не то, что видит пользователь. В этом проекте так и вышло: проход
теней в замерном пути строил список загораживателей, а в оконном — нет, и на выгрузках тени были,
а в окне нет (глава 9, раздел 9.8b.0).

Практическое следствие для этой главы: **замерный путь должен вызывать те же функции, а не
повторять их последовательность.** Разница между «оба вызывают `renderScene()`» и «оба делают то
же самое» — это ровно та разница, из-за которой измерение перестаёт означать хоть что-нибудь.

### Инструменты

**На macOS: Xcode → Debug → Capture GPU Workload.** Даёт разбивку по проходам, время каждого
вызова, счётчики занятости и пропускной способности, и — самое ценное — показывает, какие проходы
попали в тайловую память, а какие вылетели в системную. Для нашего отложенного рендеринга из
главы 8 это подтвердит то, что мы обсуждали: G-буфер выгружается в память.

**На Windows: RenderDoc.** Покадровый разбор, содержимое всех целей на каждом шаге, состояние
пайплайна.

**В приложении: метки отладки.** Обёртка присваивает `debugName` буферам, изображениям и
пайплайнам — в захвате кадра они видны, и разбираться становится многократно легче. Называйте
ресурсы осмысленно с самого начала.

## 13.8. Рецепты по сценам

Практические заметки по каждой сцене архива: что настроить и что сломается.

### Crytek Sponza

Отправная точка. Масштаб — сантиметры, габарит около 3000 единиц.

```cpp
nearZ = 1.0f;  farZ = 5000.0f;      // с reverse-Z можно и бесконечность
cameraSpeed = 200.0f;                // единиц в секунду
sunDirection = normalize({ -0.4f, -1.0f, -0.2f });
```

Что проверить: растения в вазонах и цепи должны быть с масками и двусторонними; тень от солнца
через верхние аркады — главная проверка каскадов; занавеси полупрозрачны (`d < 1` в MTL).

### Sibenik

Собор, ~75 тыс. треугольников. Проверяет диапазон глубины: от резного капителя до нефа. Идеальная
сцена для демонстрации reverse-Z из главы 4 — со старым Z мерцание видно сразу.

### Conference

~330 тыс. треугольников, много мелких объектов. Первая сцена, где отсечение по подмножествам
даёт измеримую выгоду.

### Breakfast Room / Fireplace Room

Интерьеры с одним окном. Проверяют освещение: без непрямого освещения углы получаются
неправдоподобно чёрными. Хорошая мотивация для SSAO из главы 12 — и наглядная демонстрация того,
что SSAO **не заменяет** глобальное освещение, а лишь смягчает симптом.

### Hairball

~2.9 млн треугольников, все крошечные. **Патологический случай** для растеризатора: почти каждый
треугольник мельче пикселя, и квадовый оверхед из главы 1 виден во всей красе.

Измерьте время кадра и поделите на число треугольников — результат будет в разы хуже, чем на
Sponza при том же числе. Это не ошибка в коде, это физика. Единственное лекарство — упрощение
геометрии.

### Rungholt

~6.7 млн треугольников, вся сцена — один материал с большим атласом. Проверяет сортировку
(сортировать нечего) и пространственное отсечение (единственный работающий рычаг). Отличная
демонстрация того, что сетка из раздела 13.5 нужна независимо от числа материалов.

### San Miguel

~10 млн треугольников, сотни материалов, много растительности. Главный экзамен курса:

- бинарный кеш (12.3) — иначе каждый запуск начинается с ожидания;
- компактная вершина (12.2) и BC-сжатие (глава 5) — иначе не влезет;
- пространственная сетка (12.5) — иначе отсечение бесполезно;
- предпроход глубины (глава 10) — иначе листва убивает производительность;
- отсечение по объёму каскада (12.5) — иначе тени стоят как четыре сцены.

Если работает San Miguel, работает всё.

### Bistro

Несколько миллионов треугольников, сотни материалов, интерьер и улица вместе. Ближе всего к
настоящему игровому уровню. Проверяет прозрачность (витрины), большое число текстур и переход
между внутренним и внешним освещением — то есть автоэкспозицию из главы 12.

### Powerplant

~12 млн треугольников. Проверка на бюджет памяти и время загрузки. Художественной ценности мало,
диагностической — много.

## 13.9. Итоговый бюджет кадра

Измерено на полном San Miguel, 1600×900, прямая схема с MSAA 4×, солнце с каскадными тенями.
Замер сделан **без свопчейна**: в интерактивном цикле `acquireNextImage()` ждёт монитор, и время
кадра там показывает период обновления, а не стоимость работы (глава 11).

| Что | Время кадра |
|---|---|
| Только сцена, теней нет | 21 мс |
| Сцена + 4 каскада теней, отрисовки поштучно | 49 мс |
| Сцена + 4 каскада теней, непрямая отрисовка загораживателей | **41–44 мс** |

Разбор этих чисел полезнее самих чисел.

**Тени удваивают кадр.** Четыре каскада — это четыре дополнительные растеризации сцены; на
полном San Miguel в них уходит 22–25 миллионов треугольников против 5–7 в основном проходе.
Удвоение времени за это — нормальная цена, а не признак ошибки.

**И упирается это в вызовы, а не в треугольники.** Около трёх тысяч отрисовок на проход теней
оказались дороже, чем двадцать миллионов треугольников, которые они рисуют: перевод
загораживателей без маски на непрямую отрисовку срезал 20 % кадра, ничего не изменив в геометрии.
Это стоит держать в голове как общее правило: **на больших сценах сначала считайте вызовы, потом
треугольники.**

**Что здесь ещё не учтено.** Ни SSAO, ни свечения, ни сглаживания в постобработке — только сцена
и тени. Полный список из главы 12 добавил бы к этому ещё несколько миллисекунд.

Ценность не в конкретных значениях — они зависят от железа настолько, что переносить их нельзя, —
а в **самой таблице**: постройте её для своей машины, включая и выключая по одному пункту. Обычно
один занимает больше, чем три следующих вместе, и именно он и есть ответ.

## 13.10. Что обычно ломается

| Симптом | Причина |
|---|---|
| `input stream too large (... exceeds limit ...)` | Ограничение tinyobjloader; поднимается макросом |
| Загрузка минуты, каждый запуск | Нет бинарного кеша |
| Дедупликация съедает гигабайт | Хеш-таблица по тройке индексов; нужны цепочки по позициям |
| Ошибка выделения набора дескрипторов | Пул рассчитан на меньше материалов, чем в сцене (гл. 6) |
| Загрузка медленная даже с кешем | Нет `reserve`; `unordered_map` на миллионах вставок |
| Кеш даёт мусор после правки кода | Не увеличена версия в заголовке |
| Не хватает видеопамяти | Текстуры без сжатия — это единственный настоящий рычаг |
| Всё стало медленным, ошибок нет | Ресурсы уехали в системную память; проверьте `memoryLocation()` |
| Отсечение не помогает | Гранулярность по материалам вместо пространственной |
| Большие треугольники пропадают | Отнесены к ячейке по центру, а покрывают несколько |
| Тени стоят как вся сцена | Нет отсечения по объёму каскада |
| Объекты «дёргаются» вдали | Резкое переключение уровня детализации без гистерезиса |
| Текстуры «плывут» на полу | UV в полукратной точности при больших координатах |
| Падение при загрузке из потоков | `createImage` вызывается не с главного потока |

---

## 13.11. Проверка

1. **Время загрузки** San Miguel: с кешем и без. Разница должна быть на порядки.
2. **Расход памяти** до и после BC-сжатия и компактной вершины. Выведите в интерфейс.
3. **Эффективность отсечения**: число отрисованных треугольников относительно общего, при разных
   ракурсах. В углу двора должно отсекаться подавляющее большинство.
4. **Метод изменения параметра** (12.7): определите узкое место на своей машине и запишите
   вывод. Потом проверьте его захватом кадра — совпало ли.
5. **Таблица бюджета** по проходам. Постройте её для своей машины.
6. **Скриншот-эталон.** Сохраните `readback()` кадра в файл. При любом изменении кода сравнивайте с
   эталоном: это ловит регрессии, которых глазом не видно.

## Итог

1. Компактная вершина — самый дешёвый выигрыш по памяти: заполнители были нужны только из-за
   векторных типов. На практике 24 байта (позиция полной точности, октаэдральная нормаль,
   координата полной точности) против 48 — на полном San Miguel это 321 МиБ вместо 642.
2. **Бинарный кеш обязателен** для больших OBJ. Волшебное число, версия, время и размер исходника —
   три поля, каждое спасает от отдельного класса багов.
3. Распаковка изображений — в потоках, создание ресурсов — **на главном потоке**.
4. По памяти решает только **BC-сжатие текстур**. Остальное косметика.
5. Отсечение должно быть **пространственным**, а не по материалам. И оно нужно для каскадов теней
   не меньше, чем для основного прохода.
6. Метод «меняем один параметр» находит узкое место за пять минут без инструментов.
7. **На больших сценах узкое место — число вызовов, а не треугольники.** Проверяется это
   переводом прохода без собственного состояния на непрямую отрисовку: если время падает,
   упирались в процессор.
8. San Miguel — экзамен: если работает он, работает всё.
