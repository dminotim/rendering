## 4.1. Железо: что происходит при выборке из текстуры

Выборка — не чтение памяти. Это работа отдельного аппаратного блока (TMU, texture mapping unit),
который за один запрос выполняет цепочку операций:

```
   sample(texture, uv)
        │
        ▼
 1. Режим обёртки: uv → [0,1] по правилам Repeat / Mirror / ClampToEdge
        ▼
 2. Выбор уровня мипа по ПРОИЗВОДНЫМ uv между соседями в кваде 2×2
        ▼
 3. Вычисление адресов: с учётом ТАЙЛОВОЙ раскладки, а не построчной
        ▼
 4. Чтение 4 текселей (билинейно) или 8 (трилинейно, два уровня)
        ▼
 5. Распаковка BC-блока      ← бесплатно, транзисторами
        ▼
 6. Декодирование sRGB → линейное  ← тоже бесплатно
        ▼
 7. Интерполяция и возврат float4
```

Три следствия, каждое из которых определяет решения этой главы.

**Тайловая раскладка.** Текстура в видеопамяти хранится **не построчно**. Тексели переставлены
так, чтобы пространственно близкие оказались близко и в памяти — обычно по кривой Мортона или
похожей. Причина: выборка читает квадрат 2×2, а при построчном хранении верхние и нижние соседи
разнесены на целую строку и попадают в разные строки кеша.

Именно поэтому нельзя просто отдать драйверу указатель на пиксели: `GImage::update()` копирует
данные через промежуточный буфер, а аппаратура перекладывает их в свою раскладку. Это стоит
времени, и на сотнях текстур San Miguel время станет заметным (раздел 4.7).

**Мипы ускоряют, а не замедляют.** Интуиция подсказывает обратное — мипы это же лишняя память.
Но рассмотрим пол Sponza, уходящий к горизонту. У дальних пикселей соседи по экрану отстоят в
текстуре на десятки текселей. Без мипов каждый пиксель квада читает свой участок памяти, кеш не
попадает, и каждая выборка идёт в VRAM. С мипами выбирается уровень, где соседние пиксели читают
**соседние тексели**, и весь квад укладывается в одну-две строки кеша.

Мипы дают одновременно правильную картинку и высокую скорость. Отказ от них даёт муар **и**
провал производительности. Это редкий случай, когда компромисса нет вовсе.

**BC-сжатие бесплатно.** Распаковка происходит в блоке, между чтением и фильтрацией. Сжатая
текстура читает вчетверо-ввосьмеро меньше байт и вчетверо-ввосьмеро эффективнее использует кеш.

## 4.2. Загрузчик изображений

В проекте его нет. Добавляем [`stb_image`](https://github.com/nothings/stb) — один заголовочный
файл, общественное достояние, читает PNG, JPG, TGA, BMP и HDR. Ровно тот набор, что встречается в
архиве.

`external/stb/stb_image.h` кладём рядом с уже вендоренными `tinyobjloader` и `happly`. В
`CMakeLists.txt` добавляем каталог во включения.

```cpp
// texture/TextureLoader.cpp
#define STB_IMAGE_IMPLEMENTATION
#include "stb_image.h"

#include "TextureLoader.hpp"

namespace dmrender {

    std::shared_ptr<GImage> loadTexture(const std::shared_ptr<Device>& device,
                                        const std::filesystem::path& path,
                                        bool isColorData,
                                        std::string& error)
    {
        int width = 0, height = 0, channelsInFile = 0;

        // Запрашиваем 4 канала всегда: RGB-текстуру аппаратура всё равно хранит
        // как RGBA, а формата с тремя каналами в обёртке нет.
        stbi_uc* pixels = stbi_load(path.string().c_str(),
                                    &width, &height, &channelsInFile, 4);
        if (!pixels) {
            error = "stb_image: " + std::string(stbi_failure_reason()) +
                    " (" + path.string() + ")";
            return nullptr;
        }

        ImageDesc desc{};
        desc.format    = ImageFormat::RGBA8_UNORM;
        desc.width     = static_cast<uint32_t>(width);
        desc.height    = static_cast<uint32_t>(height);
        desc.mipLevels = kFullMipChain;          // полная цепочка до 1×1
        desc.usage     = ImageUsage::Sampled;
        desc.debugName = path.filename().string();

        // Передача initialData автоматически строит всю цепочку мипов на GPU.
        std::shared_ptr<GImage> image = device->createImage(desc, pixels);

        stbi_image_free(pixels);

        if (!image) { error = "createImage failed: " + path.string(); return nullptr; }
        return image;
    }
}
```

Три момента:

**Всегда четыре канала.** Последний аргумент `stbi_load` — желаемое число каналов. Просить 3 нет
смысла: формата RGB в обёртке нет, а аппаратура всё равно хранит трёхканальные данные как
четырёхканальные.

**`kFullMipChain` плюс `initialData`.** Эта комбинация — способ получить мипы одной строкой:
обёртка выделит все уровни и построит их на GPU из нулевого. Без `initialData` уровни будут
выделены, но не заполнены, и текстура окажется мусором на всех уровнях кроме нулевого.

**`stbi_load` возвращает данные, начиная с верхней строки** — то же соглашение, что у наших
текстурных координат ((0,0) — верхний левый тексель). Переворачивать не нужно. Если картинка
окажется перевёрнутой, дело не в загрузчике, а в UV самой модели: некоторые OBJ (особенно
экспортированные из Blender) хранят V наоборот, и тогда нужно `uv.y = 1.0 - uv.y` — но это
свойство ассета, а не системная поправка.

## 4.3. sRGB, гамма и почему картинка «выцветшая»

Тема, которую пропускают чаще всего, и потом всю жизнь борются с тем, что освещение выглядит
неправильно.

### Суть проблемы

Файлы текстур хранят цвет **не линейно**. Значение 128 в PNG означает не «половина яркости», а
примерно 22 % — потому что байт кодирует цвет в пространстве sRGB, приблизительно как
`линейное^(1/2.2)`. Так сделано осознанно: человеческий глаз чувствительнее к тёмным тонам, и
такое распределение эффективнее расходует 256 градаций.

Освещение же — физика. Складывать и умножать надо **линейные** величины. Если умножить sRGB-байты
на коэффициент освещённости, результат будет неверным: тени слишком светлые, полутона грязные,
а сумма двух источников света ярче, чем должна быть.

Правильный конвейер:

```
текстура (sRGB)  ──декод──▶  линейное  ──освещение──▶  линейное HDR
                                                            │
                                                        тонмаппинг
                                                            │
                                                            ▼
                                                    линейное [0,1]
                                                            │
                                                     кодирование в sRGB
                                                            │
                                                            ▼
                                                        экран
```

### Где это делать в нашей обёртке — и честное ограничение

Обычно оба преобразования бесплатны: текстура создаётся в формате `*_SRGB`, и TMU декодирует при
выборке; цель рендеринга тоже `*_SRGB`, и ROP кодирует при записи.

**В нашем списке форматов sRGB-варианты есть только у сжатых форматов** — `BC1_RGBA_SRGB`,
`BC3_SRGB`, `BC7_SRGB`. Ни `RGBA8_SRGB`, ни `BGRA8_SRGB` в перечислении `ImageFormat` нет. Это
значит:

1. **Несжатая текстура декодируется вручную в шейдере.**
2. **Свопчейн получает линейные значения**, и кодировать в sRGB надо тоже вручную, в последнем
   шейдере кадра.

Ни то, ни другое не катастрофа, но знать надо. Варианты:

| Подход | Стоимость | Когда применять |
|---|---|---|
| `pow()` в шейдере | ~3 операции на выборку, фильтрация идёт в sRGB (слегка неверно) | Учебный код, прототип |
| Конверсия на CPU в `RGBA16_FLOAT` | ×2 память, фильтрация корректна | Небольшие важные текстуры |
| `BC7_SRGB` / `BC1_RGBA_SRGB` | Бесплатно, ещё и сжатие | Продакшн. Требует кодировщика BC |

В курсе идём по первому пути — он не требует ничего добавлять, — а в разделе 4.6 разбираем
третий как правильный финал.

```metal
// Точная формула sRGB → линейное. Кусочная: у нуля sRGB линеен.
float3 srgbToLinear(float3 c)
{
    float3 lo = c / 12.92;
    float3 hi = pow((c + 0.055) / 1.055, 2.4);
    return select(hi, lo, c <= 0.04045);
}

// Обратное преобразование — для последнего прохода кадра.
float3 linearToSrgb(float3 c)
{
    float3 lo = c * 12.92;
    float3 hi = 1.055 * pow(c, 1.0 / 2.4) - 0.055;
    return select(hi, lo, c <= 0.0031308);
}
```

`select(a, b, cond)` в MSL возвращает `b` там, где условие истинно, и `a` где ложно —
покомпонентно для векторов. Порядок аргументов обратный тернарному оператору, и на этом легко
ошибиться.

Приближение `pow(c, 2.2)` дешевле и в большинстве случаев неотличимо; кусочная формула важна там,
где значимы очень тёмные тона — например, в картах шероховатости.

### Что декодировать, а что нет

**Критически важное правило:** декодируются только **цветовые** текстуры. Карты нормалей,
шероховатости, металличности, высоты, альфа-маски — это **данные**, а не цвет. Они записаны
линейно, и применение `srgbToLinear` к карте нормалей исказит геометрию освещения.

Отсюда параметр `isColorData` в нашем загрузчике: он ничего не делает с самими байтами, но
запоминается в материале и определяет, вызовет ли шейдер декодирование.

## 4.4. Сэмплеры

```cpp
SamplerDesc desc{};
desc.minFilter = SamplerFilter::Linear;
desc.magFilter = SamplerFilter::Linear;
desc.mipFilter = SamplerFilter::Linear;      // трилинейная фильтрация
desc.addressU  = SamplerAddressMode::Repeat;
desc.addressV  = SamplerAddressMode::Repeat;
std::shared_ptr<GSampler> repeatSampler = device->createSampler(desc, "RepeatTrilinear");
```

Сэмплеры **неизменяемы и дёшевы**. Создавайте три-четыре штуки на всё приложение и переиспользуйте:

- `repeatTrilinear` — для текстур материалов;
- `clampLinear` — для полноэкранных проходов (глава 7);
- `clampNearest` — когда нужно попиксельное соответствие, например при отладочном выводе
  G-буфера.

### Честное ограничение: нет анизотропной фильтрации

В `SamplerDesc` нет поля `maxAnisotropy`. Это заметно на практике, и Sponza — идеальная
демонстрация.

Пол, уходящий вдаль, виден под скользящим углом. Пиксель на экране накрывает в текстуре вытянутый
след: несколько текселей поперёк и десятки вдоль. Трилинейная фильтрация умеет выбирать только
**квадратный** участок, поэтому берёт уровень мипа по большему размеру следа — и пол смазывается
в кашу задолго до горизонта. Анизотропная фильтрация делает несколько выборок вдоль следа и
сохраняет резкость.

Обходных путей нет. Есть только смягчение:

- **Сдвиг мипа через `minLod`** — сделает картинку резче, но вернёт муар. Компромисс, не решение.
- **Ручная анизотропия в шейдере** — несколько выборок вдоль экранной производной UV. Работает,
  но требует явного выбора уровня и умножает стоимость выборки.

Правильное решение — добавить поле в `SamplerDesc`; на обоих бэкендах это одна строка
(`VkSamplerCreateInfo::maxAnisotropy` и `MTLSamplerDescriptor.maxAnisotropy`). В главе 13 это
первый пункт списка доработок, потому что соотношение «пять строк кода — заметный выигрыш в
качестве» здесь лучшее во всём списке.

## 4.5. Расширяем материал

`MeshMaterial` сейчас знает базовый цвет и одну текстуру. Для Sponza нужно больше.

```cpp
struct MeshMaterial {
    std::string name;

    float baseColor[3] = { 0.8f, 0.8f, 0.8f };
    float opacity      = 1.0f;      // MTL: d или 1-Tr
    float roughness    = 0.5f;      // выводится из Ns
    float metallic     = 0.0f;      // в MTL нет; эвристика по Ks

    std::filesystem::path albedoTexture;    // map_Kd  — ЦВЕТ, декодировать
    std::filesystem::path alphaTexture;     // map_d   — ДАННЫЕ
    std::filesystem::path normalTexture;    // map_bump / bump — ДАННЫЕ
    std::filesystem::path specularTexture;  // map_Ks  — обычно цвет

    bool alphaMasked = false;   // требует discard во фрагментном шейдере
    bool twoSided    = false;   // не отсекать задние грани
};
```

Заполнение в `mesh/Mesh.cpp`, в цикле по материалам tinyobjloader:

```cpp
for (const tinyobj::material_t& source : objMaterials) {
    MeshMaterial material;
    material.name = source.name;

    material.baseColor[0] = source.diffuse[0];
    material.baseColor[1] = source.diffuse[1];
    material.baseColor[2] = source.diffuse[2];
    material.opacity      = source.dissolve;

    // Ns в MTL — показатель степени Фонга, от 0 до 1000. Переводим в
    // шероховатость по общепринятому приближению.
    material.roughness = std::sqrt(2.0f / (source.shininess + 2.0f));

    auto resolve = [&](const std::string& name) -> std::filesystem::path {
        if (name.empty()) return {};
        // MTL, созданные на Windows, содержат обратные слэши.
        std::string fixed = name;
        std::replace(fixed.begin(), fixed.end(), '\\', '/');
        return path.parent_path() / fixed;
    };

    material.albedoTexture   = resolve(source.diffuse_texname);
    material.alphaTexture    = resolve(source.alpha_texname);
    material.normalTexture   = resolve(source.bump_texname);
    material.specularTexture = resolve(source.specular_texname);

    material.alphaMasked = !material.alphaTexture.empty() || material.opacity < 0.999f;
    material.twoSided    = material.alphaMasked;   // эвристика из главы 3

    mesh.materials.push_back(std::move(material));
}
```

Замена обратных слэшей — не придирка. Значительная часть MTL в архиве создана на Windows и
содержит пути вроде `textures\sponza_floor.png`. На macOS такой путь не откроется, и вы получите
сцену без единой текстуры при полностью корректном коде загрузки.

## 4.6. Кеш текстур

Sponza ссылается на одну и ту же текстуру из нескольких материалов. San Miguel — из десятков.
Загружать её каждый раз означает потратить память кратно и время загрузки кратно.

```cpp
class TextureCache {
public:
    explicit TextureCache(std::shared_ptr<Device> device)
        : m_device(std::move(device)) {}

    std::shared_ptr<GImage> get(const std::filesystem::path& path)
    {
        if (path.empty()) return fallbackWhite();

        // Ключ — канонический путь: два материала могут ссылаться на один файл
        // по-разному ("textures/a.png" и "./textures/a.png").
        std::error_code ec;
        std::filesystem::path key = std::filesystem::weakly_canonical(path, ec);
        if (ec) key = path;

        auto it = m_textures.find(key.string());
        if (it != m_textures.end()) return it->second;

        std::string error;
        std::shared_ptr<GImage> image = loadTexture(m_device, key, true, error);
        if (!image) {
            std::fprintf(stderr, "texture: %s\n", error.c_str());
            image = fallbackMagenta();     // заметный цвет, а не тихий сбой
        }

        m_textures.emplace(key.string(), image);
        return image;
    }

    size_t count() const { return m_textures.size(); }

private:
    std::shared_ptr<Device> m_device;
    std::unordered_map<std::string, std::shared_ptr<GImage>> m_textures;
    // ... fallbackWhite / fallbackMagenta: изображения 1×1 ...
};
```

**Про запасные текстуры.** Отсутствующая текстура — норма для ассетов архива: пути ломаются,
файлы переименовываются. Ключевое решение — какого цвета заглушка.

Белая заглушка **скрывает** проблему: материал просто умножается на единицу и выглядит
правдоподобно. Пурпурная (`1, 0, 1`) **кричит** о проблеме и мгновенно показывает, каких файлов
не хватает. Используйте белую там, где текстура опциональна по смыслу (нет карты нормалей — и
не надо), и пурпурную там, где она обязательна (нет альбедо — это ошибка).

## 4.7. Бюджет памяти и BC-сжатие

Посчитаем, во что обходятся текстуры Sponza без сжатия.

Sponza содержит порядка 25 материалов; у большинства есть альбедо и карта нормалей, разрешение
1024×1024 или 2048×2048.

```
Одна текстура 2048×2048 RGBA8:
    2048 × 2048 × 4 Б            = 16.8 МБ
    + полная цепочка мипов (+1/3) = 22.4 МБ

40 таких текстур                 = 896 МБ
```

Почти гигабайт на сцену, которая по геометрии занимает 15 мегабайт. Текстуры — это **основной**
потребитель видеопамяти в любой реальной сцене, и понимание этого меняет приоритеты оптимизации.

С BC7 (8 бит на тексель вместо 32):

```
2048 × 2048 × 1 Б + мипы = 5.6 МБ
40 текстур               = 224 МБ
```

Вчетверо меньше. С BC1 для альбедо без альфы (4 бита на тексель) — в восемь раз.

### Формат под задачу

| Тип текстуры | Формат | Почему |
|---|---|---|
| Альбедо без прозрачности | `BC1_RGBA_SRGB` | 4 бита/тексель, аппаратный декод sRGB |
| Альбедо с альфа-маской | `BC7_SRGB` | BC1 даёт лишь 1 бит альфы — рваные края листвы |
| Карта нормалей | `BC5_UNORM` | Два канала высокой точности; Z восстанавливается в шейдере |
| Шероховатость / металличность / AO | `BC4_UNORM` | Один канал, 4 бита/тексель |

Восстановление Z для BC5:

```metal
float3 unpackNormal(float2 xy)
{
    float2 n = xy * 2.0 - 1.0;
    return float3(n, sqrt(saturate(1.0 - dot(n, n))));
}
```

Работает потому, что нормаль в касательном пространстве всегда единичной длины и всегда смотрит
наружу — знак Z известен заранее.

### Чего у нас нет: кодировщика

Обёртка умеет **принимать** BC-данные, но не умеет их **создавать**. `GImage::update()` ждёт уже
сжатые блоки, а `generateMipmaps()` на сжатом формате не работает — мипы должны прийти сжатыми
целиком (это ограничение аппаратуры, а не обёртки: блочно-сжатую текстуру нельзя отрендерить, а
построение мипов на GPU — это рендеринг).

Два пути:

**Офлайн-конвертация.** Правильный путь для продакшна: прогнать текстуры через `texconv`,
`compressonator` или `basisu` один раз, получить `.dds` или `.ktx2` со всеми мипами, и грузить их
напрямую. Быстрее и по загрузке тоже — распаковывать PNG больше не надо.

**Кодирование на лету.** Библиотека `bc7enc` или `ispc_texcomp` при старте приложения. Проще в
интеграции, но кодирование BC7 небыстрое: секунды на текстуру 2048×2048 при высоком качестве.
Годится с кешированием результата на диск.

В курсе мы остаёмся на `RGBA8_UNORM` и живём с расходом памяти, потому что это позволяет не
тащить в проект ещё одну зависимость. Но перед `queryMemoryBudget()` надо быть честными:

```cpp
const MemoryBudget budget = device->queryMemoryBudget();
std::fprintf(stderr, "VRAM: %.0f / %.0f МиБ, точный бюджет: %s\n",
             budget.deviceLocalUsedBytes / 1048576.0,
             budget.deviceLocalBudgetBytes / 1048576.0,
             budget.preciseBudget ? "да" : "оценка");
```

Обёртка не падает при исчерпании видеопамяти — она размещает ресурс в памяти, видимой процессору,
и продолжает работать медленнее. Проверить, что произошло, можно через
`GImage::memoryLocation()`. Тихая деградация вместо падения удобна, но именно поэтому её надо
отслеживать явно, иначе окажется, что «на этой машине почему-то медленно».

### Время загрузки

`GImage::update()` синхронен: он отправляет копирование и **ждёт** завершения. Для 40 текстур
Sponza это терпимо (секунды). Для San Miguel с сотнями текстур — уже нет.

Измерьте и покажите:

```cpp
const auto start = std::chrono::steady_clock::now();
// ... загрузка всех текстур ...
const auto ms = std::chrono::duration_cast<std::chrono::milliseconds>(
                    std::chrono::steady_clock::now() - start).count();
std::fprintf(stderr, "Текстуры: %zu шт. за %lld мс\n", cache.count(), (long long)ms);
```

К способам это ускорить вернёмся в главе 12.

## 4.8. Шейдер материала

```metal
#include <metal_stdlib>
using namespace metal;

struct MeshVertex {
    packed_float3 position;  float pad0;
    packed_float3 normal;    float pad1;
    packed_float2 uv;        packed_float2 pad2;
};

struct DrawConstants {
    float4x4 modelViewProjection;
    float4   baseColor;      // rgb — цвет, a — непрозрачность
    float4   flags;          // x: есть альбедо, y: альфа-маска, z: шероховатость
};

struct VertexOut {
    float4 clipPosition [[position]];
    float3 worldNormal;
    float2 uv;
};

vertex VertexOut mesh_vertex(const device MeshVertex* vertices  [[buffer(0)]],
                             constant DrawConstants&  constants [[buffer(8)]],
                             uint                     vid       [[vertex_id]])
{
    MeshVertex v = vertices[vid];

    VertexOut out;
    out.clipPosition = constants.modelViewProjection * float4(float3(v.position), 1.0);
    out.worldNormal  = float3(v.normal);
    out.uv           = float2(v.uv);
    return out;
}

float3 srgbToLinear(float3 c)
{
    return select(pow((c + 0.055) / 1.055, 2.4), c / 12.92, c <= 0.04045);
}

fragment float4 mesh_fragment(VertexOut               in        [[stage_in]],
                              constant DrawConstants& constants [[buffer(8)]],
                              texture2d<float>        albedoMap [[texture(0)]],
                              texture2d<float>        alphaMap  [[texture(1)]],
                              sampler                 albedoSmp [[sampler(0)]],
                              sampler                 alphaSmp  [[sampler(1)]],
                              bool                    facing    [[front_facing]])
{
    // Альфа-маска — ПЕРВЫМ делом. Отменённый фрагмент не должен платить
    // за остальные выборки и за освещение.
    if (constants.flags.y > 0.5) {
        const float mask = alphaMap.sample(alphaSmp, in.uv).r;
        if (mask < 0.5) discard_fragment();
    }

    float3 albedo = constants.baseColor.rgb;
    if (constants.flags.x > 0.5) {
        // Альбедо — ЦВЕТ, декодируем. Маска и нормали — данные, не декодируем.
        albedo *= srgbToLinear(albedoMap.sample(albedoSmp, in.uv).rgb);
    }

    float3 normal = normalize(in.worldNormal);
    if (!facing) normal = -normal;

    // Временное освещение: одна направленная лампа. Физика — в главе 6.
    const float3 lightDirection = normalize(float3(0.5, 1.0, 0.3));
    const float  diffuse = max(dot(normal, lightDirection), 0.0);
    const float3 ambient = float3(0.15, 0.16, 0.20);

    const float3 lit = albedo * (ambient + diffuse);

    // Свопчейн у нас в UNORM, а не в sRGB — кодируем вручную.
    return float4(pow(lit, 1.0 / 2.2), 1.0);
}
```

Порядок во фрагментном шейдере не случаен. `discard_fragment()` стоит **первым**, до выборки
альбедо. Отменённая нить всё равно занимает место в группе (глава 1), но не платит за выборки,
которые идут после. На листве San Miguel, где отбраковывается больше половины фрагментов, это
экономит заметно.

## 4.9. Привязка материала к вызову

```cpp
cmd->setRenderPipeline(material.twoSided ? pipelineTwoSided : pipelineCulled);
cmd->setVertexBuffer(0, vertexBuffer);

for (const MeshSubset& subset : mesh.subsets) {
    const MeshMaterial& material = materialOf(subset);

    DrawConstants constants{};
    std::copy(mvp.begin(), mvp.end(), constants.modelViewProjection);
    constants.baseColor[0] = material.baseColor[0];
    constants.baseColor[1] = material.baseColor[1];
    constants.baseColor[2] = material.baseColor[2];
    constants.baseColor[3] = material.opacity;
    constants.flags[0] = material.albedoTexture.empty() ? 0.0f : 1.0f;
    constants.flags[1] = material.alphaMasked           ? 1.0f : 0.0f;
    constants.flags[2] = material.roughness;

    cmd->setTexture(0, ShaderStage::Fragment, cache.get(material.albedoTexture), repeatSampler);
    cmd->setTexture(1, ShaderStage::Fragment, cache.get(material.alphaTexture),  repeatSampler);

    cmd->setPushConstants(ShaderStage::Vertex,   &constants, sizeof(constants));
    cmd->setPushConstants(ShaderStage::Fragment, &constants, sizeof(constants));

    cmd->drawIndexed(indexBuffer, IndexType::UInt32, subset.indexCount, 1,
                     subset.firstIndex * sizeof(uint32_t), 0, 0);
}
```

**Всегда привязывайте обе текстуры, даже когда вторая не нужна.** Именно поэтому `cache.get()` на
пустом пути возвращает заглушку 1×1, а не `nullptr`. Слот, объявленный в шейдере, но не
привязанный, — это ошибка слоя валидации на Vulkan и неопределённое поведение на Metal. Заглушка
1×1 занимает 4 байта и снимает целый класс проблем.

Переключение пайплайна вынесено **из** цикла, потому что смена состояния дороже смены
push-констант. Если материалы отсортировать по признаку двусторонности, переключение произойдёт
один раз, а не на каждом подмножестве. Про сортировку — следующая глава.

## 4.10. Что обычно ломается

| Симптом | Причина |
|---|---|
| Сцена без единой текстуры, ошибок нет | Обратные слэши в MTL; не заменены на прямые |
| Картинка выцветшая, тени слишком светлые | Не сделан декод sRGB для альбедо |
| Картинка тёмная и контрастная | Декод сделан **дважды**, или забыто кодирование на выходе |
| Освещение «плоское», рельеф неправильный | Декод sRGB применён к карте нормалей |
| Муар на полу вдали | Нет мипов: не передан `initialData` или `mipLevels` остался равным 1 |
| Пол смазан в кашу при взгляде вдоль | Нет анизотропной фильтрации — ограничение обёртки |
| Рваные края у листвы | BC1 с однобитной альфой; нужен BC7 или несжатый формат |
| Часть текстур пурпурная | Файлы отсутствуют — так и задумано, смотрите лог |
| Приложение стало медленным после текстур | Вышли за бюджет VRAM; проверьте `memoryLocation()` |
| Ошибка валидации про непривязанный дескриптор | Слот объявлен в шейдере, но `setTexture` не вызван |

## 4.11. Проверка

1. **Sponza отображается со своими текстурами.** В логе — число загруженных текстур и время.
2. **Пурпурных пятен нет** (или вы точно знаете, какие файлы отсутствуют).
3. **Проверка гаммы.** Нарисуйте на экране прямоугольник с константным цветом `0.5` в линейном
   пространстве. После кодирования он должен на экране выглядеть примерно как 188/255, а не
   128/255. Если 128 — кодирование не применяется.
4. **Проверка мипов.** Отойдите камерой от пола. Без мипов — рябь и мерцание при движении, с
   мипами — плавное размытие. Разница видна мгновенно.
5. **Проверка бюджета.** Выведите `queryMemoryBudget()` в интерфейс. Убедитесь, что после
   загрузки Sponza `deviceLocalUsedBytes` вырос примерно на ожидаемую величину. Расхождение в
   разы означает, что где-то создаются лишние копии.

## Итог

1. Выборка из текстуры — работа отдельного блока. **Мипы, BC-сжатие и sRGB-декод там бесплатны**,
   и мипы ускоряют, а не замедляют.
2. Добавили `stb_image`. Всегда четыре канала, `kFullMipChain` плюс `initialData`.
3. **В обёртке нет несжатых sRGB-форматов**, поэтому декод и кодирование делаются в шейдере.
   Декодируется только цвет; карты нормалей и маски — никогда.
4. **Нет анизотропной фильтрации** — заметное ограничение на Sponza, первый кандидат на доработку.
5. Текстуры — основной потребитель VRAM. BC даёт выигрыш в 4–8 раз, но кодировщик надо добавлять
   отдельно.
6. Кеш текстур по каноническому пути и **заметная** заглушка для отсутствующих файлов.
