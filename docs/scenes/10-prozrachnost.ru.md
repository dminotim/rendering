# Часть X. Прозрачность

> **Цель главы.** Разобраться с двумя принципиально разными вещами, которые в обиходе называют
> одним словом. Первая — вырезание по маске: листва и цепи Sponza, решётки San Miguel. Вторая —
> настоящая полупрозрачность: стекло, вода, дым. У них разные проблемы и разные решения, и
> путаница между ними — источник половины дефектов в самодельных рендерерах.

---

## 10.1. Железо: почему прозрачность зависит от порядка

Смешивание выполняется в ROP — блоке вывода, за фрагментным шейдером. Формула фиксирована:

```
результат = src × srcFactor  ⊕  dst × dstFactor
```

`src` — то, что выдал шейдер, `dst` — то, что уже лежит в цели.

Ключевое свойство: ROP **атомарен по пикселю**. Аппаратура гарантирует, что фрагменты одного
пикселя смешиваются строго в порядке подачи. Без этой гарантии картинка менялась бы от кадра к
кадру.

Но гарантия порядка — это одновременно и проблема. Классическая формула «поверх»

```
результат = src × α + dst × (1 − α)
```

**некоммутативна**: `A over B ≠ B over A`. Красное стекло за синим и синее за красным дают разный
цвет. Значит, для корректной картинки геометрию надо подавать строго от дальней к ближней, а
единственный способ это узнать — отсортировать.

Отсюда все дальнейшие сложности. Непрозрачная геометрия сортировки не требует: буфер глубины
разрешает любой порядок. Прозрачная требует, а отсортировать не всегда возможно в принципе — два
пересекающихся треугольника не имеют правильного порядка вообще.

**На Apple Silicon смешивание дешевле** (глава 1): оно происходит в тайловой памяти, а не через
шину. Но проблема порядка от архитектуры не зависит — она математическая.

## 10.2. Вырезание по маске — и почему это не прозрачность

Листва Sponza — это плоские четырёхугольники с текстурой, где альфа говорит «здесь лист, а здесь
дырка». Смешивания нет: пиксель либо полностью непрозрачен, либо его нет вовсе.

```metal
if (alphaMap.sample(smp, in.uv).r < 0.5) discard_fragment();
```

Раз результат бинарен, **сортировка не нужна**: буфер глубины справляется. Cutout-геометрия по
сути непрозрачна и рисуется вместе с остальной непрозрачной.

Но одна проблема есть, и она из главы 1: **`discard_fragment()` отключает ранний тест глубины**.
Аппаратура не может заранее записать глубину, потому что не знает, выживет ли фрагмент.

Последствия для Sponza:

```
Без discard:  early-Z отбрасывает перекрытые фрагменты до шейдера.
              Overdraw ≈ 1.

С discard:    шейдер выполняется для КАЖДОГО фрагмента каждого листа,
              включая полностью скрытые.
              Overdraw в кроне дерева ≈ 5–10.
```

На San Miguel, где растительность занимает значительную часть кадра, это разница в разы.

### Предпроход глубины

Решение: сначала пройти по геометрии **только** заполняя буфер глубины, и лишь потом рисовать
цвет с уже готовым буфером.

```cpp
// Проход 1: только глубина. Фрагментного шейдера нет вовсе — для материалов
// без маски. Для материалов с маской он есть, но делает лишь discard.
PipelineDesc prepassDesc{};
prepassDesc.vertexFunction   = depthOnlyVertex;
prepassDesc.fragmentFunction = alphaTestOnlyFragment;   // только discard, без записи цвета
prepassDesc.targetFormat = RenderTargetFormat::singleTarget(
    ImageFormat::Undefined, kDepthFormat);              // цветовых целей нет
prepassDesc.depthStencil = DepthStencilState::depthTestAndWrite();
prepassDesc.depthStencil.depthCompareOp = CompareOp::Greater;   // reverse-Z

// Проход 2: цвет. Глубина уже готова — только тест, без записи.
PipelineDesc mainDesc{};
mainDesc.depthStencil.depthTestEnabled  = true;
mainDesc.depthStencil.depthWriteEnabled = false;
mainDesc.depthStencil.depthCompareOp    = CompareOp::Equal;     // ровно то, что в буфере
```

`CompareOp::Equal` в основном проходе означает: рисовать только там, где глубина в точности
совпадает с записанной в предпроходе, то есть **только на ближайшей поверхности**. Overdraw
становится ровно 1, и дорогой шейдер материала выполняется один раз на пиксель.

Тонкость: `Equal` требует, чтобы оба прохода вычисляли глубину **побитово одинаково**. Значит,
вершинный шейдер предпрохода должен считать позицию тем же кодом с теми же матрицами. Малейшее
расхождение (другой порядок умножения матриц, другая оптимизация) даст пиксели, где сравнение не
проходит, и появятся дыры. Если такое случилось, замените на `GreaterOrEqual` — чуть слабее, но
устойчиво.

Цена предпрохода — ещё одна растеризация всей геометрии. Окупается, когда фрагментный шейдер
дорогой (полная BRDF, много текстур) и overdraw заметный. В отложенной схеме из главы 8 геометрический
проход уже играет роль предпрохода, поэтому отдельный нужен реже.

### Пороговое значение и мипы

Ещё одна тонкость, из-за которой листва «худеет» вдали. Альфа-маска с мипами усредняется: на
дальних уровнях тонкий лист даёт альфу порядка 0.3, и порог 0.5 её отбрасывает. Крона редеет по
мере удаления.

Промышленное решение — **alpha-to-coverage** вместе с MSAA: покрытие пикселя определяется альфой
на уровне выборок, и переход получается плавным. В нашей обёртке этого нет: в `PipelineDesc` нет
поля `alphaToCoverage`.

Доступное смягчение — масштабировать порог по уровню мипа, повышая эффективную альфу на дальних
уровнях:

```metal
float alpha = alphaMap.sample(smp, in.uv).r;

// Оценка уровня мипа по производным UV — тем самым, что аппаратура
// использует для выбора уровня (глава 5).
const float2 dx = dfdx(in.uv) * float2(alphaMap.get_width(), alphaMap.get_height());
const float2 dy = dfdy(in.uv) * float2(alphaMap.get_width(), alphaMap.get_height());
const float lod = 0.5 * log2(max(dot(dx, dx), dot(dy, dy)));

// Чем дальше — тем ниже порог, компенсируя усреднение мипов.
const float threshold = mix(0.5, 0.25, saturate(lod / 6.0));
if (alpha < threshold) discard_fragment();
```

Не идеально, но заметно лучше фиксированного порога, и на San Miguel разница видна сразу.

## 10.3. Настоящая полупрозрачность

Здесь смешивание реально, и порядок важен.

```cpp
PipelineDesc desc{};
desc.blendStates = { BlendState::alphaBlend() };

// Глубину ТЕСТИРУЕМ, но не ПИШЕМ. Прозрачная поверхность не должна
// закрывать то, что за ней, — иначе следующая прозрачная за ней не нарисуется.
desc.depthStencil.depthTestEnabled  = true;
desc.depthStencil.depthWriteEnabled = false;
desc.depthStencil.depthCompareOp    = CompareOp::GreaterOrEqual;   // reverse-Z
```

> **Внимание при reverse-Z.** Готовый `DepthStencilState::depthTestOnly()` в обёртке использует
> `CompareOp::LessOrEqual` — это для обычного Z. При reverse-Z нужен `GreaterOrEqual`. Симптом
> ошибки: прозрачные объекты видны только там, где за ними ничего нет.

Порядок в кадре:

```
1. Непрозрачная геометрия (+ cutout) → буфер глубины заполнен
2. Освещение
3. Прозрачная геометрия, отсортированная СЗАДИ НАПЕРЁД,
   с тестом глубины против непрозрачной, но без записи
```

Сортировка уже заложена в ключ из главы 6: старший бит отделяет прозрачное, а направление
сортировки по глубине для него обратное.

### Отложенный рендеринг и прозрачность несовместимы

Стоит сказать это прямо. В G-буфер на пиксель помещается **одна** поверхность. Прозрачная
поверхность и то, что за ней, — это две, и записать обе некуда.

Единственный рабочий подход — **гибридная схема**:

```
Проход 1: G-буфер     (непрозрачное)
Проход 2: освещение   (объёмы источников → HDR)
Проход 3: прямой      (прозрачное, поверх HDR, с полным освещением в шейдере)
```

То есть для прозрачных материалов нужен **второй комплект шейдеров**, считающий освещение прямым
способом. Со всеми ограничениями главы 7: много источников — дорого. На практике прозрачную
геометрию освещают упрощённо — двумя-тремя ближайшими источниками, — и это почти незаметно,
потому что она полупрозрачна.

Проход 3 подключает буфер глубины от геометрического прохода с `clear = false`:

```cpp
std::shared_ptr<RenderPassDescriptor> transparentPass = helper::createRenderPassDescriptor();
transparentPass->setColorAttachment(0, hdrTarget, /*clear=*/false, blackClear);
// Глубина от G-буфера, НЕ очищаем: она нужна для теста.
transparentPass->setDepthStencilAttachment(gbuffer.depthStencil,
                                           /*clearDepth=*/false, 0.0f, false, 0);
```

> **Про `clear = false` на TBDR.** На Apple Silicon отказ от очистки означает **загрузку** тайла
> из памяти в начале прохода — это дороже, чем очистка. Здесь загрузка неизбежна (нам нужно и
> накопленное освещение, и глубина), но не ставьте `clear = false` там, где содержимое не нужно.

## 10.4. Пределы сортировки

Сортировка по объектам решает проблему на 90 % и проваливается на оставшихся 10 %. Провалы стоит
знать в лицо.

**Пересекающиеся объекты.** Два прозрачных объекта, проходящих друг сквозь друга, не имеют
правильного порядка: для одной части экрана верен один, для другой — другой.

**Вогнутые объекты.** У бокала передняя и задняя стенки — один объект. Какой бы порядок ни
выбрали, внутри объекта грани пойдут в порядке буфера.

**Пересекающиеся треугольники.** Даже сортировка по треугольникам не спасает.

Полумеры, которые применяют на практике:

- **Разделять модель на выпуклые части** при подготовке ассета.
- **Рисовать в два прохода** — сначала задние грани (`CullMode::Front`), потом передние
  (`CullMode::Back`). Для одиночного выпуклого объекта вроде бокала это даёт правильный
  результат почти всегда и стоит одного лишнего вызова.
- **Смириться.** Для дыма, стекла и воды ошибки порядка редко заметны — эти материалы
  малоконтрастны, и перепутанный порядок даёт близкий результат.

## 10.5. Взвешенное смешивание без сортировки (OIT)

Приём Макгвайра и Бавойла: приближённое смешивание, **не зависящее от порядка**. Идея — заменить
некоммутативную формулу «поверх» на взвешенную сумму, которая коммутативна по построению, и
подобрать веса так, чтобы результат был близок к правильному.

В нашей обёртке реализуется полностью — нужны две цели с **разными** режимами смешивания, а
`PipelineDesc::blendStates` задаёт режим на каждое вложение.

### Цели накопления

```cpp
// Накопление взвешенного цвета. Нужен float: суммы выходят за [0, 1].
ImageDesc accumDesc{};
accumDesc.format = ImageFormat::RGBA16_FLOAT;
accumDesc.usage  = ImageUsage::ColorTarget | ImageUsage::Sampled;
// ... размер ...
std::shared_ptr<GImage> accumTarget = device->createImage(accumDesc);

// Накопление «просвета»: произведение (1 − α) по всем слоям.
ImageDesc revealDesc = accumDesc;
revealDesc.format = ImageFormat::R32_FLOAT;
std::shared_ptr<GImage> revealTarget = device->createImage(revealDesc);
```

### Режимы смешивания

```cpp
PipelineDesc oitDesc{};
oitDesc.targetFormat = RenderTargetFormat::multiTarget(
    { ImageFormat::RGBA16_FLOAT, ImageFormat::R32_FLOAT }, kDepthFormat);

BlendState accumBlend{};                       // цель 0: обычное сложение
accumBlend.enabled = true;
accumBlend.srcColorFactor = BlendFactor::One;
accumBlend.dstColorFactor = BlendFactor::One;
accumBlend.srcAlphaFactor = BlendFactor::One;
accumBlend.dstAlphaFactor = BlendFactor::One;

BlendState revealBlend{};                      // цель 1: перемножение (1 − α)
revealBlend.enabled = true;
revealBlend.srcColorFactor = BlendFactor::Zero;
revealBlend.dstColorFactor = BlendFactor::OneMinusSrcColor;
revealBlend.srcAlphaFactor = BlendFactor::Zero;
revealBlend.dstAlphaFactor = BlendFactor::OneMinusSrcColor;

oitDesc.blendStates = { accumBlend, revealBlend };

oitDesc.depthStencil.depthTestEnabled  = true;
oitDesc.depthStencil.depthWriteEnabled = false;
oitDesc.depthStencil.depthCompareOp    = CompareOp::GreaterOrEqual;
```

Смешивание `dst × (1 − src)` при записи `src = α` превращает накопление в произведение
`Π(1 − αᵢ)` — то есть в долю фона, оставшуюся видимой. Цель просвета очищается **единицей**
(«видно 100 % фона»), цель накопления — нулём.

### Шейдер накопления

```metal
struct OitOut {
    float4 accum  [[color(0)]];
    float  reveal [[color(1)]];
};

fragment OitOut oit_accumulate(TransparentVertexOut in [[stage_in]],
                               constant SceneUniforms& scene [[buffer(1)]],
                               constant DrawConstants& draw  [[buffer(8)]],
                               texture2d<float> albedoMap [[texture(0)]],
                               sampler smp [[sampler(0)]])
{
    const float4 sample = albedoMap.sample(smp, in.uv);
    const float  alpha  = sample.a * draw.baseColor.a;

    const float3 shaded = shadeTransparent(in, scene, draw, sample.rgb);

    // Вес: ближние слои весомее дальних, и вес быстро спадает.
    // Формула из статьи; константы подобраны эмпирически и работают
    // для диапазона глубин порядка [0.1, 500].
    const float z = in.viewDepth;
    const float weight = clamp(pow(min(1.0, alpha * 10.0) + 0.01, 3.0) *
                               1e8 * pow(1.0 - z * 0.9, 3.0), 1e-2, 3e3);

    OitOut out;
    out.accum  = float4(shaded * alpha, alpha) * weight;
    out.reveal = alpha;
    return out;
}
```

### Проход сведения

```metal
fragment float4 oit_composite(FullscreenOut in [[stage_in]],
                              texture2d<float> accumMap  [[texture(0)]],
                              texture2d<float> revealMap [[texture(1)]],
                              sampler smp [[sampler(0)]])
{
    const float reveal = revealMap.sample(smp, in.uv).r;

    // Ничего прозрачного здесь не было — оставляем фон нетронутым.
    if (reveal > 0.9999) discard_fragment();

    const float4 accum = accumMap.sample(smp, in.uv);
    const float3 color = accum.rgb / max(accum.a, 1e-5);

    // Смешивание при выводе: src = OneMinusSrcAlpha, dst = SrcAlpha,
    // где в альфу мы кладём reveal. Итог: color·(1−reveal) + фон·reveal.
    return float4(color, reveal);
}
```

Пайплайн сведения:

```cpp
BlendState compositeBlend{};
compositeBlend.enabled = true;
compositeBlend.srcColorFactor = BlendFactor::OneMinusSrcAlpha;
compositeBlend.dstColorFactor = BlendFactor::SrcAlpha;
compositeBlend.srcAlphaFactor = BlendFactor::OneMinusSrcAlpha;
compositeBlend.dstAlphaFactor = BlendFactor::SrcAlpha;
```

### Честная оценка

**Плюсы.** Сортировка не нужна вообще. Пересечения, вогнутость, взаимопроникновение — всё
работает. Стоимость не зависит от числа слоёв. Два дополнительных вызова на кадр.

**Минусы.** Это приближение. При сильно различающихся альфах порядок «размывается»: близкое
стекло не выглядит настолько ближе, насколько должно. Веса подобраны под определённый диапазон
глубин, и на сцене с другим масштабом их надо перенастраивать — а это подгонка, что для книги,
построенной на выводе из физики, неприятно, но честно.

**Память.** RGBA16F + R32F в полном разрешении = 12 байт на пиксель, ещё 44 МБ при 2560×1440.

**Практический совет.** Держите оба пути и переключайте по материалу: стекло и вода —
отсортированное смешивание (их мало, и качество важно), дым и частицы — OIT (их много, и порядок
между ними всё равно не разобрать).

## 10.5a. Развлечение: растворение

Самое известное применение `discard` за пределами листвы — эффект растворения: объект исчезает,
разъедаемый рваной границей, которая светится по краю. Строится он ровно из того, что уже
разобрано в этой главе, плюс одна функция шума.

```metal
// Хеш-шум: детерминированный псевдослучайный float из трёх координат.
// Никаких текстур — всё считается на месте.
float hash13(float3 p)
{
    p = fract(p * 0.1031);
    p += dot(p, p.yzx + 33.33);
    return fract((p.x + p.y) * p.z);
}

// Шум с интерполяцией: хеш в узлах решётки, плавный переход между ними.
float valueNoise(float3 p)
{
    const float3 i = floor(p);
    const float3 f = fract(p);
    // Кубическое сглаживание: производная на границах ячеек равна нулю,
    // поэтому решётка не проступает полосами.
    const float3 u = f * f * (3.0 - 2.0 * f);

    return mix(mix(mix(hash13(i + float3(0,0,0)), hash13(i + float3(1,0,0)), u.x),
                   mix(hash13(i + float3(0,1,0)), hash13(i + float3(1,1,0)), u.x), u.y),
               mix(mix(hash13(i + float3(0,0,1)), hash13(i + float3(1,0,1)), u.x),
                   mix(hash13(i + float3(0,1,1)), hash13(i + float3(1,1,1)), u.x), u.y), u.z);
}

struct DissolveParams {
    float4x4 modelViewProjection;
    float4   settings;   // x: прогресс 0..1, y: масштаб шума,
                         // z: толщина каймы, w: не используется
    float4   edgeColor;
};

fragment float4 dissolve_fragment(VertexOut in [[stage_in]],
                                  constant DissolveParams& params [[buffer(8)]],
                                  texture2d<float> albedoMap [[texture(0)]],
                                  sampler          smp       [[sampler(0)]])
{
    const float noise = valueNoise(in.worldPosition * params.settings.y);
    const float progress = params.settings.x;

    // Всё, что «шумнее» порога, уже исчезло.
    if (noise < progress) discard_fragment();

    float3 color = albedoMap.sample(smp, in.uv).rgb;

    // Кайма: узкая полоса перед фронтом растворения. Светится тем ярче,
    // чем ближе к краю. Именно она делает эффект читаемым — без неё
    // объект просто дырявится.
    const float edge = 1.0 - smoothstep(progress, progress + params.settings.z, noise);
    color = mix(color, params.edgeColor.rgb * 4.0, edge);   // >1: уйдёт в HDR и в свечение

    return float4(color, 1.0);
}
```

Три вещи, которые стоит унести:

**Шум в мировых координатах, а не в UV.** Тогда размер клочьев не зависит от развёртки и
одинаков на всех частях модели. Тот же довод, что у трипланарного наложения из главы 5.

**Кайма ярче единицы.** Умножение на 4 выводит её за пределы [0, 1], и в HDR-конвейере из главы 7
она станет источником свечения (глава 12) без единой дополнительной строки. Так и задумано:
светящийся край — это не «эффект свечения», это просто яркий пиксель, с которым дальше разберётся
постобработка.

**Здесь `discard` уместен, а в основном материале — нет.** Растворяющийся объект и так особый:
их единицы, они не заслоняют пол-экрана, и потеря early-Z (раздел 10.2) на них ничего не стоит.
Это тот случай, когда правило «избегайте `discard`» осознанно нарушается — потому что понятно,
чем именно платим.

Ползунок `progress` в ImGui, и весь эффект готов. Поменяйте `valueNoise` на `abs(sin(p.y * 8))`
— получится растворение горизонтальными полосами; на `length(p - center)` — сферической волной от
точки.

## 10.6. Материалы Sponza: что чем является

Практическая классификация, применимая ко всем сценам архива.

```cpp
enum class MaterialBlendMode { Opaque, Cutout, Transparent };

MaterialBlendMode classify(const MeshMaterial& material)
{
    // Есть маска в отдельной текстуре — вырезание.
    if (!material.alphaTexture.empty()) return MaterialBlendMode::Cutout;

    // d < 1 в MTL — настоящая полупрозрачность.
    if (material.opacity < 0.999f) return MaterialBlendMode::Transparent;

    // Альфа-канал внутри альбедо: определить статически нельзя — надо смотреть
    // на сами данные. Прагматично: считать cutout, если в текстуре есть
    // значения альфы строго между 0 и 1, и Opaque, если альфа везде 1.
    if (material.albedoHasVaryingAlpha) return MaterialBlendMode::Cutout;

    return MaterialBlendMode::Opaque;
}
```

Последняя проверка — не запасной вариант, а **основной**, и вот почему.

В MTL нет способа объявить материал вырезаемым иначе как через `map_d`. У San Miguel `map_d` в
файле материалов **не встречается ни разу**: маска листвы лежит в альфа-канале самой альбедо-карты.
То есть файл про вырезание не говорит ничего, и единственный источник истины — пиксели.

На практике: из 281 материала сцены признак «в альбедо есть значения альфы строго между полной
прозрачностью и полной непрозрачностью» срабатывает у **97**. Без этой проверки все девяносто
семь рисуются как непрозрачные прямоугольники — вся растительность двора превращается в
картонные щиты.

Проверка требует анализа пикселей при загрузке — один проход по данным, дешёвый по сравнению с
самой распаковкой:

```cpp
bool detectVaryingAlpha(const uint8_t* rgba, size_t pixelCount)
{
    bool sawTransparent = false;
    for (size_t i = 0; i < pixelCount; ++i) {
        const uint8_t a = rgba[i * 4 + 3];
        if (a < 250) { sawTransparent = true; break; }
    }
    return sawTransparent;
}
```

В Crytek Sponza по маске вырезаются растения в вазонах, свисающие цепи и ткань драпировок. В San
Miguel — вся растительность двора: 97 материалов из 281, и ни одного объявленного в MTL.

Важное следствие для главы 9: **вариант теневого шейдера с `discard` обязателен**. Крона, которая
в основном проходе вырезана правильно, но в теневом нарисована сплошным четырёхугольником, кладёт
на землю прямоугольную плиту вместо кружевной тени — и это первое, что выдаёт самодельные тени.

Напомню эвристику из главы 4: **материал с маской считаем двусторонним** (`CullMode::None`).
Листья и ткань смоделированы односторонними плоскостями, и с отсечением половина их пропадёт.

## 10.7. Что обычно ломается

| Симптом | Причина |
|---|---|
| Прозрачные видны только там, где за ними пусто | `LessOrEqual` вместо `GreaterOrEqual` при reverse-Z |
| Прозрачные скрывают друг друга | Включена запись глубины |
| Прозрачные исчезли за непрозрачными | Порядок проходов или прозрачность не в старшем бите ключа |
| Порядок слоёв неправильный | Не отсортировано сзади наперёд, либо объекты пересекаются |
| Резкий провал FPS на растительности | `discard` убил early-Z; нужен предпроход глубины |
| Дыры в геометрии после предпрохода | `CompareOp::Equal` при расходящемся вычислении позиции |
| Листва редеет вдали | Фиксированный порог с мипами; нужна поправка по уровню |
| Половина листьев не видна | Не выключено отсечение для двусторонних материалов |
| OIT: всё серое и плоское | Цель просвета очищена нулём вместо единицы |
| OIT: прозрачное чёрное | Делят на `accum.a` без защиты, либо цели не float |
| Прозрачное не освещено | В отложенной схеме для него нужен отдельный прямой шейдер |

---

## 10.8. Проверка

1. **Три цветных полупрозрачных плоскости** одна за другой. Меняйте порядок отрисовки: при
   сортировке картинка не должна меняться, без сортировки — должна.
2. **Сравнение OIT и сортировки** на тех же плоскостях. OIT даст близкий, но не идентичный
   результат — это ожидаемо, и полезно увидеть величину расхождения.
3. **Пересекающиеся объекты.** Два прозрачных куба, проходящих друг сквозь друга. Сортировка
   покажет шов, OIT — нет. Наглядная демонстрация того, ради чего OIT нужен.
4. **Измерьте предпроход.** Время кадра с ним и без него на виде, где крона занимает пол-экрана.
   Если предпроход не окупился — значит, overdraw мал, и он не нужен.
5. **Проверка порога.** Отойдите камерой от растения. Крона не должна заметно редеть.

## Итог

1. Вырезание по маске и полупрозрачность — **разные** вещи. Первое сортировки не требует, второе
   требует.
2. `discard` отключает early-Z. Лечится **предпроходом глубины** с `CompareOp::Equal` в основном
   проходе.
3. Полупрозрачность: тест глубины **без записи**, сортировка сзади наперёд, `GreaterOrEqual` при
   reverse-Z.
4. **Отложенный рендеринг прозрачность не поддерживает.** Нужен третий, прямой проход и второй
   комплект шейдеров.
5. Сортировка по объектам ломается на пересечениях и вогнутости. Взвешенное OIT снимает проблему
   порядка ценой приближения; в нашей обёртке реализуется через разные режимы смешивания на разных
   вложениях.
6. Материалы с маской в сценах архива считаем **двусторонними**.
