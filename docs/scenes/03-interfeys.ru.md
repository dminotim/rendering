# Часть III. Интерфейс

> **Цель главы.** Разобрать, как Dear ImGui встраивается в наш кадр: почему у него **два**
> бэкенда, а не один, кто из них дружит с GLFW и как именно, в каком порядке идут вызовы внутри
> кадра и почему любая перестановка ломается. Отдельно — самое неочевидное: как ImGui перехватывает
> ввод у GLFW и почему порядок регистрации колбэков решает, будет ли работать ваша камера.
> К концу главы над треугольником из главы 2 появится панель, которая им управляет, и мышь
> перестанет одновременно крутить камеру и тащить ползунок.

Глава стоит здесь, а не в конце, по одной причине: **отладочный интерфейс — это инструмент, а не
украшение.** Начиная с главы 4 каждая следующая тема требует что-нибудь покрутить — смещение теней
в текселях, экспозицию, порог альфа-теста, номер каскада для отладочной раскраски. Без панели это
означает пересборку на каждое значение, и глава про тени превращается в сорок пересборок.

---

## 3.1. Почему интерфейс вообще внутри обёртки

Логично было бы ожидать, что ImGui — дело приложения: он рисует свои треугольники, приложение их
показывает. Но посмотрите на список того, что ImGui нужно знать, чтобы нарисовать хоть один
прямоугольник:

- на Vulkan — `VkInstance`, `VkPhysicalDevice`, `VkDevice`, индекс семейства очередей, саму очередь,
  descriptor pool, **совместимый render pass** и количество изображений свопчейна;
- на Metal — `id<MTLDevice>` и, каждый кадр, `MTLRenderPassDescriptor`, чтобы узнать формат
  пикселей цели.

Это ровно тот набор, который обёртка существует чтобы спрятать. Если отдать интеграцию приложению,
приложение обязано снова получить все эти нативные объекты — и весь смысл абстракции исчезает.

Поэтому в обёртке есть четыре функции, и приложение видит только их:

```cpp
bool initImgui(const std::shared_ptr<SwapChain>& swapChain);
bool newFrameImgui(const std::shared_ptr<RenderPassDescriptor>& passDesc);
bool renderInternalImgui(const std::shared_ptr<CommandBuffer>& commandBuffer);
bool shutdownImgui();
```

Ни одного нативного типа в сигнатурах. Внутри — `#if defined(__APPLE__)` и развилка на
`InitImguiMetal` / `InitImguiVulkan`, и это единственное место во всём проекте, где такая развилка
для интерфейса встречается.

## 3.2. Три части, а не одна

Здесь ломается интуиция большинства. ImGui — не одна библиотека, а **три слоя**, и их надо
инициализировать по отдельности.

```
┌─────────────────────────────────────────────────────────┐
│  Ядро ImGui                                             │
│  ImGui::CreateContext(), ImGui::Begin(), SliderFloat()…  │
│  Знает только о состоянии и о списках вершин.            │
│  Ни окон, ни GPU.                                       │
└─────────────────────────────────────────────────────────┘
            ▲                              ▲
            │                              │
┌───────────────────────────┐  ┌───────────────────────────┐
│  Платформенный бэкенд     │  │  Рендер-бэкенд            │
│  imgui_impl_glfw          │  │  imgui_impl_vulkan   ИЛИ  │
│                           │  │  imgui_impl_metal         │
│  Мышь, клавиатура, размер │  │  Буферы, текстура шрифта, │
│  окна, курсоры, буфер     │  │  пайплайн, вызовы         │
│  обмена. Через GLFW.      │  │  отрисовки.               │
└───────────────────────────┘  └───────────────────────────┘
       ↑ приложение                    ↑ обёртка
```

Разделение ответственности здесь не наше — оно заложено в ImGui. И именно оно объясняет, **почему
одну половину инициализирует приложение, а вторую обёртка**:

- **платформенный** бэкенд работает с `GLFWwindow*` — окно создало приложение, значит и
  `ImGui_ImplGlfw_Init` вызывает оно;
- **рендер-бэкенд** работает с устройством и проходом — их создала обёртка, значит и
  `ImGui_ImplVulkan_Init` / `ImGui_ImplMetal_Init` вызывает она, через `helper::initImgui`.

Ядро при этом одно и общее: **один контекст** на процесс. Об этом ниже (3.9) — на этом проще всего
споткнуться, если собрать ImGui дважды.

## 3.3. Инициализация: три вызова в правильном порядке

```cpp
ImGui::CreateContext();                          // 1. ядро
ImGui_ImplGlfw_InitForOther(window, true);       // 2. платформа
// … создание swapChain …
helper::initImgui(swapChain);                    // 3. рендер (внутри обёртки)
```

Порядок обязателен, и каждая позиция объясняется одним фактом.

**`CreateContext()` первым**, потому что оба бэкенда при инициализации пишут в контекст: они
регистрируют себя в `ImGuiIO`, выставляют флаги возможностей (`BackendFlags_HasMouseCursors` и
прочие). Без контекста писать некуда.

**`initImgui(swapChain)` после свопчейна** — и это не формальность подписи. На Vulkan бэкенду нужны
две вещи, которые существуют только вместе со свопчейном:

```cpp
initInfo.RenderPass  = vulkanSwapChain->presentationRenderPass();
initInfo.ImageCount  = vulkanSwapChain->imageCount();
```

ImGui собирает **свой собственный графический пайплайн** прямо в `ImGui_ImplVulkan_Init`, а
пайплайн в Vulkan запекается под конкретный совместимый render pass. Нет свопчейна — нет прохода —
нечего передать. На Metal этого ограничения нет (там нужен только девайс, а формат пикселей
сообщается каждый кадр), но подпись у обеих реализаций общая, и по ней видно жёсткое требование, а
не самое слабое.

### Про `InitForOther`, а не `InitForVulkan`

Мы вызываем `ImGui_ImplGlfw_InitForOther` на **обеих** платформах, хотя рядом есть
`InitForVulkan`. Это не небрежность. Все три варианта — `InitForOpenGL`, `InitForVulkan`,
`InitForOther` — вызывают одну и ту же внутреннюю функцию, отличаясь единственным аргументом:

```cpp
bool ImGui_ImplGlfw_InitForVulkan(GLFWwindow* window, bool install_callbacks)
{ return ImGui_ImplGlfw_Init(window, install_callbacks, GlfwClientApi_Vulkan); }

bool ImGui_ImplGlfw_InitForOther(GLFWwindow* window, bool install_callbacks)
{ return ImGui_ImplGlfw_Init(window, install_callbacks, GlfwClientApi_Unknown); }
```

`GlfwClientApi` влияет только на многооконный режим ImGui (viewports), где ImGui сам создаёт
дополнительные окна и должен знать, какой API у них запрашивать. Мы viewports не используем, значит
`Unknown` — честное значение, и оно одинаково верно для Vulkan и для Metal. Один вызов на обе
платформы вместо развилки.

### Про второй аргумент `true`

Он важнее, чем выглядит, и ему посвящён раздел 3.7. Пока достаточно: `true` означает «ImGui, поставь
свои колбэки GLFW сам».

### Порядок при завершении

Обратный, и тоже строго:

```cpp
helper::shutdownImgui();      // рендер-бэкенд: освободить пайплайн, пул, текстуру шрифта
ImGui_ImplGlfw_Shutdown();    // платформа: снять колбэки, вернуть предыдущие
ImGui::DestroyContext();      // ядро: последним, в него пишут оба
```

Причина та же, что и при инициализации, только в другую сторону: оба бэкенда при выключении
**пишут в контекст** (вычищают из `ImGuiIO` свои указатели), поэтому уничтожать контекст можно
только когда оба уже отработали. `DestroyContext()` первым — обращение к освобождённой памяти.

## 3.4. Кадр: пять вызовов и почему именно в таком порядке

Это место, где ошибаются чаще всего, потому что вызовы выглядят взаимозаменяемыми. Они не
взаимозаменяемы.

```cpp
// ── 1. проход, в который интерфейс будет нарисован ──
auto uiPass = helper::createRenderPassDescriptor();
uiPass->setColorAttachment(0, target, /*clear=*/false, clearColor);

// ── 2. открыть кадр ImGui ──
helper::newFrameImgui(uiPass);      // рендер-бэкенд
ImGui_ImplGlfw_NewFrame();          // платформа
ImGui::NewFrame();                  // ядро

// ── 3. описать интерфейс ──
ImGui::Begin("Настройки");
ImGui::SliderFloat("Экспозиция", &exposure, 0.05f, 6.0f);
ImGui::End();

// ── 4. превратить описание в вершины ──
ImGui::Render();

// ── 5. записать эти вершины в командный буфер ──
cmd->beginRenderPass(uiPass);
helper::renderInternalImgui(cmd);
cmd->endRenderPass();
```

**Проход создаётся до `newFrameImgui`.** Причина видна в реализации для Metal:

```objc
bool NewFrameImguiMetal(const std::shared_ptr<RenderPassDescriptor>& passDesc)
{
    auto mtlPass = (MTLRenderPassDescriptor*)passDesc->nativeHandle();
    ImGui_ImplMetal_NewFrame(mtlPass);
    return true;
}
```

Metal-бэкенд ImGui читает из дескриптора **формат пикселей цели**, чтобы при необходимости
собрать под него пайплайн. Значит дескриптор должен быть заполнен *раньше*. На Vulkan аргумент
игнорируется — там формат сообщили ещё в `initImgui` — и в коде это сказано прямо:

```cpp
bool NewFrameImguiVulkan(const std::shared_ptr<RenderPassDescriptor>& /*passDesc*/)
```

Асимметрия настоящая: подпись рассчитана на более требовательный бэкенд.

**`clear = false` во втором аргументе `setColorAttachment`.** Интерфейс рисуется **поверх** уже
готового кадра. Поставьте `true` — и панель окажется на пустом фоне, а сцена исчезнет: проход
очистит цель перед отрисовкой. Это самая частая ошибка при добавлении интерфейса, и выглядит она
как «пропала вся сцена, когда я включил ImGui».

**Три `NewFrame` — не дублирование.** Каждый делает свою работу: рендер-бэкенд при необходимости
догружает текстуру шрифта, платформенный опрашивает GLFW (размер окна, положение мыши, масштаб
дисплея) и складывает события в `ImGuiIO`, ядро сбрасывает состояние прошлого кадра. Ядро **всегда
последним**: оно потребляет то, что положили первые два.

**`ImGui::Render()` не рисует.** Название обманывает. Он превращает накопленные команды в
`ImDrawData` — списки вершин и индексов — и ничего не отправляет на GPU. Отправляет
`renderInternalImgui`, который внутри вызывает `ImGui_ImplMetal_RenderDrawData(ImGui::GetDrawData(), …)`.
Отсюда правило: **`Render()` до `beginRenderPass`, `renderInternalImgui` внутри прохода.** Забыть
`Render()` — панель не появится, и никакой ошибки не будет.

### Отдельный проход или тот же?

В примере выше интерфейс идёт **вторым проходом** по той же цели. Можно и одним — дорисовать
интерфейс в конце прохода сцены. Разница практическая:

| | Отдельный проход | В конце прохода сцены |
|---|---|---|
| MSAA | цель уже сведена, интерфейс резкий и без лишней работы | панель сглаживается вместе со сценой, зря |
| Стоимость | ещё один load/store тайла на Apple Silicon | бесплатно |
| Порядок | интерфейс гарантированно сверху | зависит от порядка вызовов |

Мы берём отдельный проход. На тайловой архитектуре это не бесплатно (глава 1), но
многовыборочный путь того стоит: сглаживать текст панели нет смысла, а разрешать
сведённую цель ради интерфейса — лишняя копия.

## 3.5. Первая панель поверх треугольника

Соберём главу 2 и эту вместе. Треугольник из главы 2 получал цвет через push-константы —
теперь этим цветом можно управлять.

```cpp
struct TriangleControls {
    float color[3] = { 0.9f, 0.4f, 0.2f };
    float scale = 1.0f;
    bool  wireframe = false;
};
TriangleControls controls;
```

В кадре, между `ImGui::NewFrame()` и `ImGui::Render()`:

```cpp
ImGui::Begin("Треугольник");

// Числа в интерфейсе выравниваются по разрядам сами: ImGui использует моноширинный
// шрифт для значений, так что "0.900" и "-1.250" не прыгают.
ImGui::ColorEdit3("Цвет", controls.color);
ImGui::SliderFloat("Масштаб", &controls.scale, 0.1f, 3.0f);
ImGui::Checkbox("Сетка", &controls.wireframe);

ImGui::Separator();
ImGui::Text("%.1f FPS (%.2f мс)",
            ImGui::GetIO().Framerate,
            1000.0f / std::max(ImGui::GetIO().Framerate, 1e-3f));

ImGui::End();
```

Обратите внимание на две вещи, которые определяют весь стиль работы с ImGui.

**Виджеты принимают указатели на ваши переменные.** `SliderFloat("Масштаб", &controls.scale, …)` —
это не «создать ползунок и потом спросить значение». Виджет **пишет прямо в вашу переменную** в
момент вызова. Никакого хранилища состояния на вашей стороне не нужно, и никакой синхронизации:
после `ImGui::End()` в `controls.scale` уже новое значение, и его можно тут же положить в
push-константы.

**Интерфейс не «создаётся», он описывается каждый кадр.** Нет объектов-виджетов, нет `addWidget`,
нет коллбэков «по изменению». Есть функция, которая каждый кадр заново рассказывает, как выглядит
панель. Это и называется immediate mode. Отсюда следует то, из-за чего ImGui так удобен для
отладки: показать значение — одна строка `ImGui::Text` в том месте кода, где значение уже есть.

Счётчик кадров стоит вставлять сразу и не убирать: `io.Framerate` — усреднённое значение, и это
первое, что понадобится в главе 6, когда вызовов отрисовки станет много.

## 3.6. Что ImGui рисует физически

Стоит понимать, потому что это влияет на бюджет кадра из главы 1.

`ImGui::Render()` выдаёт **один** `ImDrawData` со списками команд. Внутри — вершины по 20 байт
(позиция `float2`, texcoord `float2`, цвет `uint32`) и 16-битные индексы. Всё рисуется
**треугольниками**, включая текст: каждый символ — два треугольника с выборкой из атласа шрифта.

Порядок величин для панели вроде нашей: 40–60 виджетов дают примерно 2–4 тысячи вершин и один-два
вызова отрисовки (ImGui сам склеивает всё, что использует одну текстуру и один прямоугольник
отсечения). На фоне сцены из главы 13 в десять миллионов треугольников это ничто.

Но одно место дорогое, и его видно только на тайловой архитектуре: **отдельный проход**.
Загрузить и выгрузить тайлы полноэкранной цели ради панели — фиксированные затраты, не зависящие
от числа виджетов. На Apple Silicon это единицы миллисекунд на 4K. Если интерфейс не нужен —
не открывайте проход вообще, а не рисуйте пустую панель:

```cpp
if (showInterface) {
    cmd->beginRenderPass(uiPass);
    helper::renderInternalImgui(cmd);
    cmd->endRenderPass();
}
```

Текстура шрифта — ещё один момент. Она догружается лениво, в первом
`ImGui_ImplVulkan_NewFrame()`, и в нашем Vulkan-бэкенде это специально отмечено:

```cpp
// The font atlas is uploaded lazily by ImGui_ImplVulkan_NewFrame(), so there is no
// one-off command buffer submission to do here.
```

Практический вывод: первый кадр с интерфейсом дороже остальных. При замерах времени кадра первый
кадр надо отбрасывать — иначе он попадёт в среднее и испортит его.

## 3.7. Ввод: как ImGui дружит с GLFW

Это самый неочевидный раздел главы, и та часть, из-за которой интерфейс «работает, но мышь
странная».

### Механика: цепочка колбэков

`ImGui_ImplGlfw_InitForOther(window, true)` — тот самый `true` — заставляет ImGui **поставить свои
колбэки GLFW**. Делает он это так:

```cpp
bd->PrevUserCallbackMousebutton = glfwSetMouseButtonCallback(window, ImGui_ImplGlfw_MouseButtonCallback);
bd->PrevUserCallbackKey         = glfwSetKeyCallback(window, ImGui_ImplGlfw_KeyCallback);
```

Ключевое: `glfwSetMouseButtonCallback` **возвращает предыдущий** колбэк, и ImGui его сохраняет. А
в своём обработчике первым делом вызывает сохранённый:

```cpp
void ImGui_ImplGlfw_MouseButtonCallback(GLFWwindow* window, int button, int action, int mods)
{
    ImGui_ImplGlfw_Data* bd = ImGui_ImplGlfw_GetBackendData();
    if (bd->PrevUserCallbackMousebutton != nullptr && ImGui_ImplGlfw_ShouldChainCallback(window))
        bd->PrevUserCallbackMousebutton(window, button, action, mods);

    ImGuiIO& io = ImGui::GetIO();
    io.AddMouseButtonEvent(button, action == GLFW_PRESS);
}
```

То есть ImGui не «захватывает» ввод, а **встраивается в цепочку**: ваш колбэк вызывается, затем
ImGui добавляет событие себе. Оба получают всё.

### Отсюда правило порядка, и оно жёсткое

> **Свои колбэки GLFW регистрируйте _до_ `ImGui_ImplGlfw_Init(..., true)`.**

Зарегистрируете после — ваш `glfwSetMouseButtonCallback` вернёт колбэк ImGui и **выбросит его**.
GLFW хранит по одному колбэку на событие; кто последний, тот и единственный. ImGui перестанет
получать нажатия — панель будет рисоваться, но не реагировать. Ни ошибки, ни предупреждения.

Симптом узнаваемый: **панель видно, ползунки не тащатся, кнопки не нажимаются, но подсветка при
наведении работает.** Подсветка работает потому, что позиция мыши читается опросом в
`ImGui_ImplGlfw_NewFrame()`, а нажатия приходят только колбэком.

Если порядок вам не подходит, есть второй путь: передать `false` и вызывать обработчики ImGui из
своих колбэков вручную —

```cpp
ImGui_ImplGlfw_InitForOther(window, false);
glfwSetMouseButtonCallback(window, [](GLFWwindow* w, int b, int a, int m) {
    ImGui_ImplGlfw_MouseButtonCallback(w, b, a, m);   // ImGui — явно
    myMouseHandler(w, b, a, m);                       // и своё
});
```

Больше кода, зато порядок ваш и виден на месте.

### Разделение: кому принадлежит мышь сейчас

Цепочка колбэков решает, что события **доходят** до обоих. Но кто на них **реагирует** — вопрос
приложения, и ImGui на него отвечает двумя флагами:

```cpp
ImGuiIO& io = ImGui::GetIO();
io.WantCaptureMouse     // мышь над панелью или тащит виджет
io.WantCaptureKeyboard  // ввод в текстовое поле
```

Без проверки получается ровно то, что видно в первой же сборке: тащишь ползунок — вместе с ним
крутится камера. В просмотрщике проверка стоит в `updateCamera` и снабжена комментарием именно об
этом:

```cpp
const bool held = glfwGetMouseButton(window, GLFW_MOUSE_BUTTON_RIGHT) == GLFW_PRESS ||
                  glfwGetMouseButton(window, GLFW_MOUSE_BUTTON_LEFT)  == GLFW_PRESS;

// Without this check, dragging a slider also spins the camera.
if (held && !io.WantCaptureMouse) {
    camera.yaw   += (mouseX - lastX) * sensitivity;
    camera.pitch -= (mouseY - lastY) * sensitivity;
}
```

Обратите внимание: камера читает мышь **опросом** (`glfwGetMouseButton`), а не колбэком. Это
проще и здесь уместно — но именно поэтому проверка `WantCaptureMouse` обязательна: опрос ничего не
знает ни про какую цепочку и вернёт «кнопка нажата» независимо от того, над панелью курсор или нет.

То же самое для клавиатуры: `WASD` в главе 4 надо гасить при `io.WantCaptureKeyboard`, иначе набор
имени в текстовом поле улетит камере — печатаете «wasd», камера едет.

### Порядок внутри кадра тоже важен

`io.WantCaptureMouse` за этот кадр становится действительным только после
`ImGui_ImplGlfw_NewFrame()` — до него там значение прошлого кадра. Значит `updateCamera` вызывается
**после** блока `NewFrame`, а не до. Ошибка даёт запаздывание на один кадр: первое нажатие на
ползунок всё-таки дёрнет камеру.

---

## 3.8. Изменение размера окна

Интерфейс сюда влезает неожиданным образом, и об этом стоит знать заранее.

ImGui сам узнаёт новый размер в `ImGui_ImplGlfw_NewFrame()` — он опрашивает окно, а не слушает
колбэк. Поэтому в вашем `FramebufferSizeCallback` **ничего для ImGui делать не нужно**:

```cpp
void FramebufferSizeCallback(GLFWwindow* window, int width, int height)
{
    auto* chain = static_cast<std::shared_ptr<SwapChain>*>(glfwGetWindowUserPointer(window));
    if (*chain) (*chain)->recreate(width, height);
}
```

Но есть один пункт, который на Vulkan **придётся** учесть: ImGui собрал свой пайплайн под
render pass свопчейна. Если пересоздание свопчейна меняет этот проход, пайплайн ImGui становится
несовместимым. В нашей обёртке `recreate()` сохраняет совместимость прохода, поэтому переинициализация
не нужна — но если вы дописываете обёртку и меняете формат цели на ходу, `initImgui` придётся
вызвать заново.

И напоминание из главы 0, потому что здесь оно кусает вдвойне: `glfwSetWindowUserPointer` надо
вызвать, иначе `*chain` — разыменование нуля. С интерфейсом эта строка нужна ещё и потому, что
масштаб дисплея (`viewDidChangeBackingProperties` на macOS) вызывает тот же колбэк при переносе
окна на другой монитор.

## 3.9. Один контекст на процесс

Про это уже говорилось в главе 0, но здесь место объяснить, почему это существенно.

У ImGui **глобальный контекст**. Не «глобальный по соглашению» — `ImGui::GetIO()` буквально
обращается к текущему контексту через статический указатель. Если в процессе окажутся две сборки
ImGui, у них будет по своему указателю, и получится два независимых интерфейса: приложение пишет
виджеты в один, обёртка рисует из другого.

Поэтому цель `imgui` в CMake обёртки создаётся **только если её ещё нет**:

```cmake
if(NOT TARGET imgui)
    add_library(imgui STATIC ${_imgui_sources})
    ...
endif()
```

И поэтому в проекте приложения `imgui` указывается в `target_link_libraries` явно — приложение
вызывает `ImGui::Begin` напрямую, значит это его зависимость, а не унаследованная.

Симптом двух контекстов: панель рисуется, но **не реагирует ни на что вообще**, и `io.Framerate`
показывает ноль или мусор. От симптома «колбэки перезаписаны» (3.7) отличается тем, что там
работает подсветка при наведении, а здесь не работает ничего.

---

## 3.10. Что обычно ломается

| Симптом | Причина |
|---|---|
| Сцена исчезла, панель на пустом фоне | `clear = true` в проходе интерфейса |
| Панели нет совсем, ошибок нет | забыт `ImGui::Render()` перед `renderInternalImgui` |
| Панель есть, ползунки не тащатся, подсветка работает | свои колбэки GLFW зарегистрированы **после** `ImGui_ImplGlfw_Init(..., true)` |
| Панель есть, не реагирует ни на что, `io.Framerate` мусор | две сборки ImGui, два контекста |
| Ползунок тащится вместе с камерой | не проверяется `io.WantCaptureMouse` |
| Первое нажатие всё равно дёргает камеру | `updateCamera` вызывается до `ImGui_ImplGlfw_NewFrame()` |
| «wasd» в текстовом поле едет камерой | не проверяется `io.WantCaptureKeyboard` |
| Падение в `initImgui` на Vulkan | вызван до создания свопчейна: нужен render pass и число изображений |
| Падение при выходе | `DestroyContext()` вызван раньше `Shutdown` бэкендов |
| Первый кадр заметно дольше | лениво грузится атлас шрифта, это нормально; отбрасывайте его при замерах |
| Панель мылится при MSAA | интерфейс рисуется в многовыборочную цель, а не в сведённую |

## 3.11. Проверка

1. Панель открывается поверх треугольника, сцена видна.
2. `ColorEdit3` меняет цвет треугольника **в тот же кадр**, без задержки.
3. Тащите ползунок — камера (когда она появится в главе 4) не двигается.
4. Тащите пустое место окна — камера двигается.
5. Окно меняет размер, панель остаётся на месте и не растягивается.
6. `io.Framerate` показывает осмысленное число, а не ноль.
7. Приложение закрывается без падения — проверьте на обеих платформах, порядок выключения
   единственный, где Metal и Vulkan ведут себя одинаково строго.
8. На Windows: включите `DMRENDER_VALIDATION=ON` и убедитесь, что консоль чиста. ImGui
   аллоцирует descriptor sets из своего пула, и валидатор сразу скажет, если его исчерпать —
   пул в обёртке рассчитан на 64 набора, чего хватает на текстуру шрифта плюс десятки
   пользовательских изображений.

## Итог

Интеграция ImGui — это три слоя, инициализируемые по отдельности: ядро, платформенный бэкенд
(наш, через GLFW) и рендер-бэкенд (внутри обёртки, потому что ему нужны нативные объекты).
Приложение вызывает `CreateContext` и `ImGui_ImplGlfw_Init` сам, всё остальное — четыре функции
`helper::*Imgui`, в подписях которых нет ни одного нативного типа.

Внутри кадра порядок не переставляется: проход → три `NewFrame` → виджеты → `Render()` →
`beginRenderPass` → `renderInternalImgui`. `clear = false`, иначе интерфейс сотрёт сцену.

С GLFW ImGui дружит через **цепочку колбэков**, а не через захват: он сохраняет предыдущий
обработчик и вызывает его первым. Отсюда единственное правило, которое стоит запомнить наизусть —
свои колбэки регистрировать **до** инициализации ImGui. А разделение «кому принадлежит мышь
сейчас» — это `io.WantCaptureMouse` и `io.WantCaptureKeyboard`, и проверять их обязан код камеры,
потому что он читает ввод опросом и о цепочке ничего не знает.

reverse-Z и камера, которую наконец есть чем крутить. Панель из этой главы с нами до конца книги:
